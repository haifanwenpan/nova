# 第 2 章 系统架构与顶层接口

这一章带你看懂顶层模块 `src/nova.v`（259 行）是如何把 52 个文件组装成一台完整 H.264 解码器的。重点搞清楚三件事：**两大模块的边界在哪、模块间靠哪些信号握手、外部存储和帧同步怎么工作**。

---

## 2.1 两大块的清晰划分

`nova.v` 内部只例化了 **2 个顶层子模块**：左半边 `BitStream_controller`（解析）和右半边 `reconstruction`（重建）：

```text
                            ┌──────────────────────────────────────────────────┐
   BitStream_buffer_input   │                  nova (src/nova.v)               │
   [15:0] ─────────────────▶│                                                  │
                            │  ┌────────────────────────────────────────────┐  │
   BitStream_ram_addr       │  │  BitStream_controller (744 行)             │  │
   [16:0] ◀─────────────────┼──│  [14 个功能子模块 + 5 个 RF]                │  │
                            │  │  ├─ BitStream_buffer     (128b 环形缓冲)   │  │
   BitStream_ram_ren        │  │  ├─ heading_one_detector (2/4/10 前导 1)   │  │
   (低有效) ◀───────────────┼──│  ├─ exp_golomb_decoding  (ue/se/te)        │  │
                            │  │  ├─ dependent_variable_decoding (u(v))     │  │
                            │  │  ├─ pc_decoding          (7b 位指针)       │  │
                            │  │  ├─ BitStream_parser_FSM (Gray 码状态机)   │  │
                            │  │  ├─ syntax_decoding      (语法元素寄存)    │  │
                            │  │  ├─ QP_decoding / CodedBlockPattern_dec    │  │
                            │  │  ├─ Intra4x4_PredMode_dec (+1 RF)          │  │
                            │  │  ├─ Inter_mv_decoding    (2611 行, +4 RF)  │  │
                            │  │  ├─ cavlc_decoder (7 功能子模块 + 3 RF)    │  │
                            │  │  ├─ bs_decoding          (905 行)          │  │
                            │  │  └─ bitstream_gclk_gen   (18 路门控时钟)   │  │
                            │  └─────────────┬──────────────────▲───────────┘  │
                            │     语法/系数/MV/bs               │ 握手反馈      │
                            │                ▼                  │              │
                            │  ┌────────────────────────────────┴───────────┐  │
   ext_frame_RAM0           │  │  reconstruction (625 行)                   │  │
   (cs_n/wr/addr[13:0],     │  │  [11 个实例]                               │  │
    读 data[31:0]) ◀───────▶┼──│  ├─ hybrid_pipeline_ctrl (块/MB 级调度)    │  │
                            │  │  ├─ IQIT                 (反量化+反变换)   │  │
   ext_frame_RAM1           │  │  ├─ Intra_pred_top       (+Intra_mbAddrB)  │  │
   (与 RAM0 乒乓)  ◀───────▶┼──│  ├─ Inter_pred_top       (LPE+CPE+滑窗)    │  │
                            │  │  ├─ sum                  (预测+残差+裁剪)  │  │
   dis_frame_RAM_din        │  │  ├─ rec_DF_RAM0/1 + ctrl (MB 双缓冲)       │  │
   [31:0] (共用写数据) ◀────┼──│  ├─ DF_top (pipeline+mem_ctrl+reg_ctrl)    │  │
                            │  │  ├─ ext_RAM_ctrl         (双帧存乒乓)      │  │
                            │  │  └─ rec_gclk_gen         (21 路门控时钟)   │  │
                            │  └────────────────────────────────────────────┘  │
                            └──────────────────────────────────────────────────┘
                                           │ pic_num[5:0] (调试帧号)
                                           │ slice_header_s6 (新帧开始脉冲)
```

**这条分界线极其干净**：
- **`BitStream_controller` 只管“读比特 → 吐语法元素”**，完全不碰像素值；
- **`reconstruction` 只管“吃语法元素 → 吐像素”**，完全不碰比特流。

## 2.2 两大块之间的全部接口信号（`nova.v:52-94`）

读懂 `nova.v:52-94` 声明的内部 wire，你就掌握了整颗芯片的数据流与控制流。它们按用途分为三类：

### 1. 控制与参数类（位流侧 → 重建侧）

| 信号 | 位宽 | 含义与用途 |
|---|---|---|
| `mb_type_general` | 4 | 重新编码后的宏块类型（见 2.4 节，最高位 `[3]` 直接区分 Intra/Inter） |
| `mb_num_h` / `mb_num_v` | 4 / 4 | 当前宏块在帧内的列号（0..10）与行号（0..8） |
| `slice_data_state` / `residual_state` / `cavlc_decoder_state` | 4 / 4 / 4 | 位流侧三层 FSM 的当前 Gray 码状态，直接喂给重建侧做控制与时钟门控 |
| `NextMB_IsSkip` / `LowerMB_IsSkip` | 1 / 1 | 右邻 / 下邻宏块是否为 skip（用于判断缓存更新是否可省电跳过） |
| `Is_skip_run_entry` / `skip_mv_calc` | 1 / 1 | 进入 `P_Skip` 连续跳过模式及每个 skip MB 的 MV 计算完成触发信号 |
| `disable_DF` | 1 | 综合了引脚 `pin_disable_DF` 与码流 `disable_deblocking_filter_idc` 的去块关闭信号 |
| `Intra16x16_predmode` / `Intra_chroma_predmode` | 2 / 2 | 16×16 亮度与 8×8 色度的帧内预测模式（0..3） |
| `Intra4x4_predmode_CurrMb` | 64 | 当前 MB 16 个 4×4 块的帧内模式打包（每块 4 bit，`16 × 4 = 64`） |
| `i4x4_CbCr` | 2 | 当前正在处理的色度 4×4 子块索引（0..3） |
| `QPy` / `QPc` | 6 / 6 | 亮度 / 色度量化参数（0..51） |
| `slice_alpha_c0_offset_div2` / `slice_beta_offset_div2` | 4 / 4 | 去块滤波的 α/β 偏移量（有符号 `÷2` 编码，使用时左移 1 位） |
| `CodedBlockPatternLuma` / `CodedBlockPatternChroma` | 4 / 2 | 编码块模式（CBP）：指示哪几个 8×8 亮度块及色度 DC/AC 有非零残差 |

### 2. 数据类（位流侧 → 重建侧）

| 信号 | 位宽 | 含义与精确打包格式 |
|---|---|---|
| `coeffLevel_0..15` | 9 × 16 | 当前 4×4 块的 16 个量化残差系数，**Zig-Zag 序**，9-bit 二进制补码（−256..+255；传入 `IQIT` 前在 `reconstruction.v:310-325` 符号扩展到 16-bit） |
| `TotalCoeff` | 5 | 当前 4×4 块的非零系数个数（0..16） |
| `mvx_CurrMb0..3` / `mvy_CurrMb0..3` | 32 × 8 | 当前 MB 的 16 个 4×4 块运动矢量，按**双 Z 8×8 象限**打包进 4 个 32-bit 寄存器，每字节存 1 个 8-bit 有符号 MV（单位 1/4 像素） |
| `mv_is16x16` / `mv_below8x8` | 1 / 4 | `mv_is16x16=1` 表示整 MB 共用 `mv*_CurrMb0[7:0]`；`mv_below8x8[i]=1` 表示第 `i` 个 8×8 子块细分到了 8×4/4×8/4×4 |
| `bs_V0..3` / `bs_H0..3` | 12 × 8 | 边界强度：`bs_Vk`（k=0..3）存第 `k` 条垂直边上从上到下 **4 个 3-bit `bs`**（`{[11:9],[8:6],[5:3],[2:0]}`）；`bs_Hk` 存第 `k` 条水平边上从左到右 4 个 3-bit `bs` |

### 3. 握手反馈类（双向协调两条流水线）

因为位流解析是**变长**的（一个块可能 1 拍也可能几十拍），而重建是**内容相关**的（跳块快、分数插值慢），两条流水线不能硬卡固定拍数，而是靠以下 10 根握手线动态配合：

| 信号 | 方向 | 触发意义（直白翻译） |
|---|---|---|
| `trigger_CAVLC` | 重建 → 位流 | `hybrid_pipeline_ctrl`：“我准备好了，请解下一个 4×4 块的残差系数！” |
| `end_of_NonZeroCoeff_CAVLC` | 位流 → 重建 | `cavlc_decoder`：“非零系数全解完并放好在 `coeffLevel_0..15` 了，`IQIT` 可以开算！” |
| `end_of_one_residual_block` | 位流 → 重建 | `cavlc_decoder`：“这一个 4×4 残差块（含全零块）解码收尾完成” |
| `curr_DC_IsZero` | 重建 → 位流 | `IQIT`：“当前块对应的 DC 系数是否为 0”（辅助跳过全零块） |
| `end_of_DCBlk_IQIT` | 重建 → 位流 | `IQIT`：“Intra16×16 或色度的 DC 块反变换算完了，可以继续解后面的 AC 块” |
| `blk4x4_rec_counter` | 重建 → 位流 | `sum.v` 当前正在重建第几个 4×4 块（0..23），反馈给 `bs_decoding` / `hybrid_pipeline_ctrl` |
| `end_of_one_blk4x4_sum` | 重建 → 位流 | `sum.v`：“一个 4×4 块已经相加重建完毕”（第 22 块结束时 `bs_decoding` 锁存 `mb_type_general_DF`） |
| `end_of_MB_DEC` | 重建 → 位流 | `hybrid_pipeline_ctrl`：“当前 MB 重建完 **且** 上一个 MB 去块滤波也完了，可以切下一个 MB！” |
| `gclk_end_of_MB_DEC` | 重建 → 位流 | 由 `end_of_MB_DEC` 门控出的单拍时钟沿，专门驱动“每 MB 仅更新一次”的寄存器（见第 8 章） |
| `end_of_BS_DEC` | 位流 → 重建 | `bs_decoding`：“48 条边的 `bs` 全算好了，`DF_top` 可以启动去块滤波！” |
| `end_of_one_frame` | 位流 → 重建 | `bitstream_gclk_gen` 帧定时器到期脉冲，驱动 `ext_RAM_ctrl` 翻转双帧存乒乓 |

> **关键设计直觉**：为什么要同时传 `end_of_MB_DEC` 和 `gclk_end_of_MB_DEC`？
> `end_of_MB_DEC` 是一个只高 1 拍的脉冲信号；对于每 MB 只需更新一次的寄存器（如 `nC_decoding` 的全零标志、`DF` 的 `indexA/B`），如果挂在常开的 `clk` 上并用 `if (end_of_MB_DEC)` 做使能，每拍时钟树都在耗电；改成直接挂在 `gclk_end_of_MB_DEC` 上，其余几百拍时钟直接停振，省下大量动态功耗。

## 2.3 顶层端口一览（`nova.v:18-50`）

```verilog
module nova (
    clk, reset_n,
    BitStream_buffer_input, BitStream_ram_ren, BitStream_ram_addr,
    pic_num, pin_disable_DF, freq_ctrl0, freq_ctrl1,
    ext_frame_RAM0_cs_n, ext_frame_RAM0_wr, ext_frame_RAM0_addr, ext_frame_RAM0_data,
    ext_frame_RAM1_cs_n, ext_frame_RAM1_wr, ext_frame_RAM1_addr, ext_frame_RAM1_data,
    dis_frame_RAM_din,
    slice_header_s6    // 规格书 Table 6 未列，专为仿真捕获帧边界引出

```

### 1. 时钟与复位

| 端口 | 方向 | 说明 |
|---|---|---|
| `clk` | in | 全局唯一主时钟（标称 1~10 MHz，QCIF@30fps 跑 1.5 MHz） |
| `reset_n` | in | 低有效复位信号（详见 2.7 节关于同步/异步复位的核实） |

### 2. 外部码流 SRAM 接口

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `BitStream_ram_ren` | out | 1 | 读使能，**低有效** |
| `BitStream_ram_addr` | out | 17 | 读地址，范围 `0..131071`（256 KB 空间），到顶饱和不回绕（`BitStream_buffer.v:116`） |
| `BitStream_buffer_input` | in | 16 | 同步 SRAM 返回的 16-bit 码流字（1 拍同步读延迟） |

### 3. 外部双帧存接口（乒乓 Ping-Pong）

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `ext_frame_RAM0_cs_n` / `RAM1_cs_n` | out | 1 | 片选，**低有效** |
| `ext_frame_RAM0_wr` / `RAM1_wr` | out | 1 | 读写选择：**1 = 写，0 = 读** |
| `ext_frame_RAM0_addr` / `RAM1_addr` | out | 14 | 32-bit 字地址（理论 16,384 word，QCIF 实际用 `0..9503` 共 38,016 字节） |
| `ext_frame_RAM0_data` / `RAM1_data` | **in** | 32 | 读数据输入（原双向口 `inout` 已被作者注释改成分离的单向口） |
| `dis_frame_RAM_din` | out | 32 | **两组帧存共用的写数据输出**（每次写 4 个水平相邻像素，`[7:0]` 为最左像素） |

### 4. 控制与调试接口

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `pin_disable_DF` | in | 1 | 引脚强制关闭去块滤波（1=关，0=由码流决定），用于低功耗降级或调试 |

| `pic_num` | out | 6 | 已完成解码的帧计数低 6 位（0..63 循环），仅调试用 |
| `slice_header_s6` | out | 1 | 解析到下一帧 Slice Header 的 `frame_num_s`（状态码 `4'b0110 = 6`）时拉高，标志上一帧已完整落盘 |

## 2.4 宏块类型重编码：`mb_type_general`（`nova_defines.v:48-63`）

H.264 规范里，I 帧和 P 帧的 `mb_type` 编号体系不统一（例如 `mb_type == 0` 在 I 帧是 `I_4x4`，在 P 帧是 `P_L0_16x16`）。为了不让后面几十个模块都同时判断 `slice_type` 和 `mb_type`，`syntax_decoding.v:319-347` 把它们统一翻译成一个 **4-bit `mb_type_general`**：

| `mb_type_general` | 宏名 | 含义 | 所属路径 |
|---|---|---|---|
| `4'b0000` | `MB_Inter16x16` | P 帧 16×16 帧间 | Inter |
| `4'b0001` | `MB_Inter16x8` | P 帧 16×8（上下 2 分区） | Inter |
| `4'b0010` | `MB_Inter8x16` | P 帧 8×16（左右 2 分区） | Inter |
| `4'b0011` | `MB_P_8x8` | P 帧 8×8（4 子块，可再细分到 4×4） | Inter |
| `4'b0100` | `MB_P_8x8ref0` | P 帧 8×8（全部固定用 ref0） | Inter |
| `4'b0101` | `MB_P_skip` | P_Skip（16×16，MV 由邻居推导，无残差） | Inter（跳过残差） |
| `4'b0110` | `MB_I_PCM` | 原始像素直传（宏已留，但 RTL 未接入） | 未实现 |
| `4'b1000` | `MB_Intra16x16_CBPChroma0` | 帧内 16×16，色度 CBP = 0（无色度残差） | Intra16×16 |
| `4'b1001` | `MB_Intra16x16_CBPChroma1` | 帧内 16×16，色度 CBP = 1（仅色度 DC） | Intra16×16 |
| `4'b1010` | `MB_Intra16x16_CBPChroma2` | 帧内 16×16，色度 CBP = 2（色度 DC+AC） | Intra16×16 |
| `4'b1100` | `MB_Intra4x4` | 帧内 4×4 | Intra4×4 |
| `4'b1111` | `MB_type_rst` | 复位态 | — |

**看穿这两位编码技巧**（读后续代码时天天用到）：
- **`mb_type_general[3]`**：**1 个 bit 直接区分 Intra(`1`) 和 Inter(`0`)**！
- **`mb_type_general[3:2]`**：`2'b10` = **Intra16×16**，`2'b11` = **Intra4×4**（排除复位态），`2'b0x` = **Inter**！
- 对于 Intra16×16，低两位 **`mb_type_general[1:0]`** 直接就是 `CodedBlockPatternChroma`（0 / 1 / 2），连译码逻辑都省了！

## 2.5 变频 / 帧率自限速控制（`freq_ctrl[1:0]`）

在 `src/nova_defines.v:32-35` 和 `src/bitstream_gclk_gen.v:89-123` 里，作者做了一个简单的帧周期定时器：

```verilog
// bitstream_gclk_gen.v:90-96
case ({freq_ctrl1, freq_ctrl0})
    2'b00:   cycles_per_frame <= `cycles_per_frame0; // 45,000 拍/帧
    2'b01:   cycles_per_frame <= `cycles_per_frame1; // 50,000 拍/帧 (akiyo300 默认)
    2'b11:   cycles_per_frame <= `cycles_per_frame3; // 70,000 拍/帧
    default: cycles_per_frame <= `cycles_per_frame2; // 57,300 拍/帧 (2'b10，foreman300 推荐)
endcase
```

**工作原理**：每当新帧进入 `start_code_prefix`，`frame_cycle_counter` 清零并开始逐拍累加；数满 `cycles_per_frame` 后拉高 1 拍 `end_of_one_frame`。在这之前，即使当前帧 99 个宏块已经提前解码完成，**解析器也会停在 `rst_parser` 空等**，直到 `end_of_one_frame` 拉高才翻转外部帧存并启动下一帧。

**两个非常关键的实测结论**（详见 [第 9 章 9.7 节](09-仿真环境与ffmpeg对比.md)）：
1. **`freq_ctrl` 与宏块解码速度完全正交**：四档设置下，解码单个宏块的硬件速度一模一样（P 帧均约 330 cycles/MB，I 帧约 423 cycles/MB）；`freq_ctrl` 只决定帧尾“空等多久”来控制恒定帧率（例如 50,000 cycles/帧 × 30 fps = 1.5 MHz）；
2. **`cycles_per_frame` 必须大于最复杂单帧的真实解码周期**：二分实测表明 `akiyo300` 第 1 帧（全 Intra 的 IDR 帧）真实需要约 **42,100 拍**（`cf0 = 42095` 会因下一帧提前覆盖帧存尾部而丢 40 个像素，`42100` 恰好 300 帧比特精确通过）。

> ⚠️ **仿真踩坑提示**：在我们的 `sim/tb/tb_nova.v` 里，`IDLE_FLUSH = 20000` 用来兜底吐出末帧。但在 `freq=2`（57,300）和 `freq=3`（70,000）下，P 帧只需 ~33,000 拍就写完帧存，帧尾空等时间超过 20,000 拍，会提前触发 testbench 的 `IDLE_FLUSH`（并非硬件算力抖动！详见 [第 9 章 9.7](09-仿真环境与ffmpeg对比.md)）。

## 2.6 帧同步机制：`slice_header_s6` 与脏缓冲标志

`src/BitStream_parser_FSM_gating.v:304` 引出了一个专门的调试信号：

```verilog
assign slice_header_s6 = (slice_header_state == `frame_num_s) ? 1'b1 : 1'b0;
```

（名字里的 `s6` 来自 `nova_defines.v:124`：`frame_num_s` 的 Gray 码值是 `4'b0110 = 6`。）

当解析器走到新帧的 `frame_num_s` 时：
- 上一帧的 99 个宏块早已完成重建并写完外部帧存（因为之前已经历了 `end_of_one_frame` 定时等待）；
- 外部帧存的乒乓指针 `ext_frame_RAM_sel` 已经翻转，新帧尚未动笔写像素；
- 所以 `slice_header_s6` 拉高的一瞬间，正是把**上一帧完整 YUV 读出显示**的最佳窗口。

原版 `src/ext_frame_RAM0/1_wrapper.v` 用 `pic_num[0]` 奇偶判断该读哪块帧存，一旦码流截断或跨 64 帧边界极易出错。我们的 `sim/tb/tb_nova.v` 改成**脏缓冲标志（`buf0_written` / `buf1_written`）**：哪块帧存在上一帧期间被写过，就在 `slice_header_s6` 时把那块原样吐出为标准 YUV420p。

## 2.7 复位机制（核实后的重要细节）

阅读 `src/*.v` 时，你会发现全芯片的触发器其实分**两种复位风格**：

1. **主时钟 `clk` 域的寄存器**（如 `BitStream_buffer.v`、`syntax_decoding.v`、`QP_decoding.v`、`Inter_mv_decoding.v`、`bitstream_gclk_gen.v` 的 `frame_cycle_counter`、`DF_mem_ctrl.v` 的 `DF_12_cycles`）：采用**同步低有效复位**：
   ```verilog
   always @ (posedge clk)
       if (reset_n == 1'b0) ...
   ```
   因此外部复位脉冲 `reset_n == 0` 必须覆盖至少 1~2 个 `clk` 上升沿（规格书要求至少 2 个周期）。

2. **门控时钟 `gclk_xxx` 域的寄存器**（如各 FSM 状态寄存器、`IQIT` 计数器、`DF_pipeline` 流水级寄存器）：采用**异步低有效复位**：
   ```verilog
   always @ (posedge gclk_xxx or negedge reset_n)
       if (reset_n == 1'b0) ...
   ```
   **为什么门控时钟域必须用异步复位？** 因为芯片刚上电时，门控时钟 `gclk_xxx` 往往处于**关闭状态（没有时钟沿）**！如果用同步复位，这些触发器永远无法清零，会一直保持 `x` 导致全芯片死锁；用了 `negedge reset_n` 异步复位后，**即使 `gclk_xxx` 停振，只要 `reset_n` 拉低，触发器也会立刻复位到初始态！**

复位释放后，`BitStream_buffer.v` 的 `reset_counter` 从 `0` 数到 `10`（共 **10 个时钟周期**），连续从码流 SRAM 预读 **8 个 16-bit word（填满整个 128-bit 环形缓冲）**，随后拉低 `BitStream_buffer_valid_n = 0`，正式启动 H.264 解码。

## 2.8 99 个宏块的无除法扫描

QCIF 一帧有 `11 × 9 = 99` 个宏块。如果只维护一个 `mb_num`（0..98），每次算行列号都要做 `mb_num / 11` 和 `mb_num % 11`（除法器在 ASIC 里极贵）。

`src/BitStream_parser_FSM_gating.v:482-500` 直接用三个极简增量计数器同步维护：

```verilog
// 每当完成一个普通宏块(mb_num_update)或跳过一个宏块(skip_run_duration)时更新：
mb_num_h <= (mb_num_h == 10) ? 0 : (mb_num_h + 1);              // 0..10 循环（11 列）
if (mb_num_h == 10)
    mb_num_v <= (mb_num_v == 8) ? 0 : (mb_num_v + 1);           // 满一行进位，0..8 循环（9 行）
mb_num   <= (mb_num == 98) ? 0 : (mb_num + 1);                  // 0..98 循环（99 MB）
if (mb_num == 98)
    pic_num  <= pic_num + 1;                                    // 整帧结束，帧号 +1
```

只用三个 4~7 bit 加法器就完全消灭了除 11 运算。代价是 `10`、`8`、`98` 作为字面量硬编码散落在工程各处 —— 改分辨率时必须系统替换（见 [第 10 章 10.2 节](10-兼容性陷阱与移植指南.md)）。
