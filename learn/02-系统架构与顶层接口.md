**分界线在 `coeffLevel_0..15` / `mvx_CurrMb0..3` / `mb_type_general` / `bs_V*` / `bs_H*`**。

这条分界线非常干净：**重建侧完全不碰位流，位流侧完全不碰像素**。
唯一例外是 `reconstruction` 里的 `DF_mem_ctrl` 会通过 `dis_frame_RAM_*`
把像素直接写进外部帧存——但那已经是最后一步了。

## 2.2 两大块之间的接口清单

这是 `nova.v:60-95` 里声明的跨模块 wire，**理解它们是理解整个设计的钥匙**：

### 控制类（位流侧 → 重建侧）

| 信号 | 位宽 | 含义 |
|---|---|---|

| `mb_num_h` / `mb_num_v` | 4 / 4 | 当前宏块在画面中的列/行号（0..10 / 0..8） |
| `blk4x4_rec_counter` | 5 | 重建到第几个 4×4 块（0..23） |
| `slice_data_state` | 4 | slice_data 层的 FSM 状态（Gray 码） |
| `residual_state` | 4 | 残差解码的 FSM 状态（Gray 码） |
| `cavlc_decoder_state` | 4 | CAVLC 解码器的 FSM 状态（Gray 码） |
| `NextMB_IsSkip` / `LowerMB_IsSkip` | 1 / 1 | 右邻/下邻 MB 是否为 skip（用于判断预测可用性） |
| `disable_DF` | 1 | 本 slice 是否关闭去块滤波 |
| `Intra16x16_predmode` | 2 | 帧内 16×16 预测模式（0..3） |
| `Intra4x4_predmode_CurrMb` | 64 | 16 个 4×4 块的预测模式，每块 4 bit |
| `Intra_chroma_predmode` | 2 | 色度预测模式（0..3） |
| `i4x4_CbCr` | 2 | 当前处理的是哪块色度（Cb/Cr 索引） |

| `slice_alpha_c0_offset_div2` / `slice_beta_offset_div2` | 4 / 4 | 去块滤波的 α/β 偏移（有符号，−6..+6，左移 1 位存储） |
| `CodedBlockPatternLuma` / `Chroma` | 4 / 2 | 编码块模式（哪些 4×4 块有非零系数） |

### 数据类（位流侧 → 重建侧）

| 信号 | 位宽 | 含义 |
|---|---|---|
| `coeffLevel_0..15` | 9 × 16 | 16 个量化后系数，**zig-zag 序**，2 补码（−256..255） |
| `TotalCoeff` | 5 | 当前 4×4 块的非零系数个数（0..16） |
| `mvx_CurrMb0..3` / `mvy_CurrMb0..3` | 32 × 8 | 当前 MB 的 4 个 8×8 子块运动矢量，每个 32 位打包了 4 个 8 位分量 |
| `mv_is16x16` | 1 | 整个 MB 是否用一个 16×16 MV |
| `mv_below8x8` | 4 | 4 个 8×8 子块是否各自细分为 8×8 以下 |
| `bs_V0..3` / `bs_H0..3` | 12 × 8 | 边界强度，4 个垂直边 + 4 个水平边各 12 位（3 个 4×4 边界 × 3 bit + 余） |

### 握手类（重建侧 → 位流侧）

这是整个设计最精妙的部分——**两条流水线用极少的信号互相"看对方进度"**：

| 信号 | 方向 | 作用 |
|---|---|---|
| `trigger_CAVLC` | 重建 → 位流 | "我要开始解下一个块的系数了" |
| `end_of_NonZeroCoeff_CAVLC` | 位流 → 重建 | "系数解完了，可以开始反量化" |
| `end_of_one_blk4x4_sum` | 重建内部 | 一个 4×4 块重建完成 |
| `end_of_MB_DEC` | 位流 → 重建 | 一个宏块的语法解完了 |
| `gclk_end_of_MB_DEC` | 重建 → 位流 | 上述信号的**门控时钟版本**，跨时钟域握手用 |
| `end_of_one_residual_block` | 位流 → 重建 | 一个残差块解完 |
| `curr_DC_IsZero` | 重建 → 位流 | DC 系数是否全零（用于跳过某些解码步骤） |
| `end_of_DCBlk_IQIT` | 重建 → 位流 | DC 反变换完成 |
| `end_of_BS_DEC` | 位流 → 重建 | 边界强度计算完成，可以启动去块滤波 |
| `end_of_one_frame` | 位流 → 重建 | 一帧解码完成，帧存交换 |

> **注意 `gclk_end_of_MB_DEC` 这个信号**。它和 `end_of_MB_DEC` 内容一样，
> 但经过了门控时钟锁存。为什么要多此一举？因为位流侧的解码器大部分时间
> 时钟是被门控关掉的（见第 8 章），如果直接用组合逻辑的 `end_of_MB_DEC`
> 去触发一个"关着时钟"的触发器，会丢失事件。用门控时钟版本保证
> **事件只在时钟真正到来的那一拍被采样**。

## 2.3 顶层端口一览

`nova.v:19-50` 定义的全部端口（比规格书 Table 6 多一个 `slice_header_s6`）：

```verilog
module nova (clk, reset_n, BitStream_buffer_input, BitStream_ram_ren, BitStream_ram_addr,
    pic_num, pin_disable_DF, freq_ctrl0, freq_ctrl1,
    ext_frame_RAM0_cs_n, ext_frame_RAM0_wr, ext_frame_RAM0_addr, ext_frame_RAM0_data,
    ext_frame_RAM1_cs_n, ext_frame_RAM1_wr, ext_frame_RAM1_addr, ext_frame_RAM1_data,
    dis_frame_RAM_din,
    slice_header_s6);          // ← 规格书没列这个，是为仿真方便加的 debug 输出
```

### 时钟与复位

| 端口 | 方向 | 说明 |
|---|---|---|
| `clk` | in | 单一时钟，全同步设计 |
| `reset_n` | in | **低有效**异步复位 |

**整个设计只有一个时钟、一个复位**，没有跨时钟域问题（门控时钟是同一时钟的派生，
不是独立时钟域）。这对 ASIC 后端非常友好。

### 位流接口

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `BitStream_buffer_input` | in | 16 | 从外部 SRAM 读来的 16 bit 数据 |
| `BitStream_ram_ren` | out | 1 | 读使能，**低有效** |
| `BitStream_ram_addr` | out | 17 | SRAM 地址（131072 word × 16 bit = 256 KB 码流空间） |

`BitStream_ram_addr` 是 17 位，正好覆盖 `Beha_Bitstream_ram_size = 131071`。
注意 `BitStream_buffer.v:116` 有个特殊处理：**地址到 131071 就不再增加**
（`no wrap around`），防止读越过码流末尾回绕到开头。

### 外部帧存接口（两组，乒乓）

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `ext_frame_RAM0_cs_n` | out | 1 | 片选，低有效 |
| `ext_frame_RAM0_wr` | out | 1 | 写使能，高有效 |
| `ext_frame_RAM0_addr` | out | 14 | 地址（16384 word × 32 bit = 64 KB/帧） |
| `ext_frame_RAM0_data` | **in** | 32 | 读数据输入 |
| `dis_frame_RAM_din` | out | 32 | **两组共用的写数据输出** |

**注意 `ext_frame_RAM*_data` 是 `input` 而不是 `inout`**。原代码里
`//inout [31:0] ext_frame_RAM0_data;` 这行被注释掉了，改成 `input`。
这意味着写数据走独立的 `dis_frame_RAM_din`（两组帧存共用一条写数据线），
读数据各自输入。这是典型的**单端口 SRAM 用法**：读和写共用地址线，
但数据线分开，靠 `cs_n`/`wr` 区分方向。

实际容量：每帧 9504 word × 32 bit = **38016 字节**，正好等于
176×144×1.5 = 38016 —— 即一帧 YUV420p 的大小，**没有padding**。

### 控制与调试

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `pin_disable_DF` | in | 1 | 引脚强制关 DF（=1 关，=0 由码流决定）。用于低功耗模式或调试 |
| `freq_ctrl0` / `freq_ctrl1` | in | 1 / 1 | 变频控制，选 4 档 `cycles_per_frame`（见 §2.5） |
| `pic_num` | out | 6 | 当前解码图像号低 6 位，**仅供 debug** |
| `slice_header_s6` | out | 1 | 解析到 slice_header 的 `frame_num` 字段时拉高，表示"上一帧已完成" |

## 2.4 宏块类型编码

`nova_defines.v` 把 H.264 的 `mb_type` 重新编码成 4 bit 的 `mb_type_general`。
**这是理解整个设计的核心表**：

| `mb_type_general` | 宏 | 含义 | 重建路径 |
|---|---|---|---|
| `4'b0000` | `MB_Inter16x16` | P 帧 16×16 帧间 | inter |
| `4'b0001` | `MB_Inter16x8` | P 帧 16×8（2 个分区） | inter |
| `4'b0010` | `MB_Inter8x16` | P 帧 8×16（2 个分区） | inter |
| `4'b0011` | `MB_P_8x8` | P 帧 8×8（4 个分区，可再细分） | inter |
| `4'b0100` | `MB_P_8x8ref0` | P 帧 8×8，全部用 ref0 | inter |
| `4'b0101` | `MB_P_skip` | P_Skip（16×16，MV 由预测得出，无残差） | inter（bypass） |
| `4'b0110` | `MB_I_PCM` | I_PCM（像素直接写在码流里） | 直通 |
| `4'b0111` | `MB_type_reserved0` | 保留 | — |
| `4'b1000` | `MB_Intra16x16_CBPChroma0` | 帧内 16×16，色度 CBP=0 | intra |
| `4'b1001` | `MB_Intra16x16_CBPChroma1` | 帧内 16×16，色度 CBP=1 | intra |
| `4'b1010` | `MB_Intra16x16_CBPChroma2` | 帧内 16×16，色度 CBP=2 | intra |
| `4'b1011` | `MB_type_reserved1` | 保留 | — |
| `4'b1100` | `MB_Intra4x4` | 帧内 4×4 | intra |
| `4'b1101` / `4'b1110` | `MB_type_reserved2/3` | 保留 | — |
| `4'b1111` | `MB_type_rst` | 复位值 | — |

**关键观察**：
- **最高位 `[3]` 就是 intra/inter 的判据**。`[3]==1` 是 intra，`[3]==0` 是 inter。
  代码里到处是 `if (mb_type_general[3])` 这样的判断，非常省逻辑。
- 剩余 3 位 `[2:0]` 只在 inter 时有意义，编码顺序是 H.264 表 7-14 的顺序
  （0..4 对应 P 帧的 5 种，5 是 skip）。intra 时 `[2:0]` 用来编码
  "Intra16×16 + 色度 CBP"或"Intra4×4"。

### 为什么 0000 是 Inter16x16 而不是 Intra4x4？

因为 **inter 是常态、intra 是例外**。让最常见的类型编码为全 0，
可以让状态机的默认分支（`default`）落在最短路径上，减少比较逻辑翻转。
配合 Gray 码状态机，这是同一种思路：**让最常见的值翻转位最少**。

## 2.5 变频控制（DVFS 接口）

`nova_defines.v` 里定义：

```verilog
`define cycles_per_frame0  17'd45000
`define cycles_per_frame1  17'd50000
`define cycles_per_frame2  17'd57300
`define cycles_per_frame3  17'd70000
```

`bitstream_gclk_gen.v:88-125` 用 `case ({freq_ctrl1, freq_ctrl0})` 选择：

| `freq_ctrl1` | `freq_ctrl0` | 选中 | `cycles_per_frame` |
|---|---|---|---|
| 0 | 0 | cf0 | 45000 |
| 0 | 1 | cf1 | 50000 |
| 1 | 1 | cf3 | 70000 |
| 1 | 0 | **cf2**（default） | 57300 |

这个机制的本质是**自限速**：`frame_cycle_counter` 数到 `cycles_per_frame` 就产生
`end_of_one_frame`，在此之前 parser 不启动下一帧的解析。所以
**`cycles_per_frame` 越小，仿真/硬件跑得越快，但必须大于"一帧真正需要的周期数"**，
否则会丢帧。

### 为什么 4 档差这么多？

看 `nova_defines.v` 的注释就能明白——这是**历史遗留**：

```
//50000 -> 51500 -> 52000 -> 52500 -> 55000 -> 56000 -> 56500 -> 57300
```

作者一开始设 50000（foreman300 刚好够），后来发现某些序列不够就一路加码，
每次加都是因为"跑某个序列丢帧了"。最终 57300 是能跑通所有测试序列的值。
**`cf0 = 45000` 是最小值，只能跑 akiyo 这类极低运动序列。**

> **实测验证**（第 9.7 节，14 帧稳态）：
>
> | `freq` | `cycles_per_frame` | 实测 cycles/帧 | 逐帧增量 |
> |---|---|---|---|
> | `0` | 45000 | **45009** | 精确 +45004 |
> | `1` | 50000 | **50009** | 精确 +50004 |
> | `2` | 57300 | 57046 | 有抖动 |
> | `3` | 70000 | 68839 | 抖动更大 |
>
> **前两档的增量精确等于 `cycles_per_frame + 4`**，那 4 个周期是帧边界握手开销。
> 说明这两档下重建流水线有富余，**完全在等速率控制的放行信号**。
> 后两档开始抖动，是因为瓶颈从"速率控制"转移到了"重建算力"（内容相关）。
>
> **关键：`freq_ctrl` 与 MB 级速度完全正交。** 探针实测四档下帧内
> MB 间隔都是 **330 cycles/MB**，一个周期都不差。`freq_ctrl` 只决定
> "解析器什么时候开始解下一帧"，不改变"跑一个 MB 要多久"。
>
> **`cf0` 的真实下限是 42100**（二分法：42095 丢 40 像素、42100 干净通过，
> 300 帧复验 PASS）。所以 akiyo 的算力需求是 42100 cycles/帧，
> 出厂值 45000 有 6.4% 余量 —— 余量留给 foreman 这类复杂序列。

## 2.6 帧同步机制

### `slice_header_s6` 的巧妙设计

```verilog
// BitStream_parser_FSM_gating.v:304
assign slice_header_s6 = (slice_header_state == `frame_num_s)? 1'b1 : 1'b0;
```

`frame_num` 是 **slice header 里第一个与"这是新的一帧吗"相关的字段**。
当解析器走到这个字段时，意味着：

1. 上一帧的所有宏块**语法**已经解完
2. 新一帧的 slice header 正在解析

此时 `end_of_one_frame` 的速率控制计数器归零，`ext_frame_RAM_sel` 翻转。

**为什么不等"上一帧像素全部写完"再翻转？**
因为走 `frame_num` 字段时，上一帧的**最后一个宏块**可能还在去块滤波流水线里。
但去块滤波写的是 `ext_frame_RAM_sel` 指向的**旧** buffer，而此时选择器还没翻转
（翻转在 `end_of_one_frame` 的下一拍）。等到新帧的第一个宏块要写像素时，
旧帧的最后几个宏块早已写完了。

**这是一个"用流水线深度换时序余量"的设计**：允许帧边界前后有约
200 cycles 的交叠，不需要全局 stall。

### 我们的 testbench 为什么改成"脏标志"

原 `ext_frame_RAM*_wrapper.v` 用 `pic_num[0]` 判断哪个 buffer 该吐帧：

```verilog
// ext_frame_RAM0_wrapper.v（原始写法）
if (slice_header_s6 == 1'b1 && pic_num[0] == 1'b1)
    $fdisplay(display_file, ...);
```

这依赖 `pic_num` 的奇偶性，非常脆弱：
- 如果码流从中间开始（比如只切出第 5..10 帧），奇偶就错了
- 如果丢帧，奇偶也错了

我们的 testbench 改成**脏标志**（`sim/tb/tb_nova.v`）：

```verilog
// 每次有写操作就置位
always @(posedge clk)
    if (ext_frame_RAM0_cs_n == 0 && ext_frame_RAM0_wr == 1) buf0_written <= 1'b1;

// slice_header_s6 拉高时，把"上次写过的那块"吐出来
if (slice_header_s6 == 1'b1) begin
    if (buf0_written && !buf1_written)      emit_picture(0);
    else if (buf1_written && !buf0_written) emit_picture(1);
    ...
end
```

这样无论从码流哪个位置开始、无论 `pic_num` 是多少，都能正确吐帧。
**这是复用这个 IP 时必须改的第一处。**

## 2.7 复位行为

`reset_n` 是**异步低有效复位**。整个设计里所有触发器都是这种写法：

```verilog
always @ (posedge gclk_xxx or negedge reset_n)
    if (reset_n == 0)
        state <= `rst_xxx;
    else
        ...
```

注意这里用的是**门控时钟** `gclk_xxx` 而不是 `clk`。所以复位虽然对 `clk` 是异步的，
但**对每个门控时钟分支都是独立的异步复位**——门控时钟关掉时触发器不响应复位，
但门控时钟关掉时触发器本来也不工作，所以没有问题。

复位后需要约 **4 个时钟周期**才能开始工作：`BitStream_buffer.v` 的
`reset_counter` 从 0 数到 10，做上电预充（把 128 bit 缓冲填到半满）。

## 2.8 99 个宏块的扫描顺序

QCIF = 11 列 × 9 行 = 99 个宏块。扫描是**光栅顺序**（raster scan）：

```verilog
// BitStream_parser_FSM_gating.v
mb_num <= (mb_num == 98) ? 0 : (mb_num + 1);

// mb_num 到 mb_num_h / mb_num_v 的分解
mb_num_h = mb_num % 11   // 0..10
mb_num_v = mb_num / 11   // 0..8
```

代码里没有用除法器，而是用**状态机的增量计数**：`mb_num_h` 到 10 就归零并
让 `mb_num_v` 加 1。这样避免了一个除法器（约 500 门）。

**注意 `98` 这个数字在代码里出现多次**（`bitstream_gclk_gen.v` 的 `nal_ena`/`slice_ena`、
`BitStream_parser_FSM_gating.v` 的 `pic_num` 递增条件）。
**这是硬编码的 QCIF 假设**——OpenCores 项目页上作者专门提醒：
> "改分辨率时要特别注意 `mb_num_h`（nova 中 0~10）与 `mb_num_v`（nova 中 0~8）计数器"

详见第 10 章。
