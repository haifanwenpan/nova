# 第 3 章 位流解析链路

这一章逐层拆解 `src/BitStream_controller.v`（744 行，内部例化 **14 个功能子模块 + 5 个寄存器堆 RF**）：它是怎样把外部码流 SRAM 里的一串原始字节，一步步翻译成重建侧能直接吃的 `coeffLevel_0..15`、`mvx/mvy_CurrMb0..3`、`mb_type_general` 和 `bs_V/H` 的。

> 📖 **概念预热**：如果你还不熟悉 NAL、SPS/PPS、指数哥伦布码（ue/se/te）、CAVLC 或运动矢量预测，请先读 [第 0 章](00-H.264基础.md) 的 0.1~0.4、0.6、0.7 节，再回来对照源码逐行看。

## 3.2 存储层：外部码流 SRAM（`Beha_BitStream_ram.v`）

`nova_defines.v:18` 定义了码流地址最大下标 `131071`（`17-bit` 地址 `0..131071` = 131,072 个 16-bit word = **256 KB**）。

读操作行为模型见 `src/Beha_BitStream_ram.v:33-35`：

```verilog
always @ (posedge clk)
    if (BitStream_ram_ren == 0)
        BitStream_ram_data <= #2 BitStream_ram[BitStream_ram_addr];
```

- **真实读延迟**：这是一个 **1 个时钟周期**的同步读 SRAM（`#2` 只是仿真用的 2 ns 输出传播延迟，不是 2 个时钟周期！）。
- **为什么 `BitStream_buffer.v` 等 2 拍才把数据写进 `BS_buffer`？** 因为 `BitStream_buffer.v` 自己发出的 `BitStream_ram_ren` 和 `BitStream_ram_addr` 也是寄存器输出（第 1 拍更新地址，第 2 拍 SRAM 同步读出数据，第 3 拍 `BitStream_buffer` 采样写入）。
- **地址不回绕**（`BitStream_buffer.v:116`）：
  ```verilog
  else if (half_fill_counter > 0 && half_fill_counter < 5 && BitStream_ram_addr != 17'd131071)
      BitStream_ram_addr <= BitStream_ram_addr + 1;
  ```
  读到最后一个字就钉死在 `131071`，防止越过码流末尾回绕到 `0` 重头死循环。

## 3.3 缓冲层：128-bit 环形桶形缓冲（`BitStream_buffer.v`）

H.264 码流是**按任意比特变长消耗**的（这一拍消费 1 bit，下一拍可能消费 13 bit），而外部 SRAM 只能每次吐 **16-bit 定长字**。`BitStream_buffer.v` 用一个 **128-bit 环形缓冲** 完美化解这个矛盾。

### 1. 比特序声明与大端反转（`BitStream_buffer.v:34, 120-149`）

```verilog
reg [0:127] BS_buffer;  // 注意下标顺序 [0:127]：下标 0 在最左（最早到达的比特）！
```

当 `reset_counter` 处于 `2..9`（上电预充 8 个 word = 128 bit）或 `half_fill_counter` 处于 `2..5`（运行中半满重填 4 个 word = 64 bit）时，把 16-bit 输入按 `buffer_index[6:4]`（8 个 16-bit 槽）写入：

```verilog
// BitStream_buffer.v:123-128（槽 0 示例，其余槽 1..7 类似）
else if ((reset_counter > 1 && reset_counter < 10) ||
         (half_fill_counter > 1 && half_fill_counter <= 5))
    case (buffer_index[6:4])
        3'b000: for (i = 0; i < 16; i = i + 1)
                    BS_buffer[i] <= BitStream_buffer_input[15 - i];
        ...
    endcase
```

**为什么要写 `BitStream_buffer_input[15 - i]`？** 因为 H.264 是 MSB-first（大端比特序）：SRAM 返回的 16-bit 字里，最高位 `[15]` 是最先到来的比特，必须放到 `BS_buffer[0]`；`[14]` 放到 `BS_buffer[1]`；以此类推。

### 2. 上电预充与双半区乒乓重填（`BitStream_buffer.v:57-117`）

把 128 bit 缓冲想象成一个分成**前半区（0..63）**和**后半区（64..127）**的圆环：
- **上电预充（`reset_counter`: `0 → 10`）**：
  - `reset_counter = 1..8`：地址 `BitStream_ram_addr` 递增 8 次，连续读 8 个 word；
  - `reset_counter = 2..9`：8 个 word 依次填入槽 0..7（填满整个 128-bit 缓冲），`buffer_index` 每次 `+16`，满 8 次正好回绕回 `0`；
  - `reset_counter == 10`：拉低 `BitStream_buffer_valid_n <= 1'b0`，通知解析器“码流就绪，可以开工！”。
- **运行中半满重填（`half_fill_counter`: `0 → 1 → 2 → 3 → 4 → 5 → 0`）**：
  每当读指针 `pc` 跨过 64-bit 中线（从前半区跨进后半区，或从后半区回绕进前半区），就说明刚刚消费完的那半区（64 bit = 4 个 word）空出来了，立刻触发 `half_fill_counter` 连续读 4 个新 word 覆盖刚刚用完的那半区（`BitStream_buffer.v:68-73`）：
  ```verilog
  if (((pc > 63 && pc_previous <= 63) || (pc < 63 && pc_previous >= 63)) && half_fill_counter == 0)
      half_fill_counter <= 1;
  else if (pc > 63 && half_fill_counter == 0 && buffer_index == 0)   // 冗余兜底 1
      half_fill_counter <= 1;
  else if (pc < 63 && half_fill_counter == 0 && buffer_index == 64)  // 冗余兜底 2
      half_fill_counter <= 1;
  ```
  *(实验 8d 就是把第 1 条改坏，结果下面两条兜底救了场，见 [第 11 章](11-动手实验.md)。)*

### 3. 128 选 1 环形滑窗输出（`BitStream_buffer.v:151-285`）

```verilog
// 注意：这是同步寄存输出（always @(posedge clk)），不是组合逻辑！
always @ (posedge clk)
    if (reset_n == 1'b0)
        BitStream_buffer_output <= 0;
    else if (BitStream_buffer_valid_n == 0)
        case (pc)
            0  : BitStream_buffer_output <= BS_buffer[0:15];
            ...
            112: BitStream_buffer_output <= BS_buffer[112:127];
            113: BitStream_buffer_output <= {BS_buffer[113:127], BS_buffer[0]};      // 环形回绕！
            114: BitStream_buffer_output <= {BS_buffer[114:127], BS_buffer[0:1]};
            ...
            127: BitStream_buffer_output <= {BS_buffer[127],     BS_buffer[0:14]};
        endcase
```

**非常漂亮的设计**：`case (pc)` 完整覆盖了 `0..127` 全部 128 个偏移，尾部 `113..127` 自动拼接回 `BS_buffer[0..14]`！因此 7-bit 无符号指针 `pc` 向前累加超过 127 时**天然模 128 溢出回绕**，完全不需要写任何“减 128”的判断逻辑。

## 3.4 比特层之一：分层前导 1 检测（`heading_one_detector.v`）

不管是 `ue(v)`/`se(v)` 还是 CAVLC 的 `coeff_token`/`level_prefix`/`total_zeros`，核心第一步都是**从最高位 `[15]` 往低位找第一个 `1` 出现在第几位**（即前导 `0` 的个数 `heading_one_pos ∈ 0..15`）。

`src/heading_one_detector.v`（仅 59 行，对应 EURASIP JES 2007 论文）没有用平铺的 16 级优先级链，而是按统计学概率分成 **2 / 4 / 10 三层**：

```verilog
// heading_one_detector.v:25-55
if (heading_one_en == 1'b0) begin          // 低有效使能！不需要检测时置 1 直接输出 0 省电
    // 第 1 级（最高 2 位）：绝大多数短码字（如 ue(0)="1", ue(1/2)="01x"）直接在这里命中！
    if (BitStream_buffer_output[15] || BitStream_buffer_output[14]) begin
        if (BitStream_buffer_output[15]) heading_one_pos <= 4'd0;
        else                             heading_one_pos <= 4'd1;
    end
    // 第 2 级（中间 4 位 [13:10]）：仅当高 2 位全 0 时进入
    else if (BitStream_buffer_output[13] || BitStream_buffer_output[12] ||
             BitStream_buffer_output[11] || BitStream_buffer_output[10]) begin
        if      (BitStream_buffer_output[13]) heading_one_pos <= 4'd2;
        else if (BitStream_buffer_output[12]) heading_one_pos <= 4'd3;
        else if (BitStream_buffer_output[11]) heading_one_pos <= 4'd4;
        else                                  heading_one_pos <= 4'd5;
    end
    // 第 3 级（低 10 位 [9:0]）：极少命中的长码字
    else begin
        if      (BitStream_buffer_output[9]) heading_one_pos <= 4'd6;
        ...
        else                                 heading_one_pos <= 4'd15;
    end
end else
    heading_one_pos <= 0;
```

**为什么要分 2 / 4 / 10 三组？** 因为视频码流里 >70% 的语法元素前导零只有 0 或 1 个。分成三层后，最常见的路径只经过 2 级门延迟，而且后两级在绝大多数拍被屏蔽，兼顾了速度与动态功耗。

## 3.5 比特层之二：指数哥伦布与变长无符号解码

### 1. `exp_golomb_decoding.v`（151 行）

支持 `ue`、`se`、`te` 三种码型，全部复用同一套 `codeNum` 提取逻辑（`exp_golomb_decoding.v:45-84`）：

1. **提取 `codeNum`（8-bit）**：只列了 `heading_one_pos = 0..7` 共 8 档（最大 `codeNum = 254`），直接从 `BitStream_buffer_output` 截取 `M+1` 位再减 1；
2. **计算码长 `exp_golomb_len`**：
   - `ue` / `se`：`(heading_one_pos << 1) + 1`（即 `2M + 1`）；
   - `te`：若 `te_range = num_ref_idx_l0_active_minus1 + 1 == 2`，码长为 `1`，否则同 `ue`；
3. **映射最终值 `exp_golomb_decoding_output`**：
   - `ue`：直接输出 `codeNum`；
   - `se`：`codeNum[0] == 1`（奇数）输出 `(codeNum + 1) >> 1`（正数 `+1, +2, ...`）；`codeNum[0] == 0`（偶数）输出 `~codeNum_se_tmp + 1`（补码 `0, -1, -2, ...`）；
   - `te`：当 `te_range == 2` 时，`(codeNum == 0) ? 8'd0 : 8'd1`（因为 1-bit `te` 中 `1` 代表 `0`、`0` 代表 `1`）。

**由 FSM 状态直接选码型（`exp_golomb_decoding.v:86-149`）**：
- **`ue`**：`first_mb_in_slice`、`slice_type`、`pic_parameter_set_id`、`idr_pic_id`、`disable_deblocking_filter_idc`、**`mb_skip_run`**（`:104`）、`mb_type`、`sub_mb_type`、`intra_chroma_pred_mode`、`coded_block_pattern`、SPS/PPS 的各无符号字段；
- **`se`**：`slice_qp_delta`、`slice_alpha_c0_offset_div2`、`mvd_l0`、`sub_mvd_l0`、`mb_qp_delta`、`pic_init_qp_minus26`、`pic_init_qs_minus26`、`chroma_qp_index_offset`；
- **`te`**：**仅**用于 `ref_idx_l0_s`（`:116`）和 `sub_ref_idx_l0_s`（`:109`）。

> ⚠️ **源码核实发现的真实小 Bug（`exp_golomb_decoding.v:99`）**：
> ```verilog
> `slice_alpha_c0_offset_div2_s : exp_golomb_sel <= se; // 正确
> `slice_beta_offset_div2_s     : exp_golomb_sel <= ue; // ← Bug！H.264 规定 beta offset 也是 se(v)！
> ```
> 在 `akiyo300` 里 `slice_beta_offset_div2 == 0`，而 `ue(0) == se(0) == 0`，所以没有暴露；一旦码流给了一个负的 beta 偏移（如 `-2`），这里会解错！

### 2. `dependent_variable_decoding.v`（55 行）

专门解码 H.264 里**位宽依赖 SPS 字段的无符号定长码 `u(v)`** —— 全芯片只服务两个 Slice Header 字段（`:30-35`）：
- `frame_num_s`：位宽 = `log2_max_frame_num_minus4 + 4`（支持 4~10 bit）；
- `pic_order_cnt_lsb_s`：位宽 = `log2_max_pic_order_cnt_lsb_minus4 + 4`（支持 4~10 bit）。

*(注意：它与 CAVLC 和 `mb_skip_run` 毫无关系！)*

## 3.6 位指针推进：`pc_decoding.v`（203 行）

每拍解完一个语法元素，`pc_decoding.v` 根据当前 FSM 状态选出 `consumed_bits_sel`（定义在 `nova_defines.v:38-44`），给 7-bit 位指针 `pc` 加上消耗的比特数：

```verilog
// pc_decoding.v:190-200
case (consumed_bits_sel)
    `exp_golomb        : pc <= pc_reg + exp_golomb_len;         // 哥伦布变长
    `dependent_variable: pc <= pc_reg + dependent_variable_len; // frame_num / poc_lsb
    `cavlc_consumed    : pc <= pc_reg + cavlc_consumed_bits_len;// CAVLC 各步消耗位数
    `fixed_length      : pc <= pc_reg + FixedLen;               // 定长字段 (1/2/3/8/16 bit)
    `trailing_bits     : pc <= (pc_reg[2:0] == 3'b000) ? pc_reg : {{pc_reg[6:3] + 1}, 3'b0}; // 字节对齐
    `pcm_alignment     : pc <= (pc_reg[2:0] == 3'b000) ? pc_reg : {{pc_reg[6:3] + 1}, 3'b0}; // 字节对齐
    default            : pc <= pc_reg;
endcase
always @ (posedge clk)
    pc_reg <= (reset_n == 0) ? 0 : pc;
```

**逐行看懂 `trailing_bits` 字节对齐**：
H.264 规定每个 NAL 单元末尾必须补 1 个 `1` 比特（`rbsp_trailing_one_bit`，消耗 1 bit）和若干个 `0`（`rbsp_trailing_zero_bits`）直到当前位指针落在 8 的倍数（字节边界）上。
- 如果 `pc_reg[2:0] == 3'b000`，说明已经对齐到 8 的倍数，保持不动；
- 否则把高 4 位 `pc_reg[6:3]` 加 1、低 3 位清零 —— 一步向上取整到下一个字节边界！
- 这里的 `+ 1` 未标位宽，在 `iverilog 12.0` 中会报 `indefinite width`，因此 `sim/scripts/setup_rtl.sh` 自动把它打补丁为 `+ 4'd1`。

## 3.7 语法装配、QP 与 CBP 解码

### 1. `syntax_decoding.v`（621 行）

`syntax_decoding.v` 的统一写法是：**“当前状态命中就旁路当前解码输出，同时在时钟沿锁存；其他状态保持寄存器值”**。例如（`:486-491`）：

```verilog
assign prev_intra4x4_pred_mode_flag = (mb_pred_state == `prev_intra4x4_pred_mode_flag_s) ?
                                      BitStream_buffer_output[15] : prev_intra4x4_pred_mode_flag_reg;
assign rem_intra4x4_pred_mode       = (mb_pred_state == `rem_intra4x4_pred_mode_s) ?
                                      BitStream_buffer_output[15:13] : rem_intra4x4_pred_mode_reg;
assign mvd                          = ((mb_pred_state == `mvd_l0_s) || (sub_mb_pred_state == `sub_mvd_l0_s)) ?
                                      exp_golomb_decoding_output[7:0] : mvd_reg;
```

**三个非常值得注意的源码细节**：
1. **`mvd` 位宽限制**：`mvd` 是 8-bit 有符号数（`-128 .. +127`），因为单位是 **1/4 像素**，对应实际运动搜索范围是 **`-32 .. +31.75` 整像素**（`Inter_mv_decoding.v:11` 注释写了 `SearchRange = 16pix`）。对于 QCIF 够用，但改成大分辨率剧烈运动视频时会溢出。
2. **`mb_type` → `mb_type_general` 翻译（`syntax_decoding.v:319-347`）**：
   - I-slice（`slice_type == 2 || 7`）：`0 → Intra4x4`，`1..24` 按色度 CBP 归入三种 `Intra16x16`；
   - P-slice：`0..4 → Inter16x16 / 16x8 / 8x16 / P_8x8 / P_8x8ref0`，`5 → Intra4x4`，`6..29` 归入 `Intra16x16`；
   - **源码核实发现的潜在 Bug（`syntax_decoding.v:342`）**：P-slice 中 `mb_type ∈ {14..17, 26..29}`（对应 `CBPChroma == 2`）误写成了 `` `MB_Intra16x16_CBPChroma0 ``（应为 `CBPChroma2`）！另外 `I_PCM`（I-slice=25 / P-slice=30）也未被映射，直接掉进 `default`。
3. **解析了但完全未使用的字段**：`pic_width_in_mbs_minus1`、`pic_height_in_map_units_minus1`（`:128-129`，4-bit，只写不读）、`num_slice_groups_minus1`、`weighted_pred_flag`。

### 2. `QP_decoding.v`（69 行）与 `CodedBlockPattern_decoding.v`（156 行）

- **亮度量化参数 `QPy`**（`QP_decoding.v:37-43`）：
  - 在 Slice Header 读到 `slice_qp_delta_s`：`QPy <= 26 + pic_init_qp_minus26 + slice_qp_delta`；
  - 在每个非 skip 宏块读到 `mb_qp_delta_s`：`QPy <= QPy + mb_qp_delta`；
- **色度量化参数 `QPc`**（`QP_decoding.v:45-68`）：先算 `QPi = QPy + chroma_qp_index_offset`，然后查 H.264 Table 8-13 非线性压表（`QPi < 30` 时 `QPc = QPi`，`30..51` 压缩映射到 `29..39`，因为人眼对高 QP 下色度失真比亮度更敏感）。
- **CBP（Coded Block Pattern）**：
  - `CodedBlockPatternLuma[3:0]`：4 个 bit 分别表示 4 个 8×8 亮度子块里有没有非零残差（`0` 表示整块全零，直接跳过 CAVLC！）；
  - `CodedBlockPatternChroma[1:0]`：`0` = 色度无残差，`1` = 只有色度 DC，`2` = 色度 DC + AC 都有；
  - Intra16×16 的 CBP 直接从 `mb_type` 推出；Intra4×4 与 Inter 的 CBP 从码流的 `ue(v)` 查 H.264 Table 9-4（`me(v)` 映射表，在 `CodedBlockPattern_decoding.v:48-137`）。

## 3.8 CAVLC 残差熵解码（2,734 行）

`src/cavlc_decoder.v`（287 行）串起了 **7 个功能子模块 + 3 个上邻寄存器堆 RF**（合计 **2,734 行**，是位流侧最精密的部分）：

| 步骤 | FSM 状态（`cavlc_decoder_state`） | 对应文件（行数） | 做什么 |
|---|---|---|---|
| 0 | `nAnB_decoding_s` → `nC_decoding_s` | `nC_decoding.v`（761）+ 3 个 RF | 从左/上邻块算上下文 `nC` |
| 1 | `NumCoeffTrailingOnes_LUT` | `NumCoeffTrailingOnes_decoding.v`（677） | 查表解 `TotalCoeff`（0..16）与 `TrailingOnes`（0..3） |
| 2 | `TrailingOnesSignFlag` | `level_decoding.v`（206，`:175-182`） | 读 `TrailingOnes` 个符号位，填 `level_0..2` 为 `+1` 或 `-1` |
| 3 | `LevelPrefix` ↔ `LevelSuffix` | `level_decoding.v`（`:62-165`） | 循环解其余非零系数幅度，自适应更新 `suffixLength` |
| 4 | `total_zeros_LUT` | `total_zeros_decoding.v`（400） | 按 `TotalCoeff` 查表解 `total_zeros` |
| 5 | `run_before_LUT` ↔ `RunOfZeros` | `run_decoding.v`（298，`:134-209`） | 循环解每个非零系数前紧跟的零个数 `run_before` |
| 6 | `LevelRunCombination` | `run_decoding.v`（`:210-295`）+ FSM | 把 `level` 和 `run` 拼装成 Zig-Zag 序 `coeffLevel_0..15` |
| 辅助 | 全程 | `end_of_blk_decoding.v`（63）、`cavlc_consumed_bits_decoding.v`（42） | 判块结束 + 统计本拍消耗比特数给 `pc_decoding` |

### 关键模块逐行精解

#### 1. `nC_decoding.v`：如何零周期拿到邻居非零数 + 全零快捷省电

按双 Z 顺序（`i8x8`, `i4x4`）查左邻 `nA` 和上邻 `nB`：
- 同一宏块内部直接从寄存器 `LumaLevel_CurrMb0..3` 取；
- 跨左宏块从 `LumaLevel_mbAddrA` 取；
- 跨上宏块从异步读 RF `LumaLevel_mbAddrB_RF`（深度 11 × 位宽 20 bit = 4 个底边 4×4 块 × 5 bit）零周期读出；
- **全零快捷标志 `Luma_8x8_AllZeroCoeff_mbAddrB`**：若上邻 8×8 块全零，不仅直接给 `nB = 0`，还会把 `LumaLevel_mbAddrB_cs_n` 拉高关掉 RF 时钟，省掉一次 RF 访问！
- 最后算 `nC`（`nC_decoding.v:423-434`）：色度 DC 固定输出 `5'd31`（代表 `-1`）；A、B 都可用时 `(nA + nB + 1) >> 1`；否则直接 `nA + nB`（不可用侧已置 0）。

#### 2. `NumCoeffTrailingOnes_decoding.v` & `total_zeros_decoding.v`：二级分组查表代替大 ROM

以 `coeff_token` 为例（`:41-45`）：先按 `nC` 分 5 档（`0..1`, `2..3`, `4..7`, `>=8`, `-1`），再用 `heading_one_pos`（前导零个数）二次分组。每组内只有几个后缀 bit 的小型组合逻辑，**比放一张大 ROM 面积更小、读功耗更低**。

#### 3. `level_decoding.v`：`suffixLength` 自适应增长（`:62-77`）

H.264 9.2.2.1 规定：大系数之后往往还会遇到大系数，因此解码完每个 `level` 后根据其绝对值 `level_abs` 动态增大后续系数的后缀位宽 `suffixLength`（0 → 1 → 2 → ... → 6）：

```verilog
// level_decoding.v:66-76（与标准逐字对应）
if (suffix_length_initialized == 1'b0)                                 // 第 1 个非 T1 系数
    suffixLength <= (TotalCoeff > 10 && TrailingOnes < 3) ? 4'd1 : 4'd0;
else if (suffixLength == 0 && level_abs > 8'd3)
    suffixLength <= 4'd2;
else if (suffixLength == 0)
    suffixLength <= 4'd1;
else if ((level_abs > (8'd3 << (suffixLength - 1))) && suffixLength < 6)
    suffixLength <= suffixLength + 1;
```

解出无符号 `levelCode` 后，按奇偶还原有符号 9-bit 补码（`:141-165`）：偶数 → `+(levelCode + 2) >> 1`，奇数 → `-(levelCode + 1) >> 1`。

#### 4. `run_decoding.v` 与 `LevelRunCombination`：怎么把倒序的 level/run 摆正？

码流里先解出的是**高频**系数的 `level_0, run_0`，最后解出的是**低频**系数的 `level_{TC-1}, run_{TC-1}`。
在 `LevelRunCombination` 阶段（`BitStream_parser_FSM_gating.v:599-625` + `run_decoding.v:210-295`），`nova` 严格按 H.264 9.2.3 **从低频往高频正向摆放**：
1. 进块前（`nAnB_decoding_s`）把 4-bit `coeffNum` 预置为 `4'b1111`（即 `-1 mod 16`）；
2. 下标计数器 `i_TotalCoeff` 从 **`TotalCoeff - 1` 倒数到 `0`**（也就是先取最低频的那个系数！）；
3. 每拍执行：
   ```verilog
   coeffNum <= coeffNum_reg + run[i_TotalCoeff] + 1; // 从 -1 开始正向跳过 run 个零并前进 1 格
   coeffLevel[coeffNum] <= level[i_TotalCoeff];      // 写入 Zig-Zag 位置！
   ```
4. 全部放完后拉高 `end_of_NonZeroCoeff_CAVLC`，`IQIT.v` 立刻接手反量化与反变换！

## 3.9 运动矢量解码：`Inter_mv_decoding.v`（2,611 行）

这是全工程最长的文件，负责 H.264 8.4.1 的全部 MV 预测规则与跨宏块存储管理。

### 1. 4 个 32-bit 输出寄存器的双 Z 打包格式（`:1211-1428`）

一个宏块最多有 16 个 4×4 子块 MV（每个 8-bit 有符号 1/4 像素）。`mvx_CurrMb0..3` 按 **4 个 8×8 象限（双 Z 序）** 打包：
- `mvx_CurrMb0` = 左上 8×8，`CurrMb1` = 右上 8×8，`CurrMb2` = 左下 8×8，`CurrMb3` = 右下 8×8；
- 每个 32-bit 内部：`[7:0]` = 子块 0（左上），`[15:8]` = 子块 1（右上），`[23:16]` = 子块 2（左下），`[31:24]` = 子块 3（右下）；
- **16×16 / P_Skip 快捷优化**：若整块共用一个 MV，只写 `mvx_CurrMb0[7:0]` 和 `mvy_CurrMb0[7:0]`，同时置 `mv_is16x16 = 1`，省去写其余 15 个字节的功耗。

### 2. 无比较器中值滤波（`:1072-1122`）

H.264 规定普通分区的预测 MV 为左（A）、上（B）、右上（C）三者的中位数：`mvp = median(mvpA, mvpB, mvpC)`。`nova` 用 3 个 9-bit 符号扩展减法器求符号位 `sub[8]`：

```verilog
// Inter_mv_decoding.v:1074-1088（X 分量；Y 分量完全相同）
assign sub_ABx  = {mvpAx[7], mvpAx[7:0]} - {mvpBx[7], mvpBx[7:0]};
assign sub_ACx  = {mvpAx[7], mvpAx[7:0]} - {mvpCx[7], mvpCx[7:0]};
assign sub_BCx  = {mvpBx[7], mvpBx[7:0]} - {mvpCx[7], mvpCx[7:0]};
assign flag_ABx = sub_ABx[8]; // 1 表示 A < B
assign flag_ACx = sub_ACx[8]; // 1 表示 A < C
assign flag_BCx = sub_BCx[8]; // 1 表示 B < C

if      ((flag_ABx && !flag_ACx) || (!flag_ABx && flag_ACx)) mvpx_median <= mvpAx; // A 夹在 B、C 中间
else if ((!flag_ABx && !flag_BCx) || (flag_ABx && flag_BCx)) mvpx_median <= mvpBx; // B 夹在 A、C 中间
else                                                         mvpx_median <= mvpCx; // C 在中间
```

*(注：`sub_ABx/ACx/BCx` 只用到了最高位符号位，差值低位并未复用于后续计算。)*

### 3. 三条 H.264 规范特例（全部精确实现）

1. **单有效邻居特例（`:1090-1096`）**：在 `nova` 中 `refIdxL0_A/B/C` 是 **1-bit 标志**（`1'b0` 表示有效 Inter ref0，`1'b1` 表示越界或 Intra，等价于标准的 `refIdx == -1`）。当且仅有一个邻居有效时（`3'b011 / 3'b101 / 3'b110`），直接采用该邻居的 MV 而不取中值；
2. **P_Skip 零 MV 特例（`:1127-1135`，H.264 8.4.1.1）**：
   ```verilog
   if (mb_num_h == 0 || mb_num_v == 0 ||
       (refIdxL0_A == 0 && mvpAx == 0 && mvpAy == 0) ||
       (refIdxL0_B == 0 && mvpBx == 0 && mvpBy == 0))
       begin mvx <= 0; mvy <= 0; end
   else
       begin mvx <= mvpx; mvy <= mvpy; end
   ```
   只要处于帧最左列、最顶行，或左邻 A、上邻 B 任一个为有效零矢量，P_Skip 直接取 `(0, 0)`！
3. **16×8 / 8×16 定向预测（`:1138-1189`）**：16×8 上半优先取 B、下半优先取 A；8×16 左半优先取 A、右半优先取 C（最右列 `mb_num_h == 10` 时 C 不可用，退回左上角 D）。

### 4. 跨行 MV 缓存：`mbAddrB_RF` 与 `mbAddrC_RF`

- `mvx_mbAddrB_RF` / `mvy_mbAddrB_RF`（深度 11 × 位宽 32 bit）：存上一行 11 个宏块各自的**底边 4 个 4×4 块 MV**（`4 × 8 = 32 bit`）；
- `mvx_mbAddrC_RF` / `mvy_mbAddrC_RF`（深度 10 × 位宽 8 bit）：存上一行宏块列 `1..10` 的**左下角那 1 个 4×4 块的 MV**，写入地址 `mb_num_h - 1`（`0..9`），供下一行左一格宏块（`0..9`）作为**右上邻 `mbAddrC` 的 MV** 读取（列 10 没有右上邻，所以深度只需 10）。

## 3.10 边界强度计算：`bs_decoding.v`（905 行）

在启动去块滤波前，`bs_decoding.v` 用 **4 个时钟周期**（`bs_dec_counter`: `0 → 3 → 2 → 1`）算出当前宏块全部 32 条亮度 4×4 边界的强度 `bs ∈ {0, 1, 2, 3, 4}`（色度去块直接复用对应亮度边界的 `bs`），然后拉高 `end_of_BS_DEC` 启动 `DF_top`。

### 1. `bs_V0..3` 与 `bs_H0..3` 的精确映射（`bs_decoding.v:360-473`）

每一根 12-bit 总线打包了**一整条直线上的 4 段 4 像素边**（每段 3 bit）：

```text
垂直边（从左到右 4 条竖线，每条竖线自上而下 4 段）：
  bs_V0 (x=0,  MB 左边界)：[2:0]第0行 | [5:3]第1行 | [8:6]第2行 | [11:9]第3行
  bs_V1 (x=4,  内部第1竖)：[2:0]第0行 | [5:3]第1行 | [8:6]第2行 | [11:9]第3行
  bs_V2 (x=8,  内部第2竖)：[2:0]第0行 | [5:3]第1行 | [8:6]第2行 | [11:9]第3行
  bs_V3 (x=12, 内部第3竖)：[2:0]第0行 | [5:3]第1行 | [8:6]第2行 | [11:9]第3行

水平边（从上到下 4 条横线，每条横线自左而右 4 段）：
  bs_H0 (y=0,  MB 上边界)：[2:0]第0列 | [5:3]第1列 | [8:6]第2列 | [11:9]第3列
  bs_H1 (y=4,  内部第1横)：[2:0]第0列 | [5:3]第1列 | [8:6]第2列 | [11:9]第3列
  bs_H2 (y=8,  内部第2横)：[2:0]第0列 | [5:3]第1列 | [8:6]第2列 | [11:9]第3列
  bs_H3 (y=12, 内部第3横)：[2:0]第0列 | [5:3]第1列 | [8:6]第2列 | [11:9]第3列
```

*(为什么不滤宏块右边界和下边界？因为它们分别是右邻 MB 的 `V0` 和下邻 MB 的 `H0`，归右/下邻 MB 处理，画面最左列 `mb_num_h == 0` 时 `V0` 全 0、最顶行 `mb_num_v == 0` 时 `H0` 全 0。)*

### 2. 源码里的 `bs` 规则与两个工程细节

- **严格遵循 H.264 8.7.2.1**（`:301-475`）：MB 边界且任一侧 Intra → `4`；内部边且 Intra → `3`；双侧 Inter 且任一侧有非零残差系数 → `2`；否则若 `|Δmvx| >= 4 || |Δmvy| >= 4`（由 16 个 `mv_diff_GE4` 子模块并行算）→ `1`；其余 → `0`。
- **`mb_type_general_DF` 锁存时机（`:62-67`）**：在 `blk4x4_rec_counter == 5'd22 && end_of_one_blk4x4_sum` 时把当前 MB 的 `mb_type_general` 锁进 `mb_type_general_DF`。原因是第 23 块结束后 `end_of_MB_DEC` 立刻拉高，位流解析器会马上进入**下一个 MB** 并改写 `mb_type_general`，而此时 `bs_decoding` 和 `DF` 处理的还是**刚刚重建完的这个 MB**，提前 1 个块锁存正好错开！
- **`MB_inter_size` 的注释（`:78-79`）**：对 Intra MB 赋默认值 `` `I8x8 ``（注释 `//Although it should be Intra,but we have no other choice`），实际上 Intra 分支根本不读 `MB_inter_size`，只是给组合 `if-else` 补一个安全默认值。

## 3.11 位流侧的 18 路门控时钟（`bitstream_gclk_gen.v`）

`src/bitstream_gclk_gen.v`（332 行）一共生成 **18 路门控时钟**（9 个状态机时钟 + 8 个 RF 写时钟 + 1 个 `gclk_bs_dec`），外加 1 个非时钟控制信号 `end_of_one_frame`。

全部采用标准的**低电平透明锁存器 + 与门**（ICG 行为模型）：

```verilog
// bitstream_gclk_gen.v:143-145（注意是电平敏感 always @(clk or ena)，不是边沿触发！）
always @ (clk or parser_ena)
    if (!clk) l_parser_ena <= parser_ena;
assign gclk_parser = l_parser_ena & clk;
```

只有在 `clk` 低电平期间才允许使能信号穿过锁存器，`clk` 高电平期间锁存器关闭，`l_parser_ena` 保持绝对稳定，从而彻底消除门控时钟毛刺（详见 [第 8 章](08-存储组织与时钟门控.md)）。

## 3.12 本章小结：位流侧的三个核心省电思想

1. **状态机直接当控制器**：`exp_golomb_sel` 和 `consumed_bits_sel` 直接由 Gray 码 FSM 状态译出，减少冗余控制逻辑与状态切换翻转。
2. **分层检测 + 二级分组查表**：`heading_one_detector` 按 2/4/10 分层，CAVLC 码表按 `nC` 与 `heading_one_pos` 分组，用轻量组合逻辑替代大 ROM。
3. **细粒度门控 + 全零短路**：8 个 RF 各自独占一路门控写时钟；`*_8x8_AllZeroCoeff` 在全零 8×8 块时直接关闭上邻 RF 读取。
