# 第 3 章 位流解析链路

这一章讲 `BitStream_controller`（744 行 + 14 个子模块）如何把外部 SRAM 里的
字节流，变成重建侧能用的 `coeffLevel` / `mv` / `mb_type`。

## 3.1 数据通路的四个层次

```
Beha_BitStream_ram (131072 × 16 bit, 外部行为模型)
        │  16 bit/word，读延迟 2 个时钟
        ▼  BitStream_ram_addr[16:0] / BitStream_ram_ren
┌───────────────────────────────────────────────────┐
│ BitStream_buffer.v   128 bit 桶形缓冲              │
│   把连续 8 个 16 bit word 拼成 128 bit             │
│   按 pc[6:0] 滑窗输出 16 bit                       │
└───────────────────────────────────────────────────┘
        │  BitStream_buffer_output[15:0]
        │  BitStream_buffer_valid_n（低有效）
        ▼
┌───────────────────────────────────────────────────┐
│ 各类语法解码器                                      │
│   heading_one_detector  → leading-one 位置        │
│   exp_golomb_decoding   → ue / se / te            │
│   dependent_variable_decoding → mb_skip_run 等     │
│   syntax_decoding       → 语法元素装配（621 行）    │
│   cavlc_decoder         → 残差系数（7 个子模块）    │
│   Inter_mv_decoding     → 运动矢量（2611 行）       │
│   bs_decoding           → 边界强度（905 行）        │
└───────────────────────────────────────────────────┘
        │
        ▼  语法元素 → reconstruction
```

**四个层次的分界很清晰**：
1. **存储层**：外部 SRAM（不在 IP 内）
2. **缓冲层**：128 bit 桶形缓冲，解决"位流是比特连续的、SRAM 是 16 bit 对齐的"这个矛盾
3. **比特层**：从 16 bit 窗口里检测 leading-one、解指数哥伦布码
4. **语法层**：把解出来的数值组成 H.264 语法元素

## 3.2 存储层：为什么码流空间是 256 KB

`nova_defines.v`：

```verilog
`define Beha_Bitstream_ram_size 131071
```

`BitStream_ram_addr` 是 17 位（0..131071），所以：

**131072 word × 16 bit = 2 Mbit = 256 KB**

随 IP 附带的 akiyo 码流（300 帧）是 262144 字节 = 256 KB，**刚好用满**。
这不是巧合——**这个 SRAM 大小是按 akiyo 300 帧定的**。

但实际上 akiyo 码流只用到 word 0..15517（我们的 testbench 扫描出来的，
见第 9 章）。剩下 87% 的 ROM 是空的。**真正的设计只需要约 32 KB 码流 RAM**。

> 这个发现很有用：如果你想把这个 IP 移植到 FPGA，**码流 RAM 可以砍到 1/8**，
> 只要保证能放下最大的 I 帧即可（akiyo 的 I 帧约 19005 bit ≈ 2.4 KB）。

### 地址不回绕

`BitStream_buffer.v:116`：

```verilog
BitStream_ram_addr <= (BitStream_ram_addr != 17'd131071) ?
                      (BitStream_ram_addr + 1) : BitStream_ram_addr;
```

**到 131071 就停住，不回绕**。这是防止码流读完后回绕到开头重新解码
（那样会无限循环）。这个特性被我们用来做 testbench 的"码流耗尽"检测（第 9 章）。

## 3.3 缓冲层：128 bit 桶形缓冲

这是整个位流解析的**性能关键**。H.264 的比特流是比特连续的，而 SRAM 是
16 bit 对齐的。每次要解一个语法元素都要"从当前比特位置取 N 个比特"，
如果每次取都去读 SRAM，吞吐会极低。

### 结构

```verilog
// BitStream_buffer.v:40
reg [0:127] BS_buffer;
```

**注意声明是 `[0:127]` 而不是 `[127:0]`**。这意味着 `BS_buffer[0]` 是
**最高位**，`BS_buffer[127]` 是**最低位**——即"先收到的比特在左边"，
符合码流的自然阅读顺序。

### 填充

```verilog
// BitStream_buffer.v 中填充逻辑（case buffer_index[6:4]）
always @(posedge clk)
    if (reset_n == 0) ...
    else if (BitStream_ram_ren == 1'b0) begin
        case (buffer_index[6:4])
            3'd0: for (i=0; i<16; i=i+1) BS_buffer[i]    <= BitStream_buffer_input[15-i];
            3'd1: for (i=0; i<16; i=i+1) BS_buffer[16+i] <= BitStream_buffer_input[15-i];
            ...
            3'd7: for (i=0; i<16; i=i+1) BS_buffer[112+i]<= BitStream_buffer_input[15-i];
        endcase
    end
```

**`BS_buffer[i] <= BitStream_buffer_input[15-i]` 是比特序翻转**。
SRAM 里存的 16 bit word，第 15 位是"最先到达的比特"，所以要放到缓冲区的高位。
`buffer_index` 每 16 递增，`[6:4]` 选择 8 个 16 bit 槽。

### 上电预充与半满重填

```verilog
reg [3:0] reset_counter;      // 0..10，上电预充
reg [2:0] half_fill_counter;  // 0..5，半满重填
```

- **上电**：`reset_counter` 从 0 数到 10，连续读 11 个 word 填满缓冲区
  （实际填 8 个槽就满了，多读的 3 个是历史余量）
- **正常**：`half_fill_counter` 在 pc 跨过 64 bit 边界时触发重填

```verilog
// 半满判据
assign half_full_trigger =
    ((pc > 63 && pc_previous <= 63) || (pc < 63 && pc_previous >= 63))
    && (half_fill_counter == 0);
```

**为什么用 `pc` 跨 64 边沿作为判据，而不是"剩余比特数小于阈值"？**
因为 `pc` 是比特指针，跨 64 说明已经消耗了一半（128 bit 的一半）。
用"穿越边界"检测比"比较剩余量"省一个加法器和一个比较器，而且
**天然只在每个 128 bit 周期触发一次**，不会重复触发。

### 输出：任意比特偏移的 16 bit 滑窗

```verilog
// BitStream_buffer.v 输出选择
always @(pc or BS_buffer)
    case (pc)
        7'd0:   BitStream_buffer_output <= BS_buffer[0:15];
        7'd1:   BitStream_buffer_output <= BS_buffer[1:16];
        ...
        7'd112: BitStream_buffer_output <= BS_buffer[112:127];
        default:BitStream_buffer_output <= 16'h0000;
    endcase
```

**这是一个 113 项的 case，综合出来是 113 选 1 的 16 位多路选择器**。
面积不小（约 113×16 = 1808 个 2:1 MUX），但**零延迟、零控制逻辑**——
只要给出 pc，组合逻辑立刻给出 16 bit 窗口。

为什么是这个规模？因为一个语法元素最长可能跨 16 bit 窗口很多次，
但单次解码最多只需要窗口内的 16 bit。pc 从 0 到 112 覆盖了 128−16 个位置，
再往后就需要重填了。

### 有效信号

```verilog
output BitStream_buffer_valid_n;   // 低有效
```

`valid_n = 0` 表示缓冲区有足够数据可以解一个语法元素。
状态机 `BitStream_parser_FSM_gating.v:154-159`：

```verilog
`rst_parser:       if (BitStream_buffer_valid_n == 0) parser_state <= `start_code_prefix;
`start_code_prefix: ...
```

## 3.4 比特层之一：leading-one 检测

H.264 的指数哥伦布码和 CAVLC 的 level_prefix 都是"若干个 0 后跟一个 1"的形式，
所以**检测前导 1 的位置**是最基础的操作。

### 朴素做法 vs nova 的做法

**朴素做法**：16 级优先编码器

```
pos = 0;
for (i = 0; i < 16; i = i + 1)
    if (in[i]) pos = i;
```
综合出来是 16 级级联的 OR 链，**关键路径长、翻转多**。

**nova 的做法**：分层 2/4/10 分组（`heading_one_detector.v`）

```
第一步：只看最高 2 位 [15] 和 [14]
        如果 [15] 是 1 → pos = 0，结束
        如果 [14] 是 1 → pos = 1，结束
第二步：看 [13:10] 这 4 位
        如果其中有 1 → 在这 4 位里定位
第三步：看 [9:0] 这 10 位
        如果其中有 1 → 在这 10 位里定位
```

对应论文 *Priority-based Heading One Detector in H.264/AVC Decoding*（EURASIP JES 2007）。

**为什么这样省电？** 因为**统计上大部分语法元素的 leading-one 在前几位**。
CAVLC 的 level_prefix 和 total_zeros 的码字，绝大多数情况下前 2 位就有 1。
所以：

- 第一步（2 位比较）**每次都要做**，但只有 2 个门
- 第二步（4 位）只在 `[15:14] == 2'b00` 时才需要做
- 第三步（10 位）只在 `[15:10] == 6'b000000` 时才需要做

后两步的比较器输入被 **operand isolation**（操作数隔离）门控掉了，
输入不变就不翻转 → **动态功耗大幅下降**。

### 输出与门控

```verilog
output [3:0] heading_one_pos;   // 0..15
input  heading_one_en;
```

`heading_one_en == 1` 时强制输出 0（用于"不需要检测"的场景，比如
`level_prefix == 15` 之后的扩展位）。这也是省电：不需要时直接不检测。

## 3.5 比特层之二：指数哥伦布码

`exp_golomb_decoding.v` 支持三种码，由 `exp_golomb_sel` 选择：

| `exp_golomb_sel` | 码型 | 用途 |
|---|---|---|
| `ue` | 无符号指数哥伦布 | `mb_type`、`ref_idx` 的差值、`mb_qp_delta` 等 |
| `se` | 有符号指数哥伦布 | `mvd`、`slice_qp_delta`、`pic_init_qp_minus26` 等 |
| `te` | 截断指数哥伦布 | `mb_skip_run`（当范围是 2 时退化为 1 bit） |

### 长度计算

```verilog
// exp_golomb_decoding.v:65-67
ue, se: exp_golomb_len <= (heading_one_pos << 1) + 1;
te    : exp_golomb_len <= (te_range == 2) ? 1 : ((heading_one_pos << 1) + 1);
```

**指数哥伦布码的总长度 = 2×前导零数 + 1**。
`heading_one_pos` 正是前导零的个数（因为 leading-one 检测是从最高位开始找 1，
位置就是前导零数）。所以 `len = (pos << 1) + 1` —— **一个移位加一个加法，无乘法**。

### 数值解码

```verilog
// exp_golomb_decoding.v:47-57（ue/se 的 codeNum）
case (heading_one_pos)
    4'd0:  codeNum <= 0;
    4'd1:  codeNum <= 1 + BitStream_buffer_output[14];
    4'd2:  codeNum <= 3 + BitStream_buffer_output[13:12];
    ...
    4'd15: codeNum <= ... ;
endcase
```

即 `codeNum = (2^pos − 1) + suffix`。用 case 直接列出 16 种情况，
**避免了一个桶形移位器 + 一个加法器**。

### 有符号映射

```verilog
// exp_golomb_decoding.v:71-84
assign codeNum_se_tmp = codeNum >> 1;
case (exp_golomb_sel)
    se: case (codeNum[0])
            1'b0: output <= codeNum_se_tmp;          // 偶数 → 正
            1'b1: output <= -codeNum_se_tmp - 1;     // 奇数 → 负
        endcase
    ...
endcase
```

这是 H.264 的 se 映射：`0→0, 1→1, 2→−1, 3→2, 4→−2, ...`。

### te 码的特例

```verilog
assign te_range = num_ref_idx_l0_active_minus1 + 1;
te: exp_golomb_len <= (te_range == 2) ? 1 : ((heading_one_pos << 1) + 1);
```

`mb_skip_run` 用 te 码，范围是 `[0, num_ref_idx_l0_active_minus1]`。
当 `te_range == 2`（即 `num_ref_idx_l0_active_minus1 == 1`，常见于 P 帧）
时退化成 1 bit 定长码。**这是 H.264 标准的规定，nova 用一行三元表达式覆盖**。

### 输出选择器（关键工程细节）

`exp_golomb_decoding.v:91-146` 是一大段 case，根据当前 FSM 状态决定
`exp_golomb_sel` 是 ue / se / te：

```verilog
case (slice_header_state)
    slice_type_s:                    exp_golomb_sel <= ue;
    pic_parameter_set_id_slice_header_s: exp_golomb_sel <= ue;
    frame_num_s:                     exp_golomb_sel <= ue;
    ...
endcase
case (slice_data_state)
    mb_skip_run_s:  exp_golomb_sel <= te;
    mb_type_s:      exp_golomb_sel <= ue;
    ...
    case (sub_mb_pred_state) ...
    case (mb_pred_state) ...
endcase
case (seq_parameter_set_state) ...
case (pic_parameter_set_state) ...
```

**这就是"FSM 状态直接当选通信号"**——不需要额外的译码逻辑，
状态机停在哪个状态，就自动选对应的码型。**这是 Gray 码状态机之外，
另一个"用状态机当控制器省逻辑"的例子**。

## 3.6 位指针推进：pc_decoding.v

`pc`（7 bit）是缓冲区内的比特位置。每解完一个语法元素，`pc` 要前进
`consumed_bits` 位。

### 不同的前进方式

```verilog
// nova_defines.v 的 consumed_bits_sel 编码
`define rst_consumed_bits_sel      3'b000
`define exp_golomb_consumed_bits_sel 3'b001
`define fixed_length_consumed_bits_sel 3'b011
`define dependent_variable_consumed_bits_sel 3'b010
`define cavlc_consumed_bits_sel    3'b110
`define trailing_bits_consumed_bits_sel 3'b111
`define pcm_alignment_consumed_bits_sel 3'b101
```

| 方式 | 前进量 | 用途 |
|---|---|---|
| `exp_golomb` | `exp_golomb_len` | 指数哥伦布码 |
| `fixed_length` | 固定位数（参数化） | `frame_num`（`log2_max_frame_num_minus4+4`）、`pic_order_cnt_lsb` 等 |
| `dependent_variable` | 由 `dependent_variable_decoding` 算 | `mb_skip_run` 依赖的值 |
| `cavlc_consumed` | `cavlc_consumed_bits` | CAVLC 码块的等效长度 |
| `trailing_bits` | **对齐到字节边界** | `rbsp_trailing_bits` |
| `pcm_alignment` | 同上 | I_PCM 的对齐 |

### trailing_bits 的对齐技巧

```verilog
// pc_decoding.v:186-200
trailing_bits:
    pc <= (pc_reg[2:0] == 3'b000) ? pc_reg : {{pc_reg[6:3] + 4'd1}, 3'b0};
pcm_alignment:
    pc <= (pc_reg[2:0] == 3'b000) ? pc_reg : {{pc_reg[6:3] + 4'd1}, 3'b0};
```

**逻辑**：如果 `pc` 已经是 8 的倍数（低 3 位为 0），不动；
否则把低 3 位清零、高位加 1 —— 即"向上取整到下一个 8 的倍数"。

**这段就是 iverilog 报错的地方**（`{{pc_reg[6:3] + 1}, 3'b0}` 里 `1` 无位宽）。
修成 `4'd1` 后功能完全一致。

### 为什么 pc 只有 7 位

128 bit 缓冲区 → 位置 0..127 → 7 bit。当 `pc` 超过 112 时（16 bit 窗口
会越过 128 边界），就需要重填缓冲区并把 `pc` 减去 128。

`BitStream_buffer.v` 里有 `pc_previous` 和重填时的 `pc` 修正逻辑，
保证"消耗了 128 bit 后指针回到缓冲区开头"。

## 3.7 语法层：syntax_decoding.v

这个模块（621 行）本身不做解码，而是**把各路解码器的输出按 FSM 状态装配成
有意义的语法元素**。

### 输出举例

```verilog
// syntax_decoding.v:489-491
assign prev_intra4x4_pred_mode_flag =
    (mb_pred_state == `prev_intra4x4_pred_mode_flag_s) ?
    BitStream_buffer_output[15] : prev_intra4x4_pred_mode_flag_reg;

assign rem_intra4x4_pred_mode =
    (mb_pred_state == `rem_intra4x4_pred_mode_s) ?
    BitStream_buffer_output[15:13] : rem_intra4x4_pred_mode_reg;

assign mvd =
    ((mb_pred_state == `mvd_l0_s) || (sub_mb_pred_state == `sub_mvd_l0_s)) ?
    exp_golomb_decoding_output[7:0] : mvd_reg;
```

**统一模式**："如果当前状态是这个字段，就取原始输出；否则保持寄存值"。
这样**一个字段只占一个寄存器 + 一个 2:1 MUX**，非常省。

### 为什么 `prev_intra4x4_pred_mode_flag` 直接取 `[15]`

因为它是 1 bit 语法元素，永远在窗口最高位（H.264 是 MSB-first）。
不需要 `pc` 参与选通——**比特层已经保证窗口对准了当前位置**。

### `rem_intra4x4_pred_mode` 取 `[15:13]`

3 bit 定长。同理。

### `mvd` 取 `exp_golomb_decoding_output[7:0]`

`mvd` 是 se 码解出来的值，8 bit 有符号（H.264 规定 mvd 范围 −2048..2047，
但 Baseline QCIF 实践中 8 bit 够用）。**这是一个隐含的精度假设**——
如果遇到大运动矢量（>127 像素），会溢出。对 QCIF 影响不大，
但改分辨率时要注意。

## 3.8 CAVLC 熵解码

CAVLC（Context-Adaptive Variable Length Coding）是 H.264 Baseline 的熵编码。
这是整个 IP 最复杂的部分，`cavlc_decoder.v` + 7 个子模块共 **1741 行**。

### CAVLC 的 5 个步骤

| 步骤 | 语法元素 | nova 模块 | 行数 |
|---|---|---|---|
| 1 | `coeff_token`（TotalCoeff + TrailingOnes） | `NumCoeffTrailingOnes_decoding.v` | 677 |
| 2 | `trailing_ones_sign_flag` | （在 cavlc_decoder 内） | — |
| 3 | `level`（level_prefix + level_suffix） | `level_decoding.v` | 206 |
| 4 | `total_zeros` | `total_zeros_decoding.v` | 400 |
| 5 | `run_before` | `run_decoding.v` | 298 |

外加：
- `nC_decoding.v`（761 行）：推导上下文 `nC`（步骤 1 需要）
- `cavlc_consumed_bits_decoding.v`（42 行）：统计总消耗位数
- `end_of_blk_decoding.v`（63 行）：判断块是否结束

### 步骤 1：coeff_token 的查表结构

H.264 的 `coeff_token` 表有 4 张（按 `nC` 分段）：
`0 ≤ nC < 2`、`2 ≤ nC < 4`、`4 ≤ nC < 8`、`nC ≥ 8`（再加 `nC == −1` 的特例）。

nova 的实现（`NumCoeffTrailingOnes_decoding.v:41-45`）：

```verilog
assign nC_0to2 = (cavlc_decoder_state == `NumCoeffTrailingOnes_LUT && (nC == 0 || nC == 1));
assign nC_2to4 = (... && (nC == 2 || nC == 3));
assign nC_4to8 = (... && (nC == 4 || nC == 5 || nC == 6 || nC == 7));
assign nC_n1   = (... && (nC == 5'd31));         // 31 代表 nC == -1（chroma DC）
assign nC_GE8  = (... && !nC_0to2 && !nC_2to4 && !nC_4to8 && !nC_n1);
```

**用 `!=` 的组合推导 `nC_GE8`，而不是 `nC >= 8`** ——省一个比较器。

### 二级查表

每张表内部还按 `heading_one_pos` 再分：

```verilog
// nC_0to2 的 4 个子表
assign nC_0to2_t0 = (nC_0to2 && (pos == 0 || pos == 1 || pos == 2));
assign nC_0to2_t1 = (nC_0to2 && (pos == 3 || pos == 4));
assign nC_0to2_t2 = (nC_0to2 && (pos == 5 || pos == 6 || pos == 7 || pos == 8));
assign nC_0to2_t3 = (nC_0to2 && (pos == 9 || pos == 10));
```

**为什么按 `heading_one_pos` 分组？** 因为 CAVLC 的 coeff_token 码字是
"变长前缀 + 定长后缀"结构，**前导零的个数决定了码字的布局**。
同一组前导零的码字，其 TotalCoeff/TrailingOnes 的编码规律相同，
所以可以共用一个小的译码逻辑。

这就是**"按码字长度分组查表"**的思想——不用一个巨大的 ROM，
而是用"分组判断 + 组内小逻辑"。**面积换成了组合逻辑，但省了 ROM**。

具体译码（例）：

```verilog
if (nC_0to2_t0)
    TrailingOnes <= heading_one_pos[1:0];      // 前导零数直接就是 TrailingOnes
else if (nC_0to2_t1) begin
    if (heading_one_pos == 4'd3 && !BitStream_buffer_output[11])
        TrailingOnes <= (BitStream_buffer_output[10]) ? 2'd0 : 2'd1;
    else if (heading_one_pos == 4'd4 && BitStream_buffer_output[10:9] == 2'b01)
        TrailingOnes <= 2'd2;
    else
        TrailingOnes <= 2'd3;
end
```

### 步骤 3：level 解码与 suffixLength 自适应

`level_decoding.v` 的核心是 `suffixLength` 的自适应（H.264 9.2.2.1）：

```verilog
// level_decoding.v:63-77
if (cavlc_decoder_state == `LevelPrefix)
    if (suffix_length_initialized == 1'b0)      // 第一个 level
        suffixLength <= (TotalCoeff > 10 && TrailingOnes < 3) ? 4'd1 : 4'd0;
    else if (suffixLength == 0 && level_abs > 8'd3)
        suffixLength <= 4'd2;
    else if (suffixLength == 0)
        suffixLength <= 4'd1;
    else if ((level_abs > (8'd3 << (suffixLength - 1))) && suffixLength < 6)
        suffixLength <= suffixLength + 1;
```

**这是 H.264 标准原文的直接翻译**，包括 `3 << (suffixLength − 1)` 这个
判断式。注意 `suffixLength < 6` 的上限——标准规定 `suffixLength` 最大 6。

`8'd3 << (suffixLength - 1)` 是**变量移位**，综合出来是一个桶形移位器。
这是这个模块里少数几个"无法避免"的较贵逻辑。

### 步骤 4：total_zeros 的"分层查表"

`total_zeros_decoding.v`（400 行）处理 `total_zeros` 语法元素。
这个表有 15 张（按 `TotalCoeff` 从 1 到 15），每张表的码字长度不同。

nova 的做法同 `coeff_token`：**先按 `TotalCoeff` 分组，再按 `heading_one_pos` 分**。

### 步骤 5：run_before 与 zig-zag 反变换

`run_decoding.v`（298 行）解出 `run_before`，然后**把 level 和 run 组合成
zig-zag 序的 `coeffLevel_0..15`**：

```verilog
// run_decoding.v 核心（概念）
coeffNum = TotalCoeff - 1;              // 从最后一个系数开始
zerosLeft = total_zeros;
for (i = 0; i < TotalCoeff; i = i + 1) begin
    coeffLevel[coeffNum] = level[i];    // 放到 zig-zag 位置
    if (i < TotalCoeff - 1) begin
        coeffNum = coeffNum - run[i] - 1;
        zerosLeft = zerosLeft - run[i];
    end
end
```

**注意输出是 zig-zag 序而不是 raster 序**。`IQIT.v` 的头部注释明确说：
> "coeffLevel: zig-zag order, OneD/TwoD/DC/rescale/rounding_output: raster-scan order"

即 **zig-zag → raster 的转换在 IQIT 内部完成**（通过选择合适的输入系数）。

## 3.9 nC 上下文的推导

H.264 的 `nC` 是 CAVLC 的上下文，由左邻（A）和上邻（B）块的非零系数个数决定：

```
nC = (nA + nB + 1) >> 1     // 当 A、B 都可用
nC = nA                     // 只有 A 可用
nC = nB                     // 只有 B 可用
nC = 0                      // 都不可用
nC = -1                     // chroma DC（特殊）
```

### 可用性判断

```verilog
// nC_decoding.v:264-280
case (residual_state)
    `Intra16x16DCLevel_s:
        nA_availability <= (mb_num_h == 0) ? 1'b0 : 1'b1;
    `Intra16x16ACLevel_s, `LumaLevel_s:
        if ((i8x8 == 0 || i8x8 == 2) && (i4x4 == 0 || i4x4 == 2))
            nA_availability <= (mb_num_h == 0) ? 1'b0 : 1'b1;   // MB 左边缘
        else
            nA_availability <= 1'b1;                            // MB 内部，总是可用
    `ChromaACLevel_Cb_s, `ChromaACLevel_Cr_s:
        nA_availability <= (mb_num_h == 0 && i4x4_CbCr[0] == 0) ? 1'b0 : 1'b1;
    default:
        nA_availability <= 1'b0;
endcase
```

**关键洞察**：只有在宏块的**左边缘**（`mb_num_h == 0` 或者当前 4×4 块在
MB 的最左列）才需要考虑"左邻不存在"。MB 内部的其他块，左邻永远存在。

### nA/nB 的取值

```verilog
// nC_decoding.v:305-330
case (residual_state)
    `Intra16x16DCLevel_s:
        nA <= (Luma_8x8_AllZeroCoeff_mbAddrA[0] == 0) ? 0 : LumaLevel_mbAddrA[4:0];
    `Intra16x16ACLevel_s, `LumaLevel_s:
        case (i8x8)
            0: case (i4x4)
                   0: nA <= (Luma_8x8_AllZeroCoeff_mbAddrA[0] == 0) ? 0 : LumaLevel_mbAddrA[4:0];
                   1: nA <= LumaLevel_CurrMb0[4:0];       // MB 内部：直接取当前 MB 的块
                   2: nA <= (Luma_8x8_AllZeroCoeff_mbAddrA[0] == 0) ? 0 : LumaLevel_mbAddrA[9:5];
                   3: nA <= LumaLevel_CurrMb0[14:10];
               endcase
            ...
        endcase
endcase
```

**`Luma_8x8_AllZeroCoeff` 是一个"整块全零"的快捷标志**。
如果整个 8×8 块的所有系数都是 0，就不必去读 `LumaLevel_mbAddrA`，
直接给 `nA = 0`。这省了一次 RF 读（约 1 mW 量级的动态功耗）。

### 存储：为什么用 RF 而不是 RAM

`LumaLevel_mbAddrB_RF` 是 11 × 20 bit 的**寄存器堆**（async read, sync write）。
深度 11 = QCIF 的 11 列，每个宏块存 4 个 4×4 块的 TotalCoeff（每个 5 bit）。

**为什么不用 RAM？** 因为 async read 的 RF 可以**零周期读取**，
而 SRAM 读要 1 个周期。CAVLC 解码是串行的，每多一个周期就多一份延迟。
代价是 11×20 = 220 个触发器 ≈ 1500 门，换回的是流水线的紧凑。

## 3.10 运动矢量解码（Inter_mv_decoding.v，2611 行）

这是**最长的文件**，因为 MV 预测要考虑的情况极多。

### MV 预测的中值滤波（无比较器）

H.264 规定：`mvp = median(mvA, mvB, mvC)`。

**朴素做法**：3 个比较器 + 6 个 MUX。
**nova 做法**：减法 + 符号位。

```verilog
// Inter_mv_decoding.v:1070-1130（简化）
sub_ABx = mvpAx - mvpBx;      // 9 bit 带符号
sub_ACx = mvpAx - mvpCx;
sub_BCx = mvpBx - mvpCx;

flag_ABx = sub_ABx[8];        // 符号位 = "A < B"
flag_ACx = sub_ACx[8];
flag_BCx = sub_BCx[8];

// 中值逻辑：
// 若 A、B 分居 C 两侧 → C 是中值 → 取 C
// 若 A、B 在 C 同侧 → 取 A、B 中离 C 近的那个
```

具体的真值表实现（按 `flag_ABx`/`flag_ACx`/`flag_BCx` 的组合），
**用 3 个减法器的借位/符号位替代 3 个比较器**。减法器和比较器面积相近，
但减法器的输出（差值）可以复用给后续计算，而比较器只有 1 bit 输出。

### refIdx 特例

```verilog
// Inter_mv_decoding.v 附近
case ({refIdxL0_A, refIdxL0_B, refIdxL0_C})
    3'b011: mvp <= mvpA;      // 只有 A 用 ref0
    3'b101: mvp <= mvpB;      // 只有 B 用 ref0
    3'b110: mvp <= mvpC;      // 只有 C 用 ref0
    default: mvp <= median;   // 否则取中值
endcase
```

这是 H.264 8.4.1.3 的规定：**只有一个邻块用了 ref0 时，直接采用它的 MV**。
用 case 实现，非常直接。

### skip MB 的特例

H.264 8.4.1.1 规定 P_Skip 的 MV 预测有额外规则：

```verilog
if (mb_num_h == 0 || mb_num_v == 0 || (A 的 refIdx 和 mv 全为 0))
    mvp = 0;                          // 边界或 A 是 skip → MV 为 0
else
    mvp = median(...);                // 正常情况
```

**QCIF 的 11×9 网格意味着第一行和第一列的所有 MB 都走 `mvp = 0` 分支**——
这解释了为什么 akiyo 序列的 skip MB 处理如此快（91/99 个 MB 是 skip，
且大部分在第一行/列，直接 MV=0，连中值都不用算）。

## 3.11 边界强度计算（bs_decoding.v，905 行）

去块滤波需要知道每条边界的"强度" `bs`（0..4）。这个计算（H.264 8.7.2.1）
依赖：
- 宏块类型（intra 边界 bs=4 或 3，inter 边界看残差和 MV）
- 相邻块的残差是否为零
- MV 差值是否 ≥ 4（整像素）
- 参考帧是否不同

### 打包格式

```verilog
// bs_decoding.v
output [11:0] bs_V0, bs_V1, bs_V2, bs_V3;   // 4 个垂直方向的 12 bit
output [11:0] bs_H0, bs_H1, bs_H2, bs_H3;   // 4 个水平方向的 12 bit
```

每个 12 bit 打包 4 个 3 bit 的边界强度？不对——**12 bit 打包 4 组？**
实际上：

- 一个宏块有 **16 个 4×4 块**，每个块的左边界和上边界都要滤波
- 但很多边界是**宏块内部**的（4×4 块之间），用 `bs` 表示
- 一个 MB 有 4 个 8×8 子块，每个 8×8 有 4 个 4×4

`bs_V0` 的 12 bit = `{[8:6], [5:3], [2:0]}` → **3 个 3 bit 值**。
所以 4 个 `bs_Vx` 共 12 个 3 bit 值 = **12 条垂直边界**？
但一个 MB 有 16 个 4×4 块，应该有 16 条垂直边界…

**实际是**：只有 4×4 变换块的边界需要滤波，而 H.264 的 4×4 变换块
在一个 MB 内有 4×4 网格 = **4 条内部垂直边界 + 4 条内部水平边界**，
加上 MB 边界的左、上、右、下。nova 的组织方式是：

| 信号 | 覆盖的边界 |
|---|---|
| `bs_V0[2:0]` | 第 0 行 4×4 块的左边界（MB 左边界） |
| `bs_V0[5:3]` | 第 0 行内部第 1 条垂直边界 |
| `bs_V0[8:6]` | 第 0 行内部第 2 条垂直边界 |
| `bs_V0[11:9]` | 第 0 行内部第 3 条垂直边界 |
| `bs_V1[*]` | 第 1 行 4×4 块的 4 条垂直边界 |
| `bs_V2[*]` | 第 2 行 |
| `bs_V3[*]` | 第 3 行 |

**即 4 行 × 4 条垂直边界 = 16 条垂直边界，正好覆盖 luma 的所有垂直边**。
水平同理（`bs_H0..3` 各覆盖一列 4 个水平边界）。

**每行/列只有 4 条边而不是 5 条**，因为宏块右边界由右邻宏块的左边界处理，
下边界由下邻宏块的上边界处理——**避免重复处理**。

### QCIF 的边界特例

```verilog
// bs_decoding.v
// mb_num_h == 10 时，右边界是画面边界，不需要滤波
// mb_num_v == 8  时，下边界是画面边界，不需要滤波
```

这也是硬编码 QCIF 假设的一处。

### DF 的 MB 类型锁定时机

```verilog
// bs_decoding.v
mb_type_general_DF <= mb_type_general;
// 锁定条件：!disable_DF && end_of_one_blk4x4_sum && blk4x4_rec_counter == 5'd22
```

**等到第 22 个 4×4 块（即第 23 个，0-based）重建完成时才锁存 mb_type**。
为什么这么晚？因为 `mb_type` 在残差解码过程中可能被修改（比如
`CodedBlockPatternChroma` 的更新），要等所有系数解完才稳定。

### MB_inter_size 的强制值

```verilog
// bs_decoding.v
if (mb_type_general_DF[3] == 1)             // intra MB
    MB_inter_size <= `I8x8;                 // 强制设为 I8x8
    // 代码注释原文："Although it should be Intra,but we have no other choice"
```

**这是一个 hack**。`MB_inter_size` 本来只对 inter MB 有意义，
但 DF 需要一个"分区尺寸"来做边界判断。对 intra MB，任何值都不对，
作者就选了个 `I8x8`（最细的划分，等价于"每个 4×4 块都要检查边界"），
保证不会漏掉边界。

**注释里的"we have no other choice"是这份代码里为数不多的"坦白"**——
说明作者知道这是个妥协。读代码时遇到这种注释要特别留意，
它往往指向一个真实的限制。

## 3.12 位流侧的时钟门控

`bitstream_gclk_gen.v`（332 行）生成 17 个门控时钟，覆盖：

```
gclk_parser, gclk_nal, gclk_slice, gclk_sps, gclk_pps,
gclk_slice_header, gclk_slice_data, gclk_residual, gclk_cavlc,
gclk_Intra4x4PredMode_mbAddrB_RF, gclk_mvx_mbAddrB_RF, gclk_mvy_mbAddrB_RF,
gclk_mvx_mbAddrC_RF, gclk_mvy_mbAddrC_RF,
gclk_LumaLevel_mbAddrB_RF, gclk_ChromaLevel_Cb_mbAddrB_RF, gclk_ChromaLevel_Cr_mbAddrB_RF,
gclk_bs_dec
```

统一模式（**latch-based clock gating**）：

```verilog
always @ (!clk)                       // 负沿锁存
    l_parser_ena <= parser_ena;
assign gclk_parser = l_parser_ena & clk;
```

**为什么在负沿锁存？** 因为门控时钟必须在 `clk` 低电平期间稳定，
否则会产生毛刺（glitch）导致触发器误触发。负沿锁存正好在 `clk` 低电平
中间采样使能信号，保证 `gclk` 上升沿干净。

这是标准的**锁存器型时钟门控单元（ICG, Integrated Clock Gating）**的行为模型。
实际 ASIC 里会用一个专门的 ICG cell（比 latch+AND 更省面积、更可靠），
但行为完全一样。

详见第 8 章。

## 3.13 本章小结：位流侧的三个设计思想

1. **"状态机即控制器"**：`exp_golomb_sel` 由 FSM 状态直接选出，
   `consumed_bits_sel` 同理。省掉了独立的译码逻辑，也省了状态编码到控制信号的转换层。

2. **"分组查表"代替"大 ROM"**：CAVLC 的 `coeff_token` / `total_zeros` 表
   都按 `nC` 和 `heading_one_pos` 二级分组，每组用小的组合逻辑实现。
   ROM 面积换成了逻辑面积，但**ROM 的读功耗通常比组合逻辑高**（尤其大 ROM），
   而且组合逻辑可以被 operand isolation 门控。

3. **"能跳过就跳过"**：`Luma_8x8_AllZeroCoeff` 让整块全零时不必读 RF；
   `CodedBlockPatternLuma == 0` 的块直接跳过 CAVLC 解析（`hybrid_pipeline_ctrl.v`
   的核心逻辑，见第 8 章）。
