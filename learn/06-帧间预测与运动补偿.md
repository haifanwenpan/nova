# 第 6 章 帧间预测与运动补偿

帧间预测（inter prediction）是 nova 里**代码量最大**的部分：6 个文件合计约
**9600 行**，占全项目 37%。

| 文件 | 行数 | 职责 |
|---|---|---|
| `Inter_mv_decoding.v` | 2611 | MV 预测（中值滤波）+ 层次化 MV 存储 |
| `Inter_pred_sliding_window.v` | 2226 | 6×9 / 1×9 / 2×2 滑动窗口重组 |
| `Inter_pred_reg_ctrl.v` | 1698 | 参考像素打包（含边界 padding） |
| `Inter_pred_pipeline.v` | 781 | 地址生成 + 三个计数器 |
| `Inter_pred_top.v` | 702 | 顶层，装配下面这些 |
| `Inter_pred_LPE.v` | 590 | 亮度 6-tap 插值器（9H + 4V + 4 双线性） |
| `Inter_pred_CPE.v` | 166 | 色度双线性插值器 |

**为什么这么多行？** 因为 H.264 的运动补偿极其复杂：

- 7 种块划分（16×16、16×8、8×16、8×8、8×4、4×8、4×4）
- 16 种分数像素位置（整数 + 15 个分数位置）
- 每个分数位置需要不同的滤波器组合
- 参考像素在 12×12 的窗口里要"重新排列"成 6×9 的滑动窗口

**这些复杂性全是规范和硬件并行性的必然结果**，不是作者写得啰嗦。

## 6.1 整体数据流

```
             mvx/mvy_CurrMb0..3（来自 BitStream_controller）
                        │
                        ▼
            ┌───────────────────────┐
            │ Inter_pred_pipeline   │  算 xInt/yInt 地址、pos_FracL、
            │                       │  xFracC/yFracC、三个计数器
            └───────────┬───────────┘
                        │ ref_frame_RAM_rd / ref_frame_RAM_rd_addr
                        ▼
              ┌──────────────────┐
              │ ext_frame_RAM    │  参考帧（上一帧的重建结果）
              └────────┬─────────┘
                       │ ref_frame_RAM_dout[31:0]（4 像素/word）
                       ▼
            ┌───────────────────────┐
            │ Inter_pred_reg_ctrl   │  打包成 13×13 的 Inter_ref_XX_YY
            │                       │  （含边界 padding）
            └───────────┬───────────┘
                        │ Inter_ref_00_00 .. Inter_ref_12_12
                        ▼
            ┌───────────────────────┐
            │ Inter_pred_sliding_   │  按 pos_FracL 抽成
            │ window               │  H_window 6×9 / V_window 1×9 /
            │                       │  C_window 3×3 / bi_window 4
            └───────────┬───────────┘
                        │
              ┌─────────┴──────────┐
              ▼                    ▼
    ┌──────────────────┐  ┌──────────────┐
    │ Inter_pred_LPE   │  │Inter_pred_CPE│
    │ 9H + 4V + 4 双线性│  │ 4 个 CPE_base│
    └─────────┬────────┘  └──────┬───────┘
              └─────────┬─────────┘
                        ▼
              Inter_pred_out0..3（4 像素/拍）
```

**注意 `Inter_ref_XX_YY` 是 13×13 = 169 个 8 bit 寄存器**。
这是整个设计里最大的寄存器阵列（169 × 8 = 1352 bit）。
**它不是浪费**——它是"用寄存器换访存带宽"的核心（见 6.3）。

## 6.2 运动矢量（MV）的预测与存储

### MV 预测：无比较器的中值滤波

H.264 规定 MVP（MV Predictor）是 **A、B、C 三个邻居 MV 的中值**：

```
MVP = median(MV_A, MV_B, MV_C)
```

朴素实现需要 3 个比较器（或 6 次比较）。`Inter_mv_decoding.v:1070-1130`
用**符号位判大小**实现：

```verilog
assign sub_ABx = mvpAx - mvpBx;   // 9 bit 带符号
assign sub_ACx = mvpAx - mvpCx;
assign sub_BCx = mvpBx - mvpCx;
assign flag_ABx = sub_ABx[8];     // 符号位：1 表示 A < B
assign flag_ACx = sub_ACx[8];
assign flag_BCx = sub_BCx[8];

// 若 A、B 分居 C 两侧（即 (A<C && B>C) || (A>C && B<C)），中值就是 C
// 若 A、B 同侧，中值在 A、B 之间，取靠近 C 的那个
```

**用 3 个减法器的符号位代替比较器**。减法器和比较器在 CMOS 里面积相近，
但**减法器的结果是"完整差值"，后面还能复用**（比如特例判断）。

### refIdx 的三种特例

```verilog
case ({refIdxL0_A, refIdxL0_B, refIdxL0_C})
    3'b011: mvp = mvpAx;
    3'b101: mvp = mvpBx;
    3'b110: mvp = mvpCx;
    default: mvp = median(mvpAx, mvpBx, mvpCx);
endcase
```

**这三个特例是 H.264 规范 8.4.1.3 的明确规定**：如果三个邻居中有两个
的参考帧索引与第三个不同，就直接取那个"孤立"的。

### MV 存储：4 个 32 bit 寄存器装 16 个 MV

```verilog
output [31:0] mvx_CurrMb0, mvx_CurrMb1, mvx_CurrMb2, mvx_CurrMb3;
```

**每个 MB 的 16 个 4×4 块 MV 被打包进 4 个 32 bit 寄存器**，每字节一个 MV：

```
mvx_CurrMb0 = { blk3_mv, blk2_mv, blk1_mv, blk0_mv }   // blk 0..3（第一行）
mvx_CurrMb1 = { blk7_mv, blk6_mv, blk5_mv, blk4_mv }   // blk 4..7
mvx_CurrMb2 = { blk11_mv, ..., blk8_mv }
mvx_CurrMb3 = { blk15_mv, ..., blk12_mv }
```

**MV 只需要 8 bit**（−128..127，单位 1/4 像素）——因为 QCIF 只有 176 像素宽，
MV 范围远小于 8 bit 能表示的范围。

### 层次化选择：`mv_is16x16` 和 `mv_below8x8`

```verilog
// Inter_pred_pipeline.v
if (mv_is16x16)
    mv = mvx_CurrMb0[7:0];           // 16×16：整个 MB 用同一个 MV
else if (!mv_below8x8_curr)
    mv = mvx_CurrMb{blk4x4_rec_counter[3:2]}[...];  // 8×8 及以上：每个 8×8 一个 MV
else
    mv = mvx_CurrMb{blk4x4_rec_counter[3:2]}[...];  // 8×8 以下：每个 4×4 一个 MV
```

**三个层次的存储粒度**：
- 16×16：1 个 MV
- 16×8 / 8×16 / 8×8：每个 8×8 子块 1 个 MV（`mv_below8x8` 标志位表示"是否有 8×8 以下的划分"）
- 8×4 / 4×8 / 4×4：每个 4×4 子块 1 个 MV

**`mv_below8x8` 是 4 bit**（每个 8×8 子块 1 bit），表示该 8×8 是否被进一步细分。
这样硬件可以**只看 1 bit 就知道要不要拆到 4×4 粒度**，不用重新解析 `sub_mb_type`。

## 6.3 滑动窗口：13×13 → 6×9 的重新排列

### 为什么需要重排

参考帧存储是 **4 像素/word**（32 bit），一次读只能读到 4 个水平相邻的像素。
但 6-tap 滤波需要 **6 个水平相邻像素**——跨 2 个 word。

`Inter_pred_reg_ctrl.v` 的做法：**把 13×13 范围内的所有像素一次性读进寄存器数组**，
然后 `Inter_pred_sliding_window.v` 按 `pos_FracL` 从中**"抽"**出需要的
6×9 窗口。

### 13×13 的来历

6-tap 滤波在水平和垂直方向各需要 6 个像素。一个 4×4 块要算：
- 水平方向：4 个输出像素各需 6 个输入 → 需要 `4 + 5 = 9` 个水平像素
- 垂直方向：4 个输出像素各需 6 个输入 → 需要 `4 + 5 = 9` 个垂直像素

但**分数像素位置会引入额外的偏移**：

| 位置 | 水平偏移 | 垂直偏移 | 需要范围 |
|---|---|---|---|
| `pos_Int` | 0 | 0 | 6×6（4×4 块）|
| `pos_b`（水平半像素）| +2 | 0 | 8×6 |
| `pos_h`（垂直半像素）| 0 | +2 | 6×8 |
| `pos_j`（水平+垂直半像素）| +2 | +2 | 9×9 |
| `pos_a`（水平 1/4）| +1 | 0 | 7×6 |
| 最坏情况（双向 6-tap）| +4 | +4 |  **13×13** |

**13×13 是最坏情况**：当 `xInt_org_unclip[1:0] = 2'b11`（最靠右）且需要
双向 6-tap 时，需要从 +4 读到 +12，共 13 个像素。

### 三种窗口

```verilog
// Inter_pred_sliding_window.v 头注释
// 1)Luma:horizontal window 6x9,vertical window 1x9
// 2)Chroma:window 2x2
```

| 窗口 | 尺寸 | 用途 |
|---|---|---|
| `Inter_H_window_0_0 .. 5_8` | **6 × 9** | 水平 6-tap 的输入（9 个位置各 6 个像素） |
| `Inter_V_window_0 .. 8` | **1 × 9** | 垂直 6-tap 的输入（9 个位置，每个只需要 1 个中间值） |
| `Inter_C_window_0_0 .. 2_2` | **3 × 3** | 色度双线性的输入 |
| `Inter_bi_window_0 .. 3` | **4** | 双线性（quarter-pel）的整数像素部分 |
| `Inter_pix_copy_0 .. 3` | **4** | 整数位置的直接复制 |

**关键观察**：
- **水平窗口是 6×9**：因为 9 个垂直位置（H0..H8）各需要 6 个水平像素做水平滤波
- **垂直窗口是 1×9**：因为垂直滤波只需要 9 个"水平滤波后的中间值"（每行 1 个）
- **两个窗口的尺寸不对称**——这是 6-tap 可分离滤波的自然结果

### H_window 的抽取：case (pos_FracL) 大表

```verilog
// Inter_pred_sliding_window.v:370 起
case (pos_FracL)
    `pos_Int: begin
        Inter_H_window_0_0 <= Inter_ref_00_00;  // 从 ref 的 (0,0) 开始
        Inter_H_window_1_0 <= Inter_ref_01_00;
        ...
    end
    `pos_a: begin
        Inter_H_window_0_0 <= Inter_ref_01_00;  // 从 (1,0) 开始，右移 1
        ...
    end
    `pos_b: begin
        Inter_H_window_0_0 <= Inter_ref_02_00;  // 右移 2
        ...
    end
    ...
endcase
```

**每个 pos_FracL 对应一个不同的起始偏移**。这就是"滑动窗口"的名字来源：
窗口在 13×13 的寄存器阵列上"滑动"，起点由 `pos_FracL` 决定。

**为什么用 case 而不是加法器算偏移？** 因为 16 种位置各有不同的**非线性**
抽取模式（不只是平移，还有"哪些像素参与"的区别）。用 case 直接列出
是最清晰的——**综合后就是一个大的 MUX 网络，面积换清晰度**。

### 窗口里的 6-tap 对齐

`Inter_H_window_{i}_{j}` 的下标含义：
- `i` = 0..5（窗口内的第 i 个像素，对应 6-tap 的 A..F）
- `j` = 0..8（当前 4×4 块的第 j 行，加上上下各 2 行的余量）

所以 `Inter_H_window_0_2` 是"第 2 行、第 0 个像素"。

## 6.4 亮度插值：16 种位置与无乘法 6-tap

### H.264 的分数像素位置

H.264 的运动矢量单位是 **1/4 像素**，所以一个像素周围有 16 个可预测位置：

```
      0    1    2    3
  0   Int   a    b    c
  1   d     e    f    g
  2   h     i    j    k
  3   n     p    q    r
```

`nova_defines.v` 的宏编码（**注意位域是 {xFracL, yFracL}**）：

| 宏 | 值 | xFrac | yFrac | 含义 |
|---|---|---|---|---|
| `pos_Int` | `4'b0000` | 0 | 0 | 整数 |
| `pos_a` | `4'b0100` | 1 | 0 | 水平 1/4 |
| `pos_b` | `4'b1000` | 2 | 0 | 水平半像素 |
| `pos_c` | `4'b1100` | 3 | 0 | 水平 3/4 |
| `pos_d` | `4'b0001` | 0 | 1 | 垂直 1/4 |
| `pos_h` | `4'b0010` | 0 | 2 | 垂直半像素 |
| `pos_n` | `4'b0011` | 0 | 3 | 垂直 3/4 |
| `pos_e` | `4'b0101` | 1 | 1 | 对角 1/4,1/4 |
| `pos_f` | `4'b1001` | 2 | 1 | 半,1/4 |
| `pos_g` | `4'b1101` | 3 | 1 | 3/4,1/4 |
| `pos_i` | `4'b0110` | 1 | 2 | 1/4,半 |
| `pos_j` | `4'b1010` | 2 | 2 | 半,半（**最复杂**）|
| `pos_k` | `4'b1110` | 3 | 2 | 3/4,半 |
| `pos_p` | `4'b0111` | 1 | 3 | 1/4,3/4 |
| `pos_q` | `4'b1011` | 2 | 3 | 半,3/4 |
| `pos_r` | `4'b1111` | 3 | 3 | 3/4,3/4 |

**位域是 {xFracL[1:0], yFracL[1:0]}**——所以 `pos_FracL[3:2]` 是 x 小数部分，
`pos_FracL[1:0]` 是 y 小数部分。代码里的 `Is_V_jfqik` 命名就是判断
"是不是 j/f/q/i/k 这五个需要两级 6-tap 的位置"。

### 6-tap 滤波器：`(A − 5B + 20C + 20D − 5E + F + 16) >> 5`

H.264 的亮度插值滤波器系数是 `(1, −5, 20, 20, −5, 1)/32`。

**朴素实现需要 6 个乘法器**。nova 的 `filterH_6tap` 用**纯移位加法**：

```verilog
// Inter_pred_LPE.v filterH_6tap
assign sum_AF = A + F;                    //   A + F
assign sum_BE = B + E;                    //   B + E
assign sum_CD = C + D;                    //   C + D
assign sum_4CD = {sum_CD, 2'b0};          //   4(C + D)
assign sum_1 = {1'b0, sum_4CD} + {3'b111, ~sum_BE} + 1;
assign sum_2 = {4'b0, sum_AF} + {sum_1[11], sum_1};
assign sum_3 = {sum_1, 2'b0};             //   sum_1 << 2
assign raw_out = {{2{sum_2[12]}}, sum_2} + {sum_3[13], sum_3};
```

**推导**：

```
目标 = (A+F) − 5(B+E) + 20(C+D)

令 P = A+F, Q = B+E, R = C+D
则   目标 = P − 5Q + 20R

sum_4CD = 4R
sum_1   = 4R − Q                    (第一级)
sum_2   = P + (4R − Q) = P − Q + 4R  (第二级)
sum_3   = (4R − Q) × 4 = 16R − 4Q
raw_out = sum_2 + sum_3 = P − Q + 4R + 16R − 4Q
        = P − 5Q + 20R              ✓
```

**三级加法器树，零乘法器**。关键技巧：

1. **`−Q` 用 `~Q + 1`**（二进制补码的取负），`{3'b111, ~sum_BE} + 1` 就是 `−sum_BE`
2. **`×20` 拆成 `×4 + ×16`**，用两次左移（`{sum_CD,2'b0}` 是 ×4，`{sum_1,2'b0}` 是 ×4 再 ×4 = ×16）
3. **符号扩展用 `{sum_2[12]}`**（补符号位）

### 舍入与饱和

```verilog
assign sum_round = (H_need_round) ? (raw_out + 16) : 0;
assign round_tmp = (H_need_round) ? sum_round[14:5] : 0;
assign round_out = (round_tmp[9]) ? 8'd0 : ((round_tmp[8]) ? 8'd255 : round_tmp[7:0]);
```

- `+16` 然后 `>>5` = `(raw + 16) >> 5`，标准的 rounding
- **饱和用 `round_tmp[9]` 和 `round_tmp[8]` 两次判断**（同 `sum.v` 的技巧）
- `H_need_round` 为 0 时输出 0（节省翻转功耗——**未被使用的滤波结果直接清零**）

### `H_need_round` 的精细控制

```verilog
assign H_need_round = (blk4x4_inter_calculate_counter != 0 && pos_FracL != `pos_Int
    && pos_FracL != `pos_i && pos_FracL != `pos_j && pos_FracL != `pos_k
    && pos_FracL != `pos_d && pos_FracL != `pos_n);
```

**哪些位置不需要 H_need_round？**
- `pos_Int`：整数位置，不用滤波
- `pos_i/j/k`：这两个是 **j 类位置**，水平滤波的 raw_out 要留给垂直滤波用（不能舍入！）
- `pos_d/n`：垂直位置，水平方向不需要滤波

**这是 H.264 的关键细节**：`pos_j`（半像素、半像素）需要
**先水平 6-tap（不舍入，保留精度）→ 再垂直 6-tap**。
如果中途舍入，精度就丢了。

**9 个水平滤波器里，只有 2 个设 `H_need_round = 1'b0`（H_6tapfilter0 和 H_6tapfilter7/8），
其余 6 个由 `H_need_round` 控制**——这是"按需计算"的细粒度功耗控制。

### 垂直滤波器：处理 15 bit 的中间值

```verilog
// filterV_6tap
assign sum_AF = {A[14],A} + {F[14],F};    // 16 bit
assign sum_BE = {B[14],B} + {E[14],E};
assign sum_CD = {C[14],C} + {D[14],D};
assign sum_4CD = {sum_CD,2'b0};            // 18 bit
assign sum_1 = sum_4CD + {~sum_BE[15],~sum_BE[15],~sum_BE} + 1;
assign sum_2 = {{2{sum_AF[15]}},sum_AF} + sum_1;   // 18 bit
assign sum_3 = {sum_1,2'b0};               // 20 bit
assign raw_out = {{2{sum_2[17]}},sum_2} + sum_3;   // 20 bit
```

**结构完全一样，只是位宽从 8→15 位输入变成 20 位输出**。

### `Is_jfqik`：两种舍入模式

```verilog
assign sum_round = (Is_jfqik) ? (raw_out + 512) : (raw_out + 16);
assign round_tmp = (Is_jfqik) ? sum_round[19:10] : sum_round[14:5];
```

- **`Is_jfqik == 0`**：输入是 8 bit 整数像素 → `+16 >> 5`（标准）
- **`Is_jfqik == 1`**：输入是 15 bit 的**水平滤波中间值** → `+512 >> 10`

**`>>10 = >>5 >>5`**——因为做了两级 6-tap，总的缩放是 2^5 × 2^5 = 2^10。
**`+512 = 2^9` 是两级的 rounding 合并**。

### 9H + 4V + 4 双线性 = 17 个滤波器实例

`Inter_pred_LPE.v` 里实例化了：
- **9 个 `filterH_6tap`**（`H_6tapfilter0..8`）
- **4 个 `filterV_6tap`**（`V_6tapfilter0..3`）
- **4 个 `bilinear`**（`bilinear0..3`）

**为什么是 9 个水平？** 因为要一次算出 9 行的水平滤波结果（供垂直滤波用）。
**为什么是 4 个垂直？** 因为一个 4×4 块一次算 4 行（4 个 PE 并行）。
**为什么是 4 个双线性？** 同上，4 个像素并行。

这就是 spec 里说的"亮度插值器 = 9 个水平 6-tap + 4 个垂直 6-tap + 4 个双线性"。

### 三种情况的计算周期

```verilog
// Inter_pred_pipeline.v "2.Calculate counter"
case (pos_FracL)
    `pos_j,`pos_f,`pos_q: blk4x4_inter_calculate_counter <= 4'd5;  // 需要 5 周期
    `pos_i,`pos_k       : blk4x4_inter_calculate_counter <= 4'd8;  // 需要 8 周期
    default             : blk4x4_inter_calculate_counter <= 4'd4;  // 4 周期
endcase
```

- **`pos_j/f/q`（双向半像素）**：5 周期（先水平 4 行，再垂直）
- **`pos_i/k`（水平 1/4 或 3/4 + 垂直半像素）**：8 周期（要多算几行水平中间值）
- **其他位置**：4 周期

**`pos_i/k` 为什么比 `pos_j` 慢？** 因为 `pos_i` 的 x 小数部分是 1/4，
水平插值需要**两级**（先 6-tap 得到半像素 b，再对 b 和整数像素做双线性）。
**这也解释了为什么 `Is_V_jfqik` 里 `pos_i/k` 的条件是 counter 7/5/3/1（隔一个）**。

## 6.5 色度插值：8 个条件移位加法器

色度用**双线性**（H.264 规定色度的 MV 精度是 1/8 像素，但插值是双线性）。

### 公式

```
pred = ((8−xFracC)(8−yFracC)·a + xFracC(8−yFracC)·b
      + (8−xFracC)yFracC·c + xFracC·yFracC·d + 32) >> 6
```

**朴素实现需要 4 个乘法器**（每个乘一个加权系数）。

### nova 的做法：CPE_base

```verilog
// Inter_pred_CPE.v CPE_base
assign sum_x3 = (x[3] == 1'b1) ? {Int_pel, 3'b0} : 0;   // 8 × pel
assign sum_x2 = (x[2] == 1'b1) ? {Int_pel, 2'b0} : 0;   // 4 × pel
assign sum_x1 = (x[1] == 1'b1) ? {Int_pel, 1'b0} : 0;   // 2 × pel
assign sum_x0 = (x[0] == 1'b1) ? Int_pel : 0;           // 1 × pel
assign sum_x = (sum_x3 + sum_x2) + (sum_x1 + sum_x0);   // x × pel

assign sum_y3 = (y[3] == 1'b1) ? {sum_x, 3'b0} : 0;      // × 8
assign sum_y2 = (y[2] == 1'b1) ? {sum_x, 2'b0} : 0;      // × 4
assign sum_y1 = (y[1] == 1'b1) ? {sum_x, 1'b0} : 0;      // × 2
assign sum_y0 = (y[0] == 1'b1) ? sum_x : 0;             // × 1
assign out = (sum_y3 + sum_y2) + (sum_y1 + sum_y0);     // y × (x × pel)
```

**用 4 个"条件移位"代替 1 个乘法器**：

- 因为 `xFracC` 只有 0..7（3 bit），而 `8 − xFracC` 也是 0..8（4 bit）
- **二进制展开**：`x = x[3]·8 + x[2]·4 + x[1]·2 + x[0]·1`
- 所以 `x · pel = (x[3] ? 8·pel : 0) + (x[2] ? 4·pel : 0) + ...`

**乘 8/4/2 是左移**，乘 1 是直通，乘 0 是清零。
**4 个"条件左移"（每个 = 1 个与门阵列 + 移位）+ 3 个加法器 = 1 个乘法器**。

同理 y 方向再做一次。**总共 8 个条件移位加法器**（x 方向 4 个 + y 方向 4 个）。

```verilog
// 顶层 CPE
assign out_tmp = (b0 + b1) + (b2 + b3) + 32;
assign out = out_tmp[13:6];
```

4 个 `CPE_base` 分别处理 a/b/c/d 四个角，加权系数由 `(xFracC, yFracC)` 及其
补码 `(xFracC_n, yFracC_n)` 组合决定：

```verilog
assign xFracC_n = 4'b1000 - xFracC;   // 8 − xFracC
assign yFracC_n = 4'b1000 - yFracC;
```

- `CPE0` 用 `(xFracC_n, yFracC_n)` × a
- `CPE1` 用 `(xFracC, yFracC_n)` × b
- `CPE2` 用 `(xFracC_n, yFracC)` × c
- `CPE3` 用 `(xFracC, yFracC)` × d

### 色度的快速路径：`Is_InterChromaCopy`

```verilog
assign Is_InterChromaCopy = (IsInterChroma && xFracC == 0 && yFracC == 0) ? 1'b1 : 1'b0;
```

**如果色度 MV 是整数位置，直接复制，跳过双线性**：

```verilog
// Inter_pred_pipeline.v
else if (trigger_blk2x2_inter_pred && IsInterChroma && mv_below8x8_curr == 1'b1)
    begin
        if (xFracC == 0 && yFracC == 0)
            blk4x4_inter_preload_counter <= ...;   // 快速路径
        else
            blk4x4_inter_preload_counter <= ...;   // 慢速路径
    end
```

注释原文：

```
//If chroma is predicted by direct copy,calculate cycle would reduce
//from 16 cycles to 4 cycles
```

**从 16 周期降到 4 周期**，省 75%。这个优化在低运动序列里命中率很高
（akiyo 里大量 skip MB 的 MV 接近 0）。

## 6.6 参考帧地址生成

### 地址公式

```verilog
// Inter_pred_pipeline.v:700
assign ref_frame_RAM_rd_addr = (offset_constant + {8'b0, xInt_addr[7:2]}) + {1'b0, offset_yInt_addr};
```

**三部分**：

| 部分 | 含义 |
|---|---|
| `offset_constant` | chroma 偏移（0 / 6336 / 7920） |
| `{8'b0, xInt_addr[7:2]}` | x 坐标 ÷ 4（因为 4 像素/word） |
| `offset_yInt_addr` | y 坐标 × 行跨距 |

```verilog
assign yInt_addr_x11 = {yInt_addr, 3'b0} + {2'b0, yInt_addr, 1'b0} + {3'b0, yInt_addr};
// = 8y + 2y + y = 11y
assign offset_yInt_addr = (IsInterLuma) ? {yInt_addr_x11, 2'b0}   // 44y（luma）
                                        : {1'b0, yInt_addr_x11, 1'b0};  // 22y（chroma）
```

**`11y` 用 3 个移位加法器实现**（`8y + 2y + y`），然后
**luma 再 ×4 = 44y、chroma ×2 = 22y**。

**行跨距 44 word（luma）/ 22 word（chroma）** 与帧存布局一致（第 8 章详述）。

### 边界裁剪

```verilog
always @ (xInt_addr_unclip or IsInterLuma or IsInterChroma)
    if (xInt_addr_unclip[8] == 1'b1)  // 负坐标
        xInt_addr <= 0;
    else if (IsInterLuma)
        xInt_addr <= (xInt_addr_unclip[7:0] > (`pic_width - 4)) ? 8'd172 : xInt_addr_unclip[7:0];
    else
        xInt_addr <= (xInt_addr_unclip[7:0] > (`half_pic_width - 4)) ? 8'd84 : xInt_addr_unclip[7:0];
```

**注意裁剪到 172 而不是 176**——因为一次读 4 个像素，地址最大 172 才能
读到 172..175 这最后 4 个。

### 越界 padding（`Inter_pred_reg_ctrl`）

```verilog
always @ (xInt_addr_unclip_reg or ref_frame_RAM_dout or IsInterLuma or IsInterChroma)
    if (xInt_addr_unclip_reg[8] == 1'b1)   // 超出左边界
        RefFrameOutPadding <= {ref_frame_RAM_dout[7:0], ref_frame_RAM_dout[7:0],
                               ref_frame_RAM_dout[7:0], ref_frame_RAM_dout[7:0]};   // 复制最左像素
    else if ((IsInterLuma && xInt_addr_unclip_reg[7:2] > 6'b101011) ||   // 43 = 172/4
             (IsInterChroma && xInt_addr_unclip_reg[7:2] > 6'b010101))   // 21 = 84/4
        RefFrameOutPadding <= {ref_frame_RAM_dout[31:24], ...};           // 复制最右像素
    else
        RefFrameOutPadding <= ref_frame_RAM_dout;
```

**H.264 的边界扩展规则**：超出画面的参考像素用**边缘像素复制**（replicate padding）。

**为什么 `xInt_addr_unclip_reg` 要打一拍？**
代码注释说得很清楚：

```
//In original version where ext_frame_RAM is read async,no need to latch xInt_addr_unclip
//since it is used here in the same cycle as it is generated in Inter_pred_pipeline module.
//However,when ext_frame_RAM is changed to sync read,xInt_addr_unclip will be used one cyle later.
```

**这是一个版本演进的痕迹**：早期 ext_frame_RAM 是异步读（同周期出数），
后来改成同步读（下一周期出数），所以地址要打一拍对齐。
**这也是 `cycles_per_frame` 从 50000 一路加到 57300 的原因之一**（第 2 章）。

## 6.7 预加载计数器：位宽决定周期数

```verilog
output [5:0] blk4x4_inter_preload_counter;   // 6 bit，最大 63
```

**预加载计数器是 6 bit**，因为它要数到 53。这个值来自**最坏情况**：

```verilog
// 8×8 及以上的划分，pos_f/q/i/k/j（最复杂）
`pos_f,`pos_q,`pos_i,`pos_k,`pos_j: blk4x4_inter_preload_counter <= 6'd53;
```

**53 = 13 行 × 4 次读 + 1**：13×13 窗口需要读 13 行，每行 4 个 word
（13 像素 ÷ 4 ≈ 4），共 52 次，从 53 倒数到 1。

**不同位置的预加载周期**：

| 情况 | 计数器初值 | 周期数 |
|---|---|---|
| 8×8+ / 整数 / x 对齐 | 17 | 17 |
| 8×8+ / 整数 / x 不对齐 | 25 | 25 |
| 8×8+ / 双向半像素 | **53** | **53** |
| 8×8+ / 垂直半像素 / 对齐 | 27 | 27 |
| 8×8+ / 水平半像素 | 33 | 33 |
| 8×8+ / 对角 | 49 | 49 |
| 8×8 以下 / 整数 / 对齐 | 5 | 5 |
| 8×8 以下 / 双向半像素 | **28** | **28** |
| 色度 / 整数 | 5 或 9 | 5–9 |
| 色度 / 分数 | 11 | 11 |
| 色度 2×2 / 整数 | 3 或 5 | 3–5 |
| 色度 2×2 / 分数 | 4 或 7 | 4–7 |

**关键洞察：8×8 以上的划分只需在第一个 4×4 块预加载一次**：

```verilog
// 注释原文
//  If block partition equals 8x8 or above,preload only at first 4x4 block of each 8x8block
//  If block partition is 8x4,4x8 or 4x4,  preload at each 4x4 block
```

**因为 8×8 的参考窗口覆盖了整个 8×8 块**，后续 3 个 4×4 块可以直接复用寄存器里的数据。
**这省下了 3/4 的预加载周期**。

## 6.8 三个计数器与流水节拍

| 计数器 | 位宽 | 作用 |
|---|---|---|
| `blk4x4_inter_preload_counter` | 6 | 预加载参考像素（从 53 倒数到 1） |
| `blk4x4_inter_calculate_counter` | 4 | 计算输出（从 4/5/8 倒数到 1） |
| `Inter_chroma2x2_counter` | 2 | 色度 2×2 子块的四个位置（11→10→01→00） |

### calculate_counter 的启动条件

```verilog
else if (IsInterLuma && ((!mv_below8x8_curr && (
                (blk4x4_rec_counter[1:0] == 2'b00 && blk4x4_inter_preload_counter == 1) ||
                (blk4x4_rec_counter[1:0] != 2'b00 && trigger_blk4x4_inter_pred))) ||
            (mv_below8x8_curr && blk4x4_inter_preload_counter == 1)))
```

**两种情况启动计算**：
1. **8×8 及以上**：只在 `blk4x4_rec_counter[1:0] == 0`（每个 8×8 的第一个 4×4）
   等 `preload_counter == 1`；后续 3 个 4×4 直接由 `trigger_blk4x4_inter_pred` 触发
2. **8×8 以下**：每个 4×4 都等 `preload_counter == 1`

**这就是流水线的节拍来源**：预加载（最长 53 周期）和计算（最长 8 周期）
**串行**，但**不同 4×4 块之间可以重叠**（下一块的预加载可以和当前块的计算并行）。

### `end_of_one_blk4x4_inter`

```verilog
assign end_of_one_blk4x4_inter = (blk4x4_inter_calculate_counter == 4'd1 &&
    ((IsInterChroma && mv_below8x8_curr && Inter_chroma2x2_counter == 2'b00) ||
     !(IsInterChroma && mv_below8x8_curr)));
```

**色度 2×2 的特殊处理**：当色度被细分到 4×4（`mv_below8x8_curr == 1`）时，
一个 4×4 色度块要分 4 个 2×2 子块（`Inter_chroma2x2_counter` 从 11 到 00），
**只有最后一个子块（00）才算"块结束"**。

## 6.9 输出选择：LPE 还是 CPE

```verilog
// Inter_pred_pipeline.v
if (IsInterLuma && blk4x4_inter_calculate_counter != 0) begin
    Inter_blk4x4_pred_output_valid <= 2'b01;
    case (pos_FracL)
        `pos_Int: Inter_pred_out <= Inter_pix_copy;     // 整数：直接复制
        `pos_b:   Inter_pred_out <= H_6tapfilter_round; // 水平半像素：只用 H
        `pos_h:   Inter_pred_out <= V_6tapfilter_round; // 垂直半像素：只用 V
        `pos_j:   Inter_pred_out <= V_6tapfilter_round; // 双向：V 的输入已是 H 的输出
        default:  Inter_pred_out <= bilinear_out;       // 1/4 位置：双线性
    endcase
end
```

**16 种位置分成 4 类输出路径**：

| 类别 | 位置 | 输出源 |
|---|---|---|
| 整数 | `pos_Int` | `Inter_pix_copy` |
| 纯水平 | `pos_b` | `H_6tapfilter*_round_out` |
| 纯垂直 | `pos_h` | `V_6tapfilter*_round_out` |
| 双向 | `pos_j/f/q/i/k` | `V_6tapfilter*_round_out`（V 的输入是 H 的 raw） |
| 部分分数 | `pos_a/c/d/e/g/n/p/r` | `bilinear*_out`（H 或 V 与整数像素做双线性） |

### `Inter_blk4x4_pred_output_valid`

```verilog
output [1:0] Inter_blk4x4_pred_output_valid;
// 2'b01 = luma 有效，2'b10 = chroma 有效，2'b00 = 无效
```

**为什么用 2 bit 而不是 1 bit？** 因为 `sum.v` 需要知道这个预测是亮度还是色度
（决定输出映射到哪 4 个像素）。

## 6.10 与 ffmpeg 的一致性验证

在我们的 300 帧仿真里，帧间预测的结果是**比特精确**的。这意味着：

- `filterH_6tap` 的三级加法器树**数学等价于 `(A−5B+20C+20D−5E+F)`**
- `filterV_6tap` 的 `>>10` 和 `+512` **与 H.264 的两次舍入规则一致**
- `H_need_round` 对 `pos_j/f/q/i/k` 的例外**正确保留了中间精度**
- `CPE_base` 的 8 个条件移位加法器**等价于 4 个乘法器**
- 边界 padding 的**复制规则**正确

**这五项任何一项错了，都会在分数像素位置产生系统性误差**，不可能比特精确。

### 一个可量化的实验

akiyo 序列里 **91% 的 MB 是 skip**（MV ≈ 0，整数位置），所以
**帧间预测的分数像素路径很少被激活**。

想验证分数像素插值，需要用**高运动序列**（如 foreman、coastguard）
或人为注入分数 MV。第 11 章的实验 4 给出方法。

## 6.11 本章小结：帧间预测的四个设计要点

### 要点 1：13×13 寄存器阵列 = 用面积换带宽

- **不做**：按需从 RAM 读（每像素 1 次读 → 大量的地址计算和等待）
- **做**：一次读 13×13 到寄存器，然后从中"抽"窗口
- **代价**：1352 bit 寄存器（约 8.5k 门，占 169K 门的 5%）
- **收益**：访存次数减少 4–10 倍，且**地址计算可以流水化**

### 要点 2：6-tap 的全加法器实现

- **不做**：6 个乘法器 + 1 个加法树
- **做**：3 个两级加法器（`P−5Q+20R` 的分解）
- **收益**：**零乘法器**，且加法器的延迟比乘法器小得多（有利于 200 MHz）

### 要点 3：色度的条件移位乘法

- **不做**：4 个 8×4 乘法器
- **做**：8 个条件移位 + 加法树
- **收益**：面积约为乘法器的 1/3，且**当 `xFracC` 某位为 0 时该路被完全屏蔽**
  （operand isolation，省动态功耗）

### 要点 4：三层 MV 粒度 + 快速路径

- **`mv_is16x16`**：整 MB 一个 MV，跳过所有子块选择逻辑
- **`mv_below8x8`**：1 bit 决定是否拆到 4×4
- **`Is_InterChromaCopy`**：色度整数位置直接复制，16 周期 → 4 周期

**三个标志位覆盖了绝大多数实际情况**，让复杂路径只在必要时激活。
