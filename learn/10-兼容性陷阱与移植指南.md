# 第 10 章 兼容性陷阱与移植指南

前 9 章证明了 nova **能正确解码它支持的码流**。这一章讲**它不支持什么**，
以及**想改造它要动哪里**。

**先说结论**：

> nova 不是"H.264 Baseline 解码器"，而是
> **"符合 H.264 Baseline 某个特定子集、且分辨率写死为 QCIF 的论文验证载体"**。
>
> 它的正确性范围是：**JM 参考软件输出的、`pic_order_cnt_type == 0` 的、
> 单 slice、无 SEI、1 个参考帧、QCIF 的码流**。

## 10.1 陷阱 1：解不了 x264 的码流（最致命的坑）

第 9.9 节已经做过实验验证。这里给**完整的根因分析**。

### 10.1.1 现象

```bash
ffmpeg -f lavfi -i "testsrc=size=176x144:rate=30:duration=2" -pix_fmt yuv420p \
       -f rawvideo testsrc.yuv
ffmpeg -f rawvideo -pix_fmt yuv420p -s 176x144 -i testsrc.yuv \
       -c:v libx264 -profile:v baseline -qp 28 -f h264 testsrc.264
./scripts/run_regression.sh -b testsrc.264 -n 2
```

```
[compare] 帧 0 / Y / maxdiff=255  mean=124.5  不同像素=25344  PSNR=4.93 dB
[compare] 结果: FAIL
```

**PSNR 4.93 dB ≈ 随机噪声。** 而且 nova 的输出只有 31 种取值、
Y 平面均值 0.54（应约 125）——**根本没解出来**。

### 10.1.2 根因 A：SPS 解析器是硬连线固定序列

**`BitStream_parser_FSM_gating.v:202-216`（原文）**：

```verilog
`seq_parameter_set_id_sps_s:
    seq_parameter_set_state <= `log2_max_frame_num_minus4_s;
`log2_max_frame_num_minus4_s:
    seq_parameter_set_state <= `pic_order_cnt_type_s;
`pic_order_cnt_type_s:
    seq_parameter_set_state <= `log2_max_pic_order_cnt_lsb_minus4_s;   // ← 无条件！
`log2_max_pic_order_cnt_lsb_minus4_s:
    seq_parameter_set_state <= `num_ref_frames_s;
```

**H.264 规范 Table 7-3（SPS 语法）**：

```
seq_parameter_set_rbsp( ) {
    profile_idc                       u(8)
    constraint_set0..3_flag           u(1) ×4
    reserved_zero_4bits               u(4)
    level_idc                         u(8)
    seq_parameter_set_id              ue(v)
    if( profile_idc == 100 || 110 || 122 || 244 || 44 || 83 || 86 || 118 || 128 || 138 || 139 || 134 )
        chroma_format_idc ...
    log2_max_frame_num_minus4         ue(v)
    pic_order_cnt_type                ue(v)
    if( pic_order_cnt_type == 0 )                        ← 条件字段！
        log2_max_pic_order_cnt_lsb_minus4   ue(v)
    else if( pic_order_cnt_type == 1 ) {
        delta_pic_order_always_zero_flag    u(1)
        offset_for_non_ref_pic              se(v)
        offset_for_top_to_bottom_field      se(v)
        num_ref_frames_in_pic_order_cnt_cycle ue(v)
        for( i = 0; i < num_ref_frames_in_pic_order_cnt_cycle; i++ )
            offset_for_ref_frame[ i ]       se(v)
    }
    num_ref_frames                    ue(v)
    gaps_in_frame_num_value_allowed_flag u(1)
    pic_width_in_mbs_minus1           ue(v)
    pic_height_in_map_units_minus1    ue(v)
    frame_mbs_only_flag               u(1)
    ...
}
```

**nova 的实现缺了三个分支**：

1. **`if (pic_order_cnt_type == 0)`** —— 无条件读 `log2_max_pic_order_cnt_lsb_minus4`
2. **`else if (pic_order_cnt_type == 1)`** —— 完全不支持（4 个额外字段 + 循环）
3. **`profile_idc == 100/110/...` 的 `chroma_format_idc`** —— 不支持 High profile

**x264 在 `-profile:v baseline` 时强制 `pic_order_cnt_type = 2`**，
所以 `log2_max_pic_order_cnt_lsb_minus4` **根本不存在**。

### 10.1.3 错位的连锁反应

**JM94 的 SPS 字节（akiyo300_1ref.txt 前 16 个字节）**：

```
00 00 00 01 67 42 00 1E E7 41 62 72 00 00 00 01
            │  │  │  │  │  │  │  │
            │  │  │  │  │  │  │  └─ num_ref_frames = 1
            │  │  │  │  │  │  └──── log2_max_poc_lsb_m4 = 6  （poc_type=0 才有）
            │  │  │  │  │  └─────── pic_order_cnt_type = 0
            │  │  │  │  └────────── log2_max_frame_num_m4 = 0
            │  │  │  └───────────── seq_parameter_set_id = 0
            │  │  └──────────────── level_idc = 30
            │  └─────────────────── profile_idc = 66 (Baseline)
            └────────────────────── NAL header (0x67 = SPS)
```

**x264 baseline 的 SPS**（`ffprobe -show_frames` 或手算）：

```
00 00 00 01 67 42 00 0A F8 41 A2 ... 
            │  │  │  │  │
            │  │  │  │  └─ pic_order_cnt_type = 2  ← 无 log2_max_poc_lsb_m4！
            │  │  │  └──── log2_max_frame_num_m4 = 0
            │  │  └─────── level_idc = 10
            │  └────────── profile_idc = 66
            └───────────── NAL header
```

**nova 按 poc_type==0 的布局去读 poc_type==2 的 SPS**：

| nova 以为在读 | 实际读到 | 后果 |
|---|---|---|
| `log2_max_pic_order_cnt_lsb_minus4` | x264 的 `num_ref_frames`（位）| 错 |
| `num_ref_frames`（ue）| x264 的 `gaps_flag` + 后续位 | 错 |
| `gaps_in_frame_num_value_allowed_flag` | 错位的 1 bit | 错 |
| **`pic_width_in_mbs_minus1`（ue）** | **错位的位** | **宽错** |
| **`pic_height_in_map_units_minus1`（ue）** | **错位的位** | **高错** |

**`pic_width` / `pic_height` 错了会怎样？**

这两个值**在 nova 里其实没被用到**（见 10.1.5），但**错位本身会让状态机
跳到奇怪的地方** ——实测 `parser_state` 卡在 `start_code_prefix`、
`pc` 停在 96 不动、`BitStream_ram_addr` 只到 5。

**为什么？** 因为 `exp_golomb_decoding` 读到的长度是错的（不是合法的
`ue(v)` 编码），`pc` 算出来的增量不是正整数 → **`pc` 前进不了**。

### 10.1.4 根因 B：NAL 类型缺分支（独立的第二个坑）

**`BitStream_parser_FSM_gating.v:170-176`（原文）**：

```verilog
case (nal_unit_type)
    5'b00001: nal_unit_state <= `slice_layer_non_IDR_rbsp;  // non-IDR slice
    5'b00101: nal_unit_state <= `slice_layer_IDR_rbsp;      // IDR slice
    5'b00111: nal_unit_state <= `seq_parameter_set_rbsp;    // SPS
    5'b01000: nal_unit_state <= `pic_parameter_set_rbsp;    // PPS
    // ← 没有 default！
endcase
```

**缺少**：

| NAL type | 名称 | 后果 |
|---|---|---|
| **6** | SEI | **死锁**（case 无匹配 → 状态不变）|
| **9** | AUD（Access Unit Delimiter）| 死锁 |
| 7 | SPS | ✓ 支持 |
| 8 | PPS | ✓ 支持 |
| 1/5 | slice | ✓ 支持 |
| 2/3/4 | slice partition A/B/C | 死锁（FMO 相关）|
| 10/11 | end of seq/stream | 死锁 |
| 12 | filler | 死锁 |
| 13 | SPS extension | 死锁 |
| 14/15 | prefix/suffix NAL | 死锁 |
| 19 | auxiliary slice | 死锁 |

**x264 默认会插 SEI（`x264` 的 user data），所以两步都踩。**

**验证**：用 ffmpeg 的 `filter_units` 去掉 SEI 后仍然 FAIL —— 因为
**poc_type 的问题更严重**（SPS 都错了，后面全错）。**两个坑必须都修。**

### 10.1.5 修正方案：给 SPS 解析器加分支

**改动量很小**（约 30 行）：

```verilog
// BitStream_parser_FSM_gating.v
// ① 加状态
`define log2_max_pic_order_cnt_lsb_minus4_s  4'b1000   // 新增
`define delta_pic_order_always_zero_flag_s   4'b1001   // 新增
// ... poc_type==1 的其他字段

// ② 改 SPS 状态机：pic_order_cnt_type 之后按类型分支
`pic_order_cnt_type_s:
    case (pic_order_cnt_type)
        2'd0: seq_parameter_set_state <= `log2_max_pic_order_cnt_lsb_minus4_s;
        2'd1: seq_parameter_set_state <= `delta_pic_order_always_zero_flag_s;
        2'd2: seq_parameter_set_state <= `num_ref_frames_s;  // ← 跳过 poc 字段
        default: seq_parameter_set_state <= `num_ref_frames_s;
    endcase
`log2_max_pic_order_cnt_lsb_minus4_s:
    seq_parameter_set_state <= `num_ref_frames_s;
`delta_pic_order_always_zero_flag_s:
    seq_parameter_set_state <= `offset_for_non_ref_pic_s;
// ... poc_type==1 的链路

// ③ 改 slice_header 状态机：注意 H.264 规范中 idr_pic_id 永远紧跟在 frame_num 之后、pic_order_cnt_lsb 之前！
`frame_num_s:
    if (nal_unit_type == 5'b00101)
        slice_header_state <= `idr_pic_id_s;
    else if (pic_order_cnt_type == 2'd0)
        slice_header_state <= `pic_order_cnt_lsb_s;
    else
        slice_header_state <= (slice_type == 3'd0 || slice_type == 3'd5)
                              ? `num_ref_idx_active_override_flag_s : `dec_ref_pic_marking;
`idr_pic_id_s:
    if (pic_order_cnt_type == 2'd0)
        slice_header_state <= `pic_order_cnt_lsb_s;
    else
        slice_header_state <= (slice_type == 3'd0 || slice_type == 3'd5)
                              ? `num_ref_idx_active_override_flag_s : `dec_ref_pic_marking;

// ④ 给 nal_unit 加 default：跳过未知 NAL（需配合搜索下一个起始码，简单跳到 rbsp_trailing 仅对短 NAL 有效）
default: nal_unit_state <= `rbsp_trailing_one_bit;
```

### 10.1.5b 隐藏陷阱 C：`slice_type` 只认 `5 / 7` 与两处源码潜在 Bug

在核实 `src/` 源码时，还发现了三处极易踩坑的隐藏限制：
1. **`slice_type` 只认 `5`（全 P）和 `7`（全 I），不认 `0` 和 `2`**：H.264 允许编码器把 P-slice 编成 `0` 或 `5`、把 I-slice 编成 `2` 或 `7`。`BitStream_parser_FSM_gating.v:259, 268` 只判断 `slice_type == 3'b101`（5），`:333` 只判断 `slice_type != 3'b111`（7）！如果新编码器输出 `slice_type == 0` 或 `2`，状态机会直接走错分支（移植时必须统一改成 `slice_type == 0 || slice_type == 5` 与 `slice_type == 2 || slice_type == 7`）；
2. **`exp_golomb_decoding.v:99` 的 `slice_beta_offset_div2_s` 误写成 `ue`**：H.264 规定它和 `slice_alpha_c0_offset_div2` 一样是 `se(v)`，此处应改为 `se`；
3. **`syntax_decoding.v:342` 的 P 帧 `Intra16x16_CBPChroma2` 拼写笔误**：`14..17, 26..29` 误映射到 `` `MB_Intra16x16_CBPChroma0 ``，移植时应修正为 `` `MB_Intra16x16_CBPChroma2 ``。

**同时要改 `pc_decoding.v` 的 `consumed_bits_sel`**（新增两个状态的
比特长度选择）和 `exp_golomb_decoding.v` 的 `exp_golomb_sel`（同上）。

**总改动量**：约 60–80 行，涉及 4 个文件。**这是移植的第一步，必须做。**

### 10.1.6 为什么作者没做

**看 `syntax_decoding.v:126`**：

```verilog
reg [2:0] num_ref_frames; //however,we only support 1 reference frame currently
```

**作者自己注释了"只支持 1 个参考帧"** —— 说明他知道自己在做子集。

**这是一篇 2008 年的**学术论文**的验证载体**：论文的核心贡献是
"5 级流水 + 204 cycles/MB 的单端口 SRAM 去块滤波器"，**不是"通用解码器"**。
作者用 JM94 编码的 10 个标准测试序列验证，**这些序列的 SPS 都是 poc_type=0**。

**所以这不是"bug"，是"设计范围"。** 但**对想复用的人是个巨大的坑**。

## 10.2 陷阱 2：分辨率写死在 40+19+8 处

**想改成 CIF（352×288，22×18 MB）？** 要改的地方比想象的多。

### 10.2.1 硬编码统计

| 硬编码模式 | 含义 | 有效代码次数（含注释） | 分布 |
|---|---|---|---|
| **`mb_num == 98`** | QCIF 共 99 个 MB（0..98）| **7**（+1 注释） | `BitStream_parser_FSM_gating.v`(5)、`bitstream_gclk_gen.v`(2)、`bs_decoding.v`(1 注释) |
| **`mb_num_h == 10`** | 11 列，10 是最后一列 | **35**（+5 注释） | `Inter_mv_decoding.v`(32+4)、`BitStream_parser_FSM_gating.v`(2)、`rec_gclk_gen.v`(1)、`Intra4x4_PredMode_decoding.v`(1 注释) |
| **`mb_num_h != 10`** | 非最右列（**千万别漏改！**） | **16** | `rec_gclk_gen.v`(6)、`nC_decoding.v`(3)、`syntax_decoding.v`(2)、`Intra_pred_pipeline.v`(2)、`Inter_mv_decoding.v`(2)、`Intra4x4_PredMode_decoding.v`(1) |
| **`mb_num_v == 8`** | 9 行，8 是最后一行 | **19** | `Inter_mv_decoding.v`(18)、`BitStream_parser_FSM_gating.v`(1) |
| **`mb_num_v != 8`** | 非最后一行（**千万别漏改！**） | **15**（+2 注释） | `nC_decoding.v`(4)、`Inter_mv_decoding.v`(4+2)、`Intra4x4_PredMode_decoding.v`(2)、`syntax_decoding.v`(2)、`bs_decoding.v`(1)，外加 `DF_mem_ctrl.v` 与 `DF_reg_ctrl.v` 的 `mb_num_h_DF == 10` / `mb_num_v_DF == 8` |

**仅 `mb_num / mb_num_h / mb_num_v` 就有 92 处以上有效硬编码**（早期粗略统计的 67 处只搜了 `==`，漏掉了 31 处 `!= 10 / != 8` 和 DF 里的 `mb_num_h_DF / mb_num_v_DF`！）。

**为什么 `Inter_mv_decoding.v` 这么多（54 处）？**

因为 **MV 预测要判断邻居可用性**：

```verilog
// Inter_mv_decoding.v（典型片段）
if (mb_num_h == 10 || mb_num_v == 8) begin
    // 最右列 / 最后一行：邻居不存在，MVP = 0
    mvpAx <= 0; mvpBx <= 0; mvpCx <= 0;
end else begin
    // 正常情况：读 mbAddrA/B/C 的 MV
    ...
end
```

**H.264 8.4.1.3 的 MVP 规则**：
- 如果 A（左邻）不存在 → `mvpA = 0`
- 如果 B（上邻）不存在 → `mvpB = 0`
- 如果 C（右上）不存在 → `mvpC = 0`

**"不存在"的判据 = `mb_num_h == 10`（最右列）或 `mb_num_v == 8`（最后一行）**。
**这两个数字是 QCIF 的 11×9 减 1。**

### 10.2.2 端口只有 4 bit

```verilog
// BitStream_controller.v:56-57
output [3:0] mb_num_h;
output [3:0] mb_num_v;
```

**4 bit 只能表示 0..15** → **最多 16 列 × 16 行 = 256 个 MB**。

**这意味着即使改了硬编码，也最多支持**：

| 分辨率 | MB 数 | 能否支持 |
|---|---|---|
| QCIF 176×144 | 11 × 9 | ✓ |
| CIF 352×288 | 22 × 18 | ✗ **超 4 bit** |
| 4CIF 704×576 | 44 × 36 | ✗ |
| 720p | 80 × 45 | ✗ |

**支持 CIF 需要把端口扩到 5 bit，且改所有 67 处硬编码。** 工作量不小。

### 10.2.3 帧存地址的三层硬编码

**第一层：`dis_frame_RAM_wr_addr_base` 的偏移**

```verilog
// DF_mem_ctrl.v:359/361/373/375
dis_frame_RAM_wr_addr_base <= 13'd6336;   // Cb
dis_frame_RAM_wr_addr_base <= 13'd7920;   // Cr
```

**6336 = 176/4 × 144 = 44 word/行 × 144 行**、**7920 = 6336 + 1584**。

**改成 CIF**：`352/4 × 288 = 88 × 288 = 25344`、`25344 + 6336 = 31680`。

**第二层：`Inter_pred_pipeline.v:697`**

```verilog
assign offset_constant = (IsInterLuma) ? 0 :
                         ((IsInterChroma) ? ((blk4x4_rec_counter < 5'd20) ? 13'd6336 : 13'd7920) : 0);
```

**同样的 6336 / 7920。**

**第三层：行跨距的移位加法树**

```verilog
// DF_mem_ctrl.v:528-530（原文）
// luma,  x44 = x32 + x8 + x4
assign y_x44 = {y, 5'b0} + {2'b0, y, 3'b0} + {3'b0, y, 2'b0};
// chroma, x22 = x16 + x4 + x2
assign y_x22 = {y, 4'b0} + {3'b0, y, 2'b0} + {4'b0, y, 1'b0};
```

**44 和 22 没有独立宏**，只以加法树形式出现。**改分辨率必须改这两个 assign。**

**（CIF 的 luma 行跨距是 88 word = 64+16+8，chroma 是 44。）**

### 10.2.4 存储容量要全部重算

| 存储 | QCIF | CIF | 说明 |
|---|---|---|---|
| `Intra_mbAddrB_RAM` | 88 | **176** | 一行 luma 88 + Cb 44 + Cr 44 |
| `DF_mbAddrA_RAM` | 32 | 32 | 一个 4×4 块 × 4 行 × 4 列 / 4 像素每 word = 32 |
| `DF_mbAddrB_RAM` | 352 | **704** | 22 列 × 32 |
| `rec_DF_RAM0/1` | 96 | 96 | 一个 MB 的 24 块 × 4 word（与分辨率无关）|
| 外帧存 | 9504 | **38016** | 352×288×1.5/4 |

**注意 `rec_DF_RAM0/1` 和 `DF_mbAddrA_RAM` 不变**（它们是"一个 MB 内"的存储），
**只有"跨 MB 边界"的存储要扩**。

### 10.2.5 只能等宽吗

**不能。** nova 有**隐式的"每行 MB 数 = 11"假设**：

```verilog
// BitStream_parser_FSM_gating.v:500
mb_num <= (mb_num == 98) ? 0 : (mb_num + 1);
```

**`mb_num` 是 0..98 的线性计数**（不分行列）。**分行列的逻辑在别处**：

```verilog
// BitStream_parser_FSM_gating.v（隐含）
mb_num_h <= mb_num % 11;    // ← 但实际不是这么写的
mb_num_v <= mb_num / 11;
```

**实际实现**（`BitStream_parser_FSM_gating.v:482-500` 核实原文）：三个计数器各自独立回绕，`mb_num_h` 和 `mb_num_v` **并不依赖 `mb_num == 98` 归零**：

```verilog
// BitStream_parser_FSM_gating.v:482-500
mb_num_h <= (mb_num_h == 10) ? 0 : (mb_num_h + 1);
if (mb_num_h == 10)
    mb_num_v <= (mb_num_v == 8) ? 0 : (mb_num_v + 1);
mb_num <= (mb_num == 98) ? 0 : (mb_num + 1);
```

**所以"11"和"10"是同一个硬编码的两个面。**

## 10.3 陷阱 3：Baseline 子集的具体边界

**以下是 nova 不支持、但 H.264 Baseline 允许的工具**：

| 工具 | 规范要求 | nova 实现 | 证据 |
|---|---|---|---|
| **I_PCM** | 必须支持 | **完全未接入（仅留空宏）** | `nova_defines.v:54` 虽有 `MB_I_PCM 4'b0110`，但 `syntax_decoding.v:324-344` 未映射 `mb_type=25/30`、`BitStream_parser_FSM_gating.v` 从不跳入 `pcm_*` 状态；`:394` 注释 `//pcm_byte_s: --> Currently no deal with it` |
| **参考帧数 > 1** | Baseline 允许 | **只支持 1 个** | `syntax_decoding.v:126` `//however,we only support 1 reference frame currently` |
| **Weighted prediction** | Baseline 无（P 帧的 weighted_pred_flag 在 baseline 应为 0）| 解析但不使用 | `syntax_decoding.v:195-196` 声明且 `:233` 解析，无后续使用 |
| **FMO（多 slice group）** | Baseline 允许 | **解析但不用** | `num_slice_groups_minus1` 在 `syntax_decoding.v:192` 声明、`:230` 解析，**无任何后续使用** |
| **ASO（任意 slice 顺序）** | Baseline 允许 | 不支持 | 单 slice 假设 |
| **多 slice / 帧** | Baseline 允许 | 不支持 | `mb_num == 98` 判帧尾（假设一帧一个 slice）|
| **SEI / AUD** | 可以忽略但必须能跳过 | **死锁** | `BitStream_parser_FSM_gating.v:170-176` 无 default |
| **pic_order_cnt_type = 1 或 2** | Baseline 允许 | 不支持 | SPS FSM 无条件读 poc_type==0 的字段 |
| **8×8 变换** | High profile | 不支持 | 无对应模块（Baseline 本来就没有）|
| **CABAC** | Main/High profile | 不支持 | 只有 `cavlc_decoder.v` |
| **B 帧 / B slice** | Baseline 无（baseline 只有 I/P）| 不支持 | 有 `num_ref_idx_l1` 寄存器但无 `mb_pred` 分支 |

### 10.3.1 I_PCM 的坑最隐蔽

**`I_PCM` 是"直接存原始像素"的 MB 类型**：位流里是这个 MB 的 384 个
原始字节（16×16 luma + 2×8×8 chroma）。

**nova 的实际行为（源码核实）**：

- `nova_defines.v:54` 仅声明了 `MB_I_PCM = 4'b0110`，`pc_decoding.v:82-83, 159` 保留了 `pcm_alignment_zero_bit_s / pcm_byte_s` 分支；
- **但 `syntax_decoding.v:324-344` 根本没有映射 I-slice 的 `mb_type=25` 或 P-slice 的 `mb_type=30`**（它们会掉进 `default` 被错认成 `Inter16x16`/`Inter16x8`）；
- **而且 `BitStream_parser_FSM_gating.v` 的 `slice_data_state` 从未转移到 `pcm_alignment_zero_bit_s` 或 `pcm_byte_s`**，`syntax_decoding.v:394` 注释 `//pcm_byte_s: --> Currently no deal with it`。
- 结果：**一旦码流出现 I_PCM 宏块，解析会立即错位崩溃。**

**为什么 JM94 的测试序列没暴露这个问题？** 因为**这 10 个序列的 QP 都在 24–36**，
**编码器不会选 I_PCM**（I_PCM 只在极高码率/极低 QP 时才用）。

### 10.3.2 `pic_width_in_mbs_minus1` 是 4 bit（且没用）

```verilog
// syntax_decoding.v:128-129
reg [3:0] pic_width_in_mbs_minus1;
reg [3:0] pic_height_in_map_units_minus1;
// :175-176
`pic_width_in_mbs_minus1_s : pic_width_in_mbs_minus1 <= exp_golomb_decoding_output[3:0];
```

**两个问题**：

1. **4 bit 只能存 0..15**（即宽度 ≤ 16 MB = 256 像素）。**1080p 需要 7 bit。**
2. **这两个寄存器解析出来后没有任何地方使用**（grep 确认：只有声明、
   复位、赋值，无读取）

**这说明**：**nova 完全忽略码流里的分辨率**，硬编码为 QCIF。
**好处**：少一条数据通路。**坏处**：码流的分辨率错了也不报错，
**行为不可预测**（我们实测是卡死）。

## 10.4 移植路线图

### 10.4.1 最小可用移植（能解现代码流，仍是 QCIF）

**目标**：让 nova 能解 x264 输出的 QCIF baseline 码流。

| 步骤 | 文件 | 改动 | 工作量 |
|---|---|---|---|
| 1 | `BitStream_parser_FSM_gating.v` | SPS 加 `pic_order_cnt_type` 分支 | 20 行 |
| 2 | `BitStream_parser_FSM_gating.v` | slice_header 加 poc 分支 | 10 行 |
| 3 | `BitStream_parser_FSM_gating.v` | nal_unit 加 default（跳过未知 NAL）| 5 行 |
| 4 | `pc_decoding.v` | 新状态的 `consumed_bits_sel` | 10 行 |
| 5 | `exp_golomb_decoding.v` | 新状态的 `exp_golomb_sel` | 10 行 |
| 6 | `nova_defines.v` | 新状态宏（Gray 码）| 6 行 |

**总计约 60 行，4 个文件。** 改完后能解 poc_type=2 的码流。

**验证方法**：

```bash
./scripts/run_regression.sh --encode -n 2 -t poc2_fixed
# 期望 PASS（2 帧比特精确）
```

**注意还需确认 x264 有没有用其他不支持的工具**（比如 `weighted_pred`）。
建议编码参数：

```bash
-x264-params "weightedp=0:8x8dct=0:cabac=0:bframes=0:ref=1:slices=1:keyint=30"
```

### 10.4.2 支持 CIF（352×288）

**这是个大工程**（约 2 周）：

| 步骤 | 改动 | 工作量 |
|---|---|---|
| 1 | 端口 `mb_num_h/v` 扩到 5 bit | 触达 10+ 个模块的端口列表 |
| 2 | **67 处硬编码** `98`/`10`/`8` 改成参数 | 主要工作 |
| 3 | `nova_defines.v` 加 `mb_per_row`/`mb_per_col`/`total_mb` | 3 行 |
| 4 | 帧存偏移 6336/7920 → 25344/31680 | 4 处 |
| 5 | 行跨距 44/22 → 88/44（移位加法树）| 2 处 |
| 6 | `Intra_mbAddrB_RAM` 88 → 176 | 1 处 + 参数 |
| 7 | `DF_mbAddrB_RAM` 352 → 704 | 1 处 + 参数 |
| 8 | 外帧存 9504 → 38016 | tb + wrapper |
| 9 | `mb_num_h/v` 的 4 bit 比较全改 | 与步骤 2 重合 |
| 10 | 重新跑 300 帧验证 | 1 天（仿真时间）|

**最大的坑是步骤 2**：`Inter_mv_decoding.v` 里的 54 处不只是"数字替换" ——
**它们是 `if (mb_num_h == 10)` 这种"最右列"判断**，要换成
`if (mb_num_h == MB_PER_ROW - 1)`。

**建议做法**：先用 `sed` 批量替换成宏，再逐个 review：

```bash
sed -i 's/mb_num_h == 10/mb_num_h == (`MB_PER_ROW - 1)/g' src/Inter_mv_decoding.v
sed -i 's/mb_num_v == 8/mb_num_v == (`MB_PER_COL - 1)/g' src/Inter_mv_decoding.v
sed -i 's/mb_num == 98/mb_num == (`TOTAL_MB - 1)/g' src/*.v
```

**但 `mb_num_h == 10` 在有些地方是"11 列"的语义，有些是"最后一列"的语义** ——
sed 之后必须**逐处确认**。

### 10.4.3 支持 1080p

**不建议**。原因：

1. **`mb_num_h/v` 要 8 bit**（120/68 列行）
2. **帧存地址要 22 bit**（当前 14 bit = 16384 word = 64 KB）
3. **`DF_mbAddrB_RAM` 要 120 × 32 = 3840 word**（当前 352）
4. **位流 ROM 要几 MB**（当前 256 KB）
5. **流水线周期数不变，但频率要提到 ~150 MHz**（1080p30 = 8100 MB/s ÷ 204 cycles/MB）

**而 nova 的定位是"移动设备的 QCIF 低功耗解码"** ——
**1080p 用这个架构是选错了工具**（该用多核 + 帧级并行）。

### 10.4.4 集成到 SoC 的注意事项

**nova 的顶层接口很"裸"**：

```verilog
module nova (clk, reset_n, BitStream_buffer_input, BitStream_ram_ren, BitStream_ram_addr,
             pin_disable_DF, freq_ctrl0, freq_ctrl1, pic_num,
             ext_frame_RAM0_cs_n, ext_frame_RAM0_wr, ext_frame_RAM0_addr,
             ext_frame_RAM0_data, ext_frame_RAM1_cs_n, ext_frame_RAM1_wr,
             ext_frame_RAM1_addr, ext_frame_RAM1_data, dis_frame_RAM_din,
             slice_header_s6);
```

**集成时要注意的五点**：

#### 1. `BitStream_ram_*` 是标准 **1 周期同步读 SRAM** 接口

```verilog
// Beha_BitStream_ram.v:33-35
always @ (posedge clk)
    if (BitStream_ram_ren == 0)
        BitStream_ram_data <= #2 BitStream_ram[BitStream_ram_addr];
```

**注意**：`#2` 只是 2 ns 的仿真输出传播延迟，**不是 2 个时钟周期** —— 它就是一块普通的 **1 拍同步读 SRAM**（`BitStream_buffer.v` 本身发出寄存后的地址和 `ren`，加上 SRAM 的 1 拍同步读，整个环路共 2 拍）。换成真实单端口同步 SRAM 时保持标准 1 拍同步读时序即可。

#### 2. `ext_frame_RAM*_data` 是 **input 不是 inout**

**两块帧存是分开的读端口和写端口**：

- `ext_frame_RAM0_data[31:0]` 是 **input**（读数据进 nova）
- `dis_frame_RAM_din[31:0]` 是 **output**（写数据出 nova）

**所以外部需要一个"读数据 MUX"**：

```verilog
// 外部胶合逻辑
wire [31:0] ref_frame_RAM_dout = ext_frame_RAM_sel ? ram1_q : ram0_q;
assign ram0_din = (!ram0_cs_n && ram0_wr) ? dis_frame_RAM_din : 32'bz;
```

**`ext_RAM_ctrl.v` 内部已经做了这个选择**（第 9 章讲过），但**外部 RAM
实例要自己接**。

#### 3. `freq_ctrl0/1` 必须给对

**如果给错档位会丢帧**（第 9.7 节）。**推荐**：

- QCIF 30 fps → `freq_ctrl = 2'b00`（45000）
- QCIF 15 fps → `freq_ctrl = 2'b11`（70000）
- **不确定就给 `2'b11`**（最慢，最安全）

#### 4. `pin_disable_DF` 的默认值

**`pin_disable_DF = 1` 会关闭去块滤波** ——
**只有调试时才用**。正常解码必须 `= 0`。

#### 5. `pic_num` 是 debug 输出，不要用它做帧同步

**`pic_num` 是 6 bit（0..63 循环）**，而且**只有在 `mb_num == 98` 时才递增**
（`BitStream_parser_FSM_gating.v:506`）。**不要用它判断"第几帧"** ——
用 `slice_header_s6` + 你自己的帧计数器（就像我们的 tb）。

### 10.4.5 时钟与复位

```verilog
// 规格书 Table 6
// clk: 1..10 MHz，占空比 50/50
// reset_n: 低有效，至少保持 2 个 clk 周期
```

**我们的 tb 用 1.47 MHz**（680 ns 周期）。**这是"最小频率"**，
对应 QCIF 30 fps 的最低要求。

**复位要求（核实后的两类触发器）**：

- **门控时钟域**（`always @(posedge gclk_* or negedge reset_n)`）：**异步低有效复位**，确保门控关断时仍能立刻清零；
- **主时钟域**（如 `BitStream_buffer.v`、`syntax_decoding.v`、`bitstream_gclk_gen.v` 等 `always @(posedge clk)`）：**同步低有效复位**；
- 因此 `reset_n == 0` 必须至少覆盖 **2 个 `clk` 上升沿**（我们的 tb 保持 1000 ns ≈ 1.5 个周期且覆盖了 1 个上升沿，实测安全；工程集成时建议严格保持 ≥ 2 个周期）。

**如果复位太短**：`BitStream_buffer` 的 `reset_counter` 没走完 0..10，
**位流桶形缓冲里有 X** → 解码出错。

## 10.5 兼容性自检清单

**拿到一个码流，先跑这个清单**：

```bash
# 1. 看 SPS 的关键字段
ffprobe -v error -show_streams -select_streams v:0 input.264 | grep -E "profile|level|width|height|refs"

# 2. 看 pic_order_cnt_type（需要 trace_headers）
ffmpeg -v trace -i input.264 -f null - 2>&1 | grep -m5 "pic_order_cnt_type"

# 3. 看有没有 SEI
ffmpeg -v trace -i input.264 -f null - 2>&1 | grep -c "nal_unit_type: 6"

# 4. 看参考帧数
ffprobe -v error -show_entries stream=refs -of default=nw=1 input.264
```

**判据表**：

| 字段 | nova 支持 | 不支持怎么办 |
|---|---|---|
| `profile_idc` | 66（Baseline）| 重新编码 |
| `level_idc` | 任意 | ✓ |
| `pic_order_cnt_type` | **0** | **修 RTL（10.4.1）或换编码器** |
| `num_ref_frames` | **1** | **`-x264-params ref=1`** |
| `vui_parameters_present_flag` | 0 | **修 RTL（VUI 会错位）** |
| SEI 存在 | 否 | **`-bsf:v filter_units=remove_types=6`** |
| AUD 存在 | 否 | **`-bsf:v filter_units=remove_types=9`** |
| 分辨率 | **176×144** | **修 RTL（10.4.2）** |
| slice 数/帧 | **1** | **`-x264-params slices=1`** |
| B 帧 | 否 | **`-x264-params bframes=0`** |
| CABAC | 否 | **`-x264-params cabac=0`** |
| 8×8 变换 | 否 | **`-x264-params 8x8dct=0`** |

**最快的验证**：直接跑 `run_regression.sh`，看 PSNR。
**PSNR < 20 dB = 完全没解对**（检查 SPS）；**PSNR 30–50 dB = 部分对**（检查其他工具）。

## 10.6 本章小结

### 三句话总结 nova 的能力边界

1. **码流层**：只认 `poc_type==0`、无 SEI/AUD、1 个参考帧、单 slice
2. **分辨率**：写死 QCIF，且 `mb_num_h/v` 只有 4 bit（< CIF）
3. **工具集**：Baseline 的 I/P 帧、CAVLC、4×4/16×16 帧内、1/4 像素帧间、
   去块滤波 —— **I_PCM 和 FMO 是"识别但不实现"的静默失败**

### 移植的优先级

| 优先级 | 改动 | 工作量 | 收益 |
|---|---|---|---|
| **P0** | SPS 加 poc_type 分支 + nal_unit 加 default | 60 行 | **能解现代码流** |
| P1 | 禁用会错位的编码工具（编码侧解决）| 0 行 | 同上 |
| P2 | 分辨率参数化（CIF）| 67 处 + 端口 | 支持更大分辨率 |
| P3 | I_PCM 实现 | ~100 行 | 支持极高码率 |
| P4 | 多参考帧 | ~500 行 | 提升压缩率 |
| — | 1080p | 不建议 | 架构不匹配 |

### 最后的建议

**如果你想"学一个 H.264 解码器"**：nova 是极好的教材 ——
25.8k 行、单一 profile、模块清晰、论文完整、**而且我们证明了它比特精确**。

**如果你想"做一个能用的解码器"**：nova 的架构（204 cycles/MB、
单端口 SRAM、39 路门控时钟）**非常值得借鉴**，但**它的码流解析层必须重写**。

**这正是学术 IP 的典型状态**：**核心创新（DF 流水线）扎实可用，
外围工程（码流兼容性）只做到"论文验证够用"。**
