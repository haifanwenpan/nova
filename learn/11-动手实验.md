## 11.1 实验一：亲眼看见"比特精确"

### 目的

理解为什么这个项目的对比判据是 `maxdiff == 0` 而不是 PSNR。

### 命令

```bash
cd /home/chenye/learning/nova/sim

# 解 10 帧，输出到 /tmp
vvp out/nova_tb.vvp \
    +bitstream=../test/bitstream/akiyo300_1ref.txt \
    +out=/tmp/lab1_nova.yuv +frames=10

# ffmpeg 解同样 10 帧作为参考
ffmpeg -v error -i /tmp/akiyo300.264 -frames:v 10 \
       -f rawvideo -pix_fmt yuv420p /tmp/lab1_ref.yuv -y

# 逐像素比对
python3 scripts/compare_yuv.py /tmp/lab1_nova.yuv /tmp/lab1_ref.yuv --frames 10
```

> `/tmp/akiyo300.264` 怎么来的？把 `test/bitstream/akiyo300_1ref.txt`（每行 2 字节 hex）
> 拼回二进制。一行一行 `xxd -r -p` 也行，用 python 也行：
> ```bash
> python3 -c "
> import sys
> with open('../test/bitstream/akiyo300_1ref.txt') as f, open('/tmp/akiyo300.264','wb') as o:
>     for line in f:
>         o.write(bytes.fromhex(line.strip()))
> "
> ```

### 预期输出

```
帧    平面        maxdiff      mean      不同像素     PSNR(dB)
--------------------------------------------------------------
   0     Y            0     0.000          0         inf
   0     U            0     0.000          0         inf
   0     V            0     0.000          0         inf
   ...
============================================================
[compare] 总像素数    : 380160
[compare] 不同像素总数: 0
[compare] 最差单点    : 帧 0 /  / maxdiff=0
[compare] 整序列 PSNR : inf (比特精确)
[compare] 结果: PASS —— 10 帧全部比特精确，与 ffmpeg 完全一致
```

### 你该看出什么

**nova 和 ffmpeg 是两个完全独立的实现**：

- ffmpeg 是 C 语言、跑在通用 CPU 上、用 x86 SIMD 加速、有几十万行
- nova 是 Verilog、29 个模块、25.8k 行、纯硬件数据通路

而它们输出的 **380160 个字节逐位相同**。这不是"误差很小"，
是"**一模一样**"。

### 为什么能做到

H.264 标准（ITU-T Rec. H.264 / ISO/IEC 14496-10）对解码端的**每一个算术运算**
都规定了精确的中间精度和舍入方式：

| 环节 | 标准条款 | 精度规定 |
|---|---|---|
| 反量化 | 8.5.9 | 移位量、LevelScale 表都是精确的 |
| 反变换 | 8.5.10 ~ 8.5.12 | 蝶形运算、两次归一化的时机都是精确的 |
| 帧内预测 | 8.3.1 ~ 8.3.3 | 加权系数、`round`、`shift` 都是精确的 |
| 6-tap 插值 | 8.4.2.2.1 | `(A − 5B + 20C + 20D − 5E + F + 16) >> 5` |
| 去块滤波 | 8.7 | `alpha`/`beta`/`tc0` 表 + 逐条公式 |

**唯一允许"自由发挥"的地方是反变换的中间位宽**（标准允许一定范围），
但实践中 JM、x264、ffmpeg **都用了标准附件的简化 IDCT**，
所以大家的结果都收敛到同一个值。

> **这解释了第 4 章为什么对 `IsHadamard` 那么讲究**：
> `IsHadamard` 决定蝶形单元对 `D1/D3` 是否做 `>> 1`（DC Hadamard 不右移，AC 4×4 IDCT 在 1D 和 2D 两个方向都要右移）。如果搞错，所有 AC 块反变换系数都会错位，`maxdiff` 立刻变成几十而不是 0。

## 11.2 实验二：测去块滤波到底花多少周期

### 目的

验证规格书说的 "204 cycles/MB"，并解释实测的 209 从哪来。

### 原理

`DF_duration` 是 `DF_pipeline.v` 里的一个寄存器，在 `end_of_BS_DEC` 时置 1、
在 `end_of_MB_DF` 或 `end_of_lastMB_DF` 时清 0。它的高电平宽度就是
**这个 MB 的去块滤波耗时**。

### 探针

```verilog
// /tmp/lab_df.v
module lab_df;
    integer n = 0, cur = 0, mx = 0, mn = 99999, sum = 0;

    always @ (posedge tb_nova.clk)
        if (tb_nova.reset_n === 1'b1 && tb_nova.u_nova.reconstruction.gclk_DF === 1'b1)
            cur = cur + 1;
        else if (cur != 0) begin
            n   = n + 1;
            sum = sum + cur;
            if (cur > mx) mx = cur;
            if (cur < mn) mn = cur;
            cur = 0;
            if (n == 200) begin
                $display("[DF] bursts=%0d  avg=%0d  max=%0d  min=%0d", n, sum/n, mx, mn);
                $finish;
            end
        end
endmodule
```

### 命令

```bash
cd /home/chenye/learning/nova/sim

iverilog -g2005 -o /tmp/lab_df.vvp -s tb_nova -s lab_df -I rtl \
         tb/tb_nova.v rtl/*.v /tmp/lab_df.v

vvp /tmp/lab_df.vvp +bitstream=../test/bitstream/akiyo300_1ref.txt \
    +out=/tmp/lab_df.yuv +frames=5 2>&1 | grep "\[DF\]"
```

### 预期输出

```
[DF] bursts=200  avg=210  max=210  min=210
```

（用 `gclk_DF` 的高电平宽度算得 **210**；如果直接测 `DF_duration` 寄存器
本身，得到的是 **209** —— 差 1 是因为 `rec_gclk_gen.v:375` 的 `DF_ena = DF_duration | end_of_BS_DEC` 让 `gclk_DF` 比 `DF_duration` **早一拍**打开。）

### 204 从哪来

`DF_mem_ctrl.v` 里有个 4 bit 计数器 `DF_12_cycles`：

```verilog
// DF_mem_ctrl.v
// reset → 12
if (!disable_DF && DF_edge_counter_MW == 6'd47 && one_edge_counter_MW == 2'd3)
    DF_12_cycles <= 0;                    // 最后一个像素处理完 → 从 0 开始数
else if (DF_12_cycles != 4'd12)
    DF_12_cycles <= DF_12_cycles + 1;     // 数到 12 停
```

**账**：

| 项 | 周期数 | 说明 |
|---|---|---|
| 亮度边 | 32 条 × 4 像素 = 128 | 16 条垂直 + 16 条水平 |
| 色度边 | 16 条 × 4 像素 = 64 | Cb/Cr 各 8 条 |
| 小计 | **192** | 每像素一拍 |
| `DF_12_cycles` | **+12** | 把 p2/p3 与转置缓冲写回帧存 |
| **合计** | **204** | 正好是论文标题里的数字 |

**实测 209 的差额 = 5 拍**，是五级流水线（MR→TD→PRE→FIR→MW）的
**填充 + 排空**开销。这 5 拍只在每个 MB 的头尾各出现一次，
不随 MB 数量增长，所以 MB 越多，相对开销越小。

> **这就是"流水线深度"与"吞吐率"的区别**：
> 204 是**稳态吞吐**（每 MB 192+12），209 是**单 MB 的端到端延迟**。
> 做系统集成时用 204 算带宽，做时序分析时用 209 算关键路径。

## 11.3 实验三：门控时钟到底省了多少

### 目的

量化 39 路门控时钟的实际占空比 —— 这是 293µW 的主要来源。

### 探针

```verilog
// /tmp/lab_gclk.v
module lab_gclk;
    integer irf = 0, df = 0, sum_e = 0, clk_e = 0, pulses = 0;

    always @ (posedge tb_nova.clk) clk_e = clk_e + 1;
    always @ (posedge tb_nova.u_nova.reconstruction.gclk_Inter_ref_rf) irf   = irf + 1;
    always @ (posedge tb_nova.u_nova.reconstruction.gclk_DF)           df    = df + 1;
    always @ (posedge tb_nova.u_nova.reconstruction.gclk_blk4x4_sum)   sum_e = sum_e + 1;

    always @ (posedge tb_nova.u_nova.end_of_MB_DEC) begin
        pulses = pulses + 1;
        if (pulses == 594) begin                 // 594 脉冲 = 297 个 MB（每 MB 两脉冲）
            $display("[GCLK] clk edges = %0d, MBs = %0d", clk_e, pulses/2);
            $display("[GCLK]   Inter_ref_rf = %0d (%0.1f%%)  per-MB %0d", irf,   irf*100.0/clk_e,   irf/(pulses/2));
            $display("[GCLK]   DF           = %0d (%0.1f%%)  per-MB %0d", df,    df*100.0/clk_e,    df/(pulses/2));
            $display("[GCLK]   blk4x4_sum   = %0d (%0.1f%%)  per-MB %0d", sum_e, sum_e*100.0/clk_e, sum_e/(pulses/2));
        end
    end
endmodule
```

> ⚠️ **为什么异步探针 `always @(posedge end_of_MB_DEC)` 要写 `pulses/2`？（源码与波形核实真相！）**
>
> 从 RTL 设计逻辑看，`end_of_MB_DEC`（`hybrid_pipeline_ctrl.v:159-174`）**每个宏块本来只有效 1 拍**（同步逻辑 `always @(posedge clk) if (end_of_MB_DEC)` 和门控时钟 `gclk_end_of_MB_DEC` 看到的都精确是 **99 拍/帧**，见第 12 章波形实测！）。
>
> **但为什么这里用异步边沿 `@(posedge end_of_MB_DEC)` 会数出 2 倍次数？** 根因在 `src/sum.v:225-241` 的**两个独立 `always @(posedge clk)` 块**：
> - 在第 22 块结束的那一拍上升沿，`blk4x4_rec_counter` 从 `22 → 23` 与 `blk4x4_sum_counter` 从 `3 → 4`（使 `end_of_one_blk4x4_sum` 从 `1 → 0`）按 NBA 队列先后执行；
> - 在 iverilog 中 `blk4x4_rec_counter` 先更新为 `23`，而 `end_of_one_blk4x4_sum` 仍短暂为 `1` —— 在这 **0 ns（1 个 delta cycle）** 里，组合信号 `end_of_MB_rec = (blk4x4_rec_counter == 23 && end_of_one_blk4x4_sum)` 产生了一次 **0 宽度毛刺（`0→1→0`）**，顺带把组合输出 `end_of_MB_DEC` 也顶出一次 0 ns 假上升沿！
> - 负电平锁存器 `gclk_end_of_MB_DEC` 和同步触发器完全过滤掉了这个 0 ns 毛刺，**但异步敏感列表 `@(posedge end_of_MB_DEC)` 会把它和真正第 23 块结束的上升沿都数进去**（每 MB 共 2 次）！
> - **最佳实践**：写探针时直接用同步写法 `always @(posedge tb_nova.clk) if (tb_nova.u_nova.end_of_MB_DEC)`，就能干净数出 99 次/帧，完全不用 `/2`（下面实验九的 `perf_counter.v` 就是同步写法）。

### 命令

```bash
iverilog -g2005 -o /tmp/lab_gclk.vvp -s tb_nova -s lab_gclk -I rtl \
         tb/tb_nova.v rtl/*.v /tmp/lab_gclk.v

vvp /tmp/lab_gclk.vvp +bitstream=../test/bitstream/akiyo300_1ref.txt \
    +out=/tmp/lab_gclk.yuv +frames=6 2>&1 | grep "\[GCLK\]"
```

### 预期输出

```
[GCLK] clk edges = 132397, MBs = 297
[GCLK]   Inter_ref_rf = 22342 (16.9%)  per-MB 75
[GCLK]   DF           = 62161 (47.0%)  per-MB 209
[GCLK]   blk4x4_sum   = 28513 (21.5%)  per-MB 96
```

**注意 `DF = 209 cycles/MB` —— 和实验二用完全不同的方法测到的 209 一致。**
两个独立探针互相印证，这是数据可信的最强证据。

### 你该看出什么

**1. `gclk_Inter_ref_rf` 的 16.9% 是"akiyo 特有"的数字，不是通用的。**

只跑 2 帧时它是 **0.0%**（2 次翻转），因为**第 1 帧全是 intra MB**，
根本不做运动补偿。跑到 6 帧才升到 16.9%，因为第 2 帧起有 8/99 个 inter MB。

**换 foreman（高运动序列）这个数字会高得多。** 这说明门控时钟的省电效果
**强烈依赖视频内容** —— 这就是为什么低功耗设计必须"内容自适应"。

**2. `gclk_DF` 的 47.7% 是最高的，因为去块滤波是唯一"每个 MB 都必做"的环节。**

不管是 skip、inter 还是 intra，只要 `disable_DF == 0`，
每个 MB 都要过 DF。用 per-MB 探针测：**DF 每 MB 占用 211 个周期**，
而一个 MB 总共只有 **333 周期** ——

```
211 / 333 ≈ 63%
```

**去块滤波吃掉了三分之二的时间。** 这就是为什么作者要专门为 DF
写一篇论文（TCSVT 2008），也是为什么这一章的实验二值得单独做。

**3. `gclk_blk4x4_sum` 的 21.5% 对应"重建"本身。**

`blk4x4_sum_counter` 是 0..3 循环、4 是空闲态，所以 4/5 = 80% 理论占空比。
实测 21.5% 说明**大部分时间它停在 4（空闲），等前面的流水线供数据**。
per-MB 探针给出 **96 周期/MB** —— 一个 MB 有 24 个 4×4 块，
所以平均**每块 4 周期**，远小于第 4 章按流水线深度估的 16 周期/块。
这正是"混合自适应流水线"的含义：**IQIT、预测、sum 都在并行跑，
哪个环节有空就关掉哪个** —— sum 只在预测结果和残差都就绪时才开 4 拍。

### 对照实验：不门控会怎样

```bash
# 把 rec_gclk_gen.v 里的全部 21 路 gclk 改成直连 clk（注意第 189 行 gclk_rescale 用的是门级例化 and！）
cp rtl/rec_gclk_gen.v /tmp/rec_gclk_gen.v.bak

## 11.4 实验四：关掉去块滤波，看 PSNR 掉多少

### 目的

量化去块滤波对画质的贡献，理解"为什么 H.264 必须有 DF"。

### 命令

```bash
cd /home/chenye/learning/nova/sim

# 正常（DF 开）
./scripts/run_regression.sh -n 5 --tag lab_df_on

# 关掉 DF（pin_disable_DF=1）
./scripts/run_regression.sh -n 5 --nodb --tag lab_df_off
```

`--nodb` 给 testbench 传 `+nodb`，tb 把 `pin_disable_DF` 拉成 1。

### 预期输出（DF 关掉时）

```
[compare] 总像素数    : 190080
[compare] 不同像素总数: 75947
[compare] 最差单点    : 帧 0 / Y / maxdiff=24
[compare] 整序列 PSNR : 46.35 dB
[compare] 结果: FAIL —— 5 帧存在差异 (首帧 0, 末帧 4)
```

**注意这是"预期 FAIL"** —— 关掉 DF 本来就不该和 ffmpeg 一致，
因为 ffmpeg 是**按标准开启 DF** 的。这个 FAIL 恰恰证明 DF 在工作。

### 你该看出什么

| 指标 | 数值 | 含义 |
|---|---|---|
| PSNR | 46.35 dB | 已经很高，因为 akiyo 是静止序列 |
| 不同像素 | 75947 / 190080 = **40%** | 40% 的像素被 DF 改动过 |
| maxdiff | 24 | 单个像素最多差 24 级（约 9%） |

**40% 的像素被动过** —— 这个数字说明去块滤波不是"锦上添花"，
而是**H.264 画质的关键组成**。块效应（blocking artifact）是
基于块的编码的固有缺陷，DF 专门用来消除它。

**为什么 PSNR 还有 46 dB？** 因为 akiyo 是极低运动序列（几乎全是 skip MB），
残差很小，块边界本来就不明显。

**换成 foreman 会掉到 35 dB 左右** —— 运动剧烈时块效应严重，DF 更重要。

> **这也解释了第 7 章为什么值得单独一篇 TCSVT 论文**：
> 204 cycles/MB、单端口 SRAM、五级流水，而它只影响 40% 的像素。
> 在 293µW 的总预算里，DF 占了将近一半的动态功耗。

## 11.5 实验五：变频四档，看速率控制怎么工作

### 目的

理解 `freq_ctrl[1:0]` 与 `cycles_per_frame` 的对应关系，并亲手验证
**一个非常容易搞错的事实**：`freq_ctrl` 不改变解码一个 MB 的速度，
它只改变"什么时候开始解下一帧"。

### 命令

```bash
cd /home/chenye/learning/nova/sim

for f in 0 1 2 3; do
    vvp out/nova_tb.vvp +bitstream=../test/bitstream/akiyo300_1ref.txt \
        +out=/tmp/lab_f$f.yuv +frames=14 +freq=$f 2>&1 \
        | grep -E "DONE|emitted picture (1|14) "
done
```

> **为什么跑 14 帧而不是 4 帧？** 跑 4 帧时，你算出来的"每帧周期"里
> 混着**启动填充**（第一帧要预充位流缓冲）和**帧边界等待**，
> 不是稳态值。**至少要跳过前 2 帧**，否则会得到一张自相矛盾的表
> （我们最早那版文档就踩了这个坑，详见第 9.7 节）。

### 预期输出

```
[TB] emitted picture 1 at cycle 45067
[TB] emitted picture 14 at cycle 630119
[TB] DONE: 14 pictures, 630121 cycles, 45009 cycles/picture

[TB] emitted picture 1 at cycle 50067
[TB] emitted picture 14 at cycle 700119
[TB] DONE: 14 pictures, 700121 cycles, 50009 cycles/picture

[TB] emitted picture 1 at cycle 57367
[TB] emitted picture 14 at cycle 798638
[TB] DONE: 14 pictures, 798640 cycles, 57046 cycles/picture

[TB] emitted picture 1 at cycle 62154
[TB] emitted picture 14 at cycle 963738
[TB] DONE: 14 pictures, 963740 cycles, 68839 cycles/picture
```

### 四档对照表

| `freq_ctrl[1:0]` | `cycles_per_frame` | 14 帧均值 | 逐帧增量 | 与设定值 |
|---|---|---|---|---|
| `00` | 45000 | **45009** | 精确 +45004 | +4 |
| `01`（默认）| 50000 | **50009** | 精确 +50004 | +4 |
| `10` | 57300 | **57046** | 53352~57937（抖）| −254 |
| `11` | 70000 | **68839** | 61265~70637（抖）| −1161 |

**前两档的逐帧增量精确等于 `cycles_per_frame + 4`**，
后两档开始抖动。

### 你该看出什么

**1. `freq=0/1` 时，每帧周期 = `cycles_per_frame` + 4，一个周期都不差。**

```
45004 = 45000 + 4
50004 = 50000 + 4
```

那 4 个周期是**帧边界握手开销**（`end_of_one_frame` 拉高 → 解析器真正启动）。
说明这两档下**重建流水线有富余，完全在等速率控制的放行信号**。

**2. `freq=2/3` 为什么出现小于设定值的“抖动”？**

注意上面 `freq=3`（设定 70,000）的首页吐在 **62,154**，后续增量低至 61,265 —— 它们比 `cycles_per_frame` 更小，说明**不是算力追不上**，而是**再次触发了 `tb_nova.v` 的 `IDLE_FLUSH = 20000` 兜底逻辑**！
- 第 1 帧在 cycle **42,154** 写完外部帧存，随后一直空等到 cycle 70,000 才来下一帧 `slice_header_s6`，空等时间 `27,846 > 20,000`，于是 TB 恰好在 **`42,154 + 20,000 = 62,154`** 处提前把帧吐出！
- 后续 P 帧写完时间随画面内容在 33,000~37,000 拍波动，加 20,000 后就表现为 53k~68k 的抖动。若把 `tb_nova.v` 里的 `IDLE_FLUSH` 提到 45,000 以上，`freq=2/3` 也会变成干净的精确 `+57304` / `+70004`。

**3. 最重要的一条：MB 级速率与 `freq_ctrl` 完全无关。**

用一个探针统计**帧内相邻 MB 起始时刻的间隔**（跳过帧边界）：

```verilog
// /tmp/mbrate.v
always @ (posedge tb_nova.u_nova.end_of_MB_DEC) begin
    n = n + 1;
    if (n % 2 == 1) begin              // 每个 MB 产生两个脉冲，取第一个
        if (prev != 0 && frames >= 3 && frames <= 12)
            begin sum = sum + ($time/680 - prev); cnt = cnt + 1; end
        prev = $time/680;
    end
end
```

四档各跑 13 帧，结果：

```
cf=0  [RATE] in-frame avg MB period = 330 cycles over 980 MBs
cf=1  [RATE] in-frame avg MB period = 330 cycles over 980 MBs
cf=2  [RATE] in-frame avg MB period = 330 cycles over 980 MBs
cf=3  [RATE] in-frame avg MB period = 330 cycles over 980 MBs
```

**四档一模一样，都是 330 cycles/MB。**

> ⚠️ **探针注意**：如 11.3 节所核实，由于 `sum.v:225-241` 在第 22→23 块边界存在 0 ns delta-cycle 毛刺，异步 `@(posedge end_of_MB_DEC)` 探针会在每 MB 触发两次（一次在 blk 22→23 的 0 ns 毛刺，一次在 blk 23 真正的结束沿），所以 `n % 2 == 1` 只取每对的第一个脉冲。
>
> 如果不做这个过滤，你会得到 `gap=13`（正是第 23 块这 1 个色度 4×4 块的耗时！）和 `gap=312` 交替的数据 —— 若把探针改成同步写法 `always @(posedge tb_nova.clk) if (tb_nova.u_nova.end_of_MB_DEC)`，就能直接避开 0 ns 毛刺，无需 `% 2`。

**结论**：`freq_ctrl` **只控制解析器什么时候开始解下一帧，完全不改变
重建流水线跑一个 MB 的速度**。想让每个 MB 更快，只能改 RTL；
想让帧率更高，才去调 `freq_ctrl`。这两件事是**正交**的。

### 加分实验：二分找到 akiyo 的真实算力下限

既然 `freq=0` 实测 45009，那 `cf0` 能不能设小一点？

```bash

cp rtl/nova_defines.v /tmp/nd.bak

```

|---|---|---|
| 40000 | FAIL | 179127 |
| 42000 | FAIL | 1536 |

**为什么差 40 个像素？** 因为 `cf0` 太小时，**下一帧的 slice header 会在

### 一条附带的教训：很多数字是调出来的，不是算出来的

`nova_defines.v` 注释里那句 "because ext_frame_RAM is changed from

是调出来的，不是算出来的**。你在做类似设计时，不要指望"算出一个
最优的 `cycles_per_frame`"：**先按最坏情况给个保守值，再拿实际
序列去二分逼近**，就像我们上面做的那样。

## 11.6 实验六：MB 类型分布与每 MB 周期

### 目的

把"平均每 MB 周期"拆开，看**不同 MB 类型各花多少周期** ——
这是判断"性能瓶颈在哪"最直接的方法。

### 探针

```verilog
// /tmp/mbtype2.v
module mbtype2;
    integer n=0, prev=0, frames=0, i, mb=0;
    integer cnt[0:15];
    integer tot[0:15];
    reg [3:0] t;
    initial begin for (i=0;i<16;i=i+1) begin cnt[i]=0; tot[i]=0; end end

    always @ (posedge tb_nova.u_nova.end_of_MB_DEC) begin
        n = n + 1;
        if (n % 2 == 1) begin                 // 每 MB 两个脉冲，只取第一个
            mb = mb + 1;
            if (prev != 0 && frames >= 3 && frames <= 40) begin
                t = tb_nova.u_nova.mb_type_general;
                cnt[t] = cnt[t] + 1;
                tot[t] = tot[t] + ($time/680 - prev);
            end
            prev = $time/680;
        end
    end

    always @ (posedge tb_nova.slice_header_s6) begin
        frames = frames + 1;
        if (frames == 41) begin
            $display("[TYPE] mb_type  count  avg_cycles_per_MB");
            for (i=0;i<16;i=i+1) if (cnt[i] != 0)
                $display("[TYPE]    %0d      %0d       %0d", i, cnt[i], tot[i]/cnt[i]);
            $finish;
        end
        prev = 0; n = 0;
    end
endmodule
```

### 命令

```bash
cd /home/chenye/learning/nova/sim
iverilog -g2005 -o /tmp/mt2.vvp -s tb_nova -s mbtype2 -I rtl \
         tb/tb_nova.v rtl/*.v /tmp/mbtype2.v
vvp /tmp/mt2.vvp +bitstream=../test/bitstream/akiyo300_1ref.txt \
    +out=/tmp/mt2.yuv +frames=41 +freq=0 +maxcyc=5000000 2>&1 | grep "\[TYPE\]"
```

### 预期输出

```
[TYPE] mb_type  count  avg_cycles_per_MB
[TYPE]    0      239       422
[TYPE]    1      92       432
[TYPE]    2      136       433
[TYPE]    4      177       515
[TYPE]    5      3080       326
```

### 对照表

| `mb_type` | 含义 | 次数 | **cycles/MB** | 为什么 |
|---|---|---|---|---|
| `5` | `P_skip` | 3080（83%）| **326** | 跳过 MV 解码、跳过残差、跳过 IQIT，直接复制参考块 |
| `0` | `Inter16x16` | 239 | **422** | 一个 MV，预加载一次 |
| `1` | `Inter16x8` | 92 | 432 | 两个 MV |
| `2` | `Inter8x16` | 136 | 433 | 两个 MV |
| `4` | `P_8x8` | 177 | **515** | 4 个 8×8 子块各自有 MV，**预加载窗口跑 4 次** |

### 你该看出什么

**1. skip 最快、P_8x8 最慢，差距 58%。**

`515 / 326 = 1.58`。这个差距几乎全部来自**运动补偿的预加载次数**：
- 16×16 / 16×8 / 8×16：每 MB 只预加载一次参考窗口（422~433）
- P_8x8：4 个子块各预加载一次（515）
- skip：完全跳过预加载（326）

**2. 加权平均对得上独立测量。**

```
(3080×326 + 239×422 + 92×432 + 136×433 + 177×515) / 3724 = 337 cycles/MB
```

而我们用另一个探针直接测帧内 MB 间隔得到的是 **330**（11.5 节）。
两者差 2%，来自统计窗口不同（这个统计了 38 帧，那个统计了 10 帧）。
**两个独立方法互相印证，说明数据是可信的。**

**3. 为什么 skip MB 还要 326 周期？**

因为 skip MB **并没有真的"跳过"** —— 它仍然要：
- 做去块滤波（**固定 204 周期**，占 326 的 **63%**）
- 从参考帧读 13×13 窗口、做 MC
- 走完整个状态机（CAVLC 侧的 skip_run 解析、MB 计数更新）

**这就是为什么作者要专门为 DF 写一篇论文**：DF 是**所有 MB 都要付的固定成本**，
优化它等于优化全部 MB。论文把 DF 压到 204 cycles/MB，
在 326 的 skip MB 里就是 63% 的占比 —— **省 DF 才是省大钱**。

**4. 早期文档里"skip 634 / inter 441"是错的。**

那组数字来自 `IDLE_FLUSH = 5000` 那个 bug 时期（见 9.2 节），
时间戳被 flush 兜底污染。**实测数据一定要在修好 tb 之后再取。**
这也说明一件事：**性能数据比功能数据更容易被"看起来对"掩盖** ——
功能错了你一眼能看出画面花屏，性能错了却只是"数字不太对"，
反而更难发现。

## 11.7 实验七：复现"x264 码流解不了"

### 目的

亲手撞一次墙，理解为什么 [10 章](10-兼容性陷阱与移植指南.md) 说这是"第一个会撞的墙"。

### 命令

```bash
cd /home/chenye/learning/nova/sim

# 用 ffmpeg 生成一个标准 baseline 码流
ffmpeg -v error -f lavfi -i testsrc=size=176x144:rate=30:duration=1 \
       -c:v libx264 -profile:v baseline -qp 28 -g 30 \
       -x264-params "keyint=30:min-keyint=30:ref=1:slices=1" \
       -f h264 /tmp/lab_x264.264 -y

# 看看它的 SPS 长什么样
ffprobe -v error -show_streams /tmp/lab_x264.264 | grep -E "profile|width|height|refs"

# 用 nova 解
./scripts/run_regression.sh -b /tmp/lab_x264.264 -n 5 --tag lab_x264
```

### 预期输出

```
[compare] 最差单点    : 帧 0 / Y / maxdiff=255
[compare] 整序列 PSNR : 4.93 dB
[compare] 结果: FAIL —— 5 帧存在差异 (首帧 0, 末帧 4)
```

**PSNR 4.93 dB 是什么概念？** 相当于"随机噪声"。
如果两个完全无关的图像比，PSNR 大约是 8~10 dB。
**4.93 比"完全无关"还差**，说明 nova 输出的根本不是图像
（大量像素是 0 或 128）。

### 诊断：为什么

```bash
# 提取 SPS 的原始字节
xxd -l 64 /tmp/lab_x264.264
```

你会看到 SPS 的 NAL 头 `67`（type 7），后面跟 `42 c0 0b ...`：

| 字节 | 含义 | 值 |
|---|---|---|
| `42` | profile_idc | 66 = Baseline |
| `c0` | constraint_set | `1100 0000`（Constrained Baseline）|
| `0b` | level_idc | 11 = Level 1.1 |

**关键在后面的 `pic_order_cnt_type`**。x264 加 `-profile:v baseline`
时**强制** `pic_order_cnt_type = 2`（因为 baseline 不用 POC 排序）。

而 nova 的 SPS 状态机（`BitStream_parser_FSM_gating.v:206-214`）是：

```verilog
// 无论 pic_order_cnt_type 是什么，都按 poc_type == 0 的布局继续解析
pic_order_cnt_type_s:
    seq_parameter_set_state <= log2_max_pic_order_cnt_lsb_minus4_s;   // ← 无条件！
```

于是 **从这一位开始，后面全部错位**：

| 字段 | nova 以为读的是 | 实际读到的是 |
|---|---|---|
| `log2_max_pic_order_cnt_lsb_minus4` | 6 | `num_ref_frames` = 1 |
| `num_ref_frames` | 1 | `gaps_flag` + 后续位 |
| `pic_width_in_mbs_minus1` | 0 | 0（错）|
| `pic_height_in_map_units_minus1` | 0 | 0（错）|

**宽高都读成 0** —— 虽然 nova 根本不用这两个值（见 10 章），
但 SPS 解析器本身也会因为后续位流不是它期望的而卡住。

### 再试一次：强行指定 poc_type=0

```bash
ffmpeg -v error -f lavfi -i testsrc=size=176x144:rate=30:duration=1 \
       -c:v libx264 -profile:v baseline -qp 28 \
       -x264-params "keyint=30:min-keyint=30:ref=1:slices=1:pic_order_cnt_type=0" \
       -f h264 /tmp/lab_x264_poc0.264 -y

./scripts/run_regression.sh -b /tmp/lab_x264_poc0.264 -n 2 --tag lab_poc0
```

### 预期输出

```
[compare] 整序列 PSNR : 12.84 dB
[compare] 结果: FAIL —— 2 帧存在差异
```

**还是 FAIL，但 PSNR 从 4.93 涨到 12.84 —— 有进步，说明 poc_type 确实是第一个坎。**

再分析差异：

```bash
python3 - <<'EOF'
import sys
w, h = 176, 144
fs = w*h*3//2
a = open('/tmp/lab_poc0_nova.yuv','rb').read()[:fs]
b = open('/tmp/lab_poc0_ref.yuv','rb').read()[:fs]
# Y 平面均值
ya = sum(a[:w*h])/(w*h); yb = sum(b[:w*h])/(w*h)
print(f"Y mean: nova={ya:.2f}  ref={yb:.2f}")
# U 平面（从 w*h 开始，w*h/4 个字节）
ua = sum(a[w*h:w*h*5//4])/(w*h//4); ub = sum(b[w*h:w*h*5//4])/(w*h//4)
print(f"U mean: nova={ua:.2f}  ref={ub:.2f}")
EOF
```

**典型输出**：

```
Y mean: nova=127.31  ref=125.14
U mean: nova=200.21  ref=128.42
```

**Y 差不多，但 U 偏了 72 级** —— 这是色度出了问题。
说明还有别的工具 nova 不支持（大概率是 `vui_parameters`：
`-profile:v baseline` 让 x264 写入 VUI，nova 在
`vui_parameter_present_flag_s` 之后直接跳到 `rst`，VUI 内容全被当成后续语法）。

### 结论

**要用 nova，码流必须满足**：

1. `pic_order_cnt_type == 0`
2. 无 SEI（type 6）/ AUD（type 9）NAL
3. 单 slice/帧
4. 无 FMO（`num_slice_groups_minus1 == 0`）
5. 无 8×8 变换（`transform_8x8_mode_flag == 0`）
6. 无 weighted prediction
7. **无 VUI**

**最省事的做法**：直接用 JM 参考软件的 Baseline 配置编码
（nova 附带的 `akiyo300_1ref.txt` 就是 JM94 编的）。

## 11.8 实验八：改一行代码，看现象

### 目的

通过"故意改错"来理解每个模块的作用 —— 这是学 RTL 最快的方法。

### 实验 8a：把 `IsHadamard` 改成恒 1

**改什么**：`rtl/IQIT.v` 里的 IsHadamard 赋值：

```verilog
// 原版
assign IsHadamard = (res_DC == 1'b1 && (OneD_counter != 0 || TwoD_counter != 0))? 1'b1:1'b0;

// 改成
assign IsHadamard = 1'b1;
```

**实测结果**（3 帧）：

```
[compare] 总像素数    : 114048
[compare] 不同像素总数: 76391
[compare] 最差单点    : 帧 0 / Y / maxdiff=71
[compare] 整序列 PSNR : 32.96 dB
[compare] 结果: FAIL —— 3 帧存在差异

逐平面（帧 0）:
   0     Y     maxdiff=71   mean=3.948   不同像素 20011   PSNR 32.07
   0     U     maxdiff=63   mean=2.688   不同像素  4036   PSNR 32.96
   0     V     maxdiff=30   mean=0.635   不同像素  1422   PSNR 42.53
```

**三个观察**：

1. **Y 平面 67% 的像素（20011/25344）变了** —— 不是局部问题，是全局的
2. **U 也变了（maxdiff 63）**，比预想的严重 —— 因为色度 AC 系数同样走
   4×4 IDCT，`IsHadamard` 恒 1 也会把色度 AC 的归一化搞错
3. **V 影响最小（maxdiff 30）** —— 因为 akiyo 画面偏暖，V 分量的 AC 能量本来就小

**为什么**：在 `IQIT.v:279, 771-791` 中，`IsHadamard` 用来区分 **DC 的 Hadamard 变换**（`1D` 与 `2D` 两个方向系数都是 `±1`，`D1/D3` 不右移）和 **AC 的 4×4 整数 IDCT**（`1D` 与 `2D` 两个方向系数都有 `1/2`，`D1/D3` 必须算术右移 1 位）。把 `IsHadamard` 改成恒 `1` 后，DC 路径不受影响，但**所有 Y/U/V 的 AC 4×4 IDCT 都丢失了 `>> 1` 缩放**，反变换出的残差幅值严重失真，于是 67% 像素出错、PSNR 暴跌到 32.96 dB！

> **这就是第 4 章强调的关键开关。** 一行代码，**67% 的像素偏移、
> PSNR 掉到 32.96 dB**。而且注意：32.96 dB 仍然"看起来不差"——
> 这就是为什么必须看 maxdiff（71）而不是 PSNR。

### 实验 8b：把 `filterH_6tap` 的 `+16` 改成 `+0`

**改什么**：`rtl/Inter_pred_LPE.v` 里 filterH_6tap 的舍入：

```verilog
// 原版
assign sum_round = (H_need_round)? (raw_out + 16):0;
assign round_tmp = (H_need_round)? sum_round[14:5]:0;

// 改成（去掉舍入）
assign sum_round = (H_need_round)? raw_out:0;
assign round_tmp = (H_need_round)? sum_round[14:5]:0;
```

**预期**：inter MB 的像素整体偏暗约 0.5 级（16/32 = 0.5），
`maxdiff` 变成 1，**PSNR 仍然很高但 `maxdiff != 0`**。

**实测结果**（3 帧）：

```
[compare] 总像素数    : 114048
[compare] 不同像素总数: 186
[compare] 最差单点    : 帧 1 / Y / maxdiff=1
[compare] 整序列 PSNR : 76.01 dB
[compare] 结果: FAIL —— 2 帧存在差异 (首帧 1, 末帧 2)
```

**76.01 dB** —— 这个数字是本章最有说服力的一行。

如果只看 PSNR，76 dB 意味着"几乎完美"（一般认为 40 dB 以上就看不出差别）。
但它**只错了 186 个像素、每像素只差 1 级**。
换成 PSNR 判据，这个 bug 会被当成"通过"；换成 `maxdiff == 0`，它立刻暴露。

**这个实验最有价值的地方**：它证明了**为什么必须用 `maxdiff == 0` 而不是 PSNR**。

### 实验 8c：把 DF 的 alpha 表某一项改掉（**先踩一个坑**）

**第一版尝试（会失败）**：改 `rtl/DF_pipeline.v` 里
`6'd32: alpha <= 8'd32;` → `8'd33`

**结果**：**PASS，一个像素都没变。**

**为什么？** 因为你改的表项根本没被用到。用探针实测一下
`indexA` 到底取了哪些值：

```verilog
// /tmp/idxA.v
module idxA;
    reg seen [0:63];
    integer i;
    initial for (i=0;i<64;i=i+1) seen[i]=0;
    always @ (posedge tb_nova.clk)
        if (tb_nova.reset_n===1'b1 &&
            tb_nova.u_nova.reconstruction.DF_top.DF_pipeline.indexA !== 6'bx) begin
            if (!seen[tb_nova.u_nova.reconstruction.DF_top.DF_pipeline.indexA]) begin
                seen[tb_nova.u_nova.reconstruction.DF_top.DF_pipeline.indexA] = 1;
                $display("[IDXA] seen indexA = %0d",
                         tb_nova.u_nova.reconstruction.DF_top.DF_pipeline.indexA);
            end
        end
endmodule
```

```bash
iverilog -g2005 -o /tmp/idxA.vvp -s tb_nova -s idxA -I rtl \
    tb/tb_nova.v rtl/*.v /tmp/idxA.v
vvp /tmp/idxA.vvp +bitstream=../test/bitstream/akiyo300_1ref.txt \
    +out=/tmp/idxA.yuv +frames=6
```

**输出**：

```
[IDXA] seen indexA = 0
[IDXA] seen indexA = 28
```

**akiyo 序列的 `indexA` 只取 0 和 28 两个值**
（`indexA = QPy + 2 × slice_alpha_c0_offset_div2`，akiyo 全程 QP=28、offset=0）。
改 `6'd32` 那一项，**永远不会被访问到**。

**第二版（正确做法）**：改实测会碰到的项 ——
`6'd28: alpha <= 8'd20;` → `8'd21`

**实测结果**（3 帧）：

```
[compare] 总像素数    : 114048
[compare] 不同像素总数: 123
[compare] 最差单点    : 帧 0 / V / maxdiff=8
[compare] 整序列 PSNR : 69.39 dB
[compare] 结果: FAIL —— 3 帧存在差异
```

**三个观察**：

1. **只有 123 个像素变化**（占 114048 的 0.1%）—— alpha 从 20 改到 21，
   只影响"|p0−q0| 恰好等于 20"的那些边界
2. **差异全部在 V 平面** —— 因为色度的 `indexA_c` 用的是同一张 alpha 表，
   而 akiyo 的 U/V 平坦区域大、边界更容易卡在阈值上
3. **maxdiff 只有 8** —— 阈值判断改变后，滤波强度从弱变强（或反之），
   单点最多偏 8 级

**这个实验教你两件事**：

1. **阈值型参数的错误极其难查** —— 它不影响大部分数据，只在边界条件下暴露。
   写测试平台时要用**多种 QP、多种内容**的码流。
2. **做"改一行看现象"的实验，必须先用探针确认那行代码真的被执行到。**
   否则你改了半天看不到现象，会误判成"这行代码没用"，
   而真相是"这段码流走不到这条路径"。**这个坑比实验本身更值得记住。**

### 实验 8d：把 `BitStream_buffer` 的半满判据改掉（**又踩一个坑**）

**第一版尝试（不会卡死）**：`rtl/BitStream_buffer.v` 里的 `pc > 63` → `pc > 127`

**预期**：仿真直接卡死（`BitStream_buffer_valid_n` 永远不为 0）。

**实际结果**：**一切正常，两帧全对。**

```
[TB] emitted picture 1 at cycle 50067 (t=34046240)
[TB] emitted picture 2 at cycle 100071 (t=68048960)
[TB] DONE: 2 pictures, 100073 cycles, 50036 cycles/picture
```

**为什么没卡死？** 因为半满检测**有三条冗余判据**（`BitStream_buffer.v:68-73`）：

```verilog
if (((pc > 63 && pc_previous <= 63) || (pc <63 && pc_previous >=63)) && half_fill_counter == 0)
    half_fill_counter <= 1;
else if (pc > 63 && half_fill_counter == 0 && buffer_index == 0)
    half_fill_counter <= 1;
else if (pc < 63 && half_fill_counter == 0 && buffer_index == 64)
    half_fill_counter <= 1;
```

- 第 1 条：**看 `pc` 的跨沿**（`pc_previous` 在 63 的另一侧）
- 第 2 条：**看 `buffer_index == 0`**（8 个 16bit 槽的写指针刚回绕）
- 第 3 条：**看 `buffer_index == 64`**（4 bit 字段写满 8 槽后的值）

三条指向同一件事——"缓冲区被消耗到半满"，**任意一条成立就 refill**。
所以改坏第 1 条，第 2、3 条照常接管。

**第二版（把三条全部废掉）**：

```verilog
if (1'b0)      half_fill_counter <= 1;
else if (1'b0) half_fill_counter <= 1;
else if (1'b0) half_fill_counter <= 1;
```

**实测结果**：**确实卡死。**

```
[TB] end-of-stream flush: emitting last picture from buffer 0
[TB] emitted picture 1 at cycle 55584 (t=37797800)
[TB] TIMEOUT after 500001 cycles, 1 pictures decoded
```

只吐出 1 帧，而且是靠 testbench 的 flush 兜底路径吐的；输出文件 38016 B。

**这个实验教你两件事**：

1. **位宽是 Verilog 最容易出错的地方**。`pc` 是 7 bit，最大值 127，
   `> 127` 是恒假条件 —— 但**恒假不等于会崩**，只要还有别的路径兜住。
   综合工具会给你 warning，仿真时它只是"某条路径不工作"。
2. **冗余设计会让"改一行看现象"失效**。这是第三个"改了没反应"的实验
   （前面 8c 是"改的表项没被用到"）—— **一个 IP 里越关键的地方，
   保护代码往往越多**，这正是它可靠的原因，也是它难被"一行改动"理解的原因。

## 11.9 实验九：加一个新模块（进阶）

### 目的

从"读代码"跨到"改代码"。给 nova 加一个**简单的性能计数器**，
统计每个 MB 的周期数和 MB 类型，输出到文件。

### 设计

新建 `rtl/perf_counter.v`：

```verilog
// perf_counter.v —— 统计每个 MB 的周期数与类型
// 纯观测模块，不参与解码逻辑
module perf_counter (
    clk, reset_n, end_of_MB_DEC, mb_type_general, mb_num_h, mb_num_v,
    pic_num, cycle_out, type_out, valid_out
);
    input        clk, reset_n, end_of_MB_DEC;
    input  [3:0] mb_type_general, mb_num_h, mb_num_v;
    input  [5:0] pic_num;

    output [31:0] cycle_out;      // 本 MB 消耗的周期
    output [3:0]  type_out;       // MB 类型
    output        valid_out;      // 一个脉冲，表示 cycle_out 有效

    reg [31:0] cycle_cnt, cycle_out_r;
    reg [3:0]  type_out_r;
    reg        valid_r;
    reg [31:0] last_cycle;

    always @ (posedge clk or negedge reset_n)
        if (!reset_n) begin
            cycle_cnt   <= 0;
            cycle_out_r <= 0;
            type_out_r  <= 0;
            valid_r     <= 0;
            last_cycle  <= 0;
        end else begin
            cycle_cnt <= cycle_cnt + 1;
            valid_r   <= 1'b0;
            if (end_of_MB_DEC) begin
                cycle_out_r <= cycle_cnt - last_cycle;   // 本 MB 的周期数
                type_out_r  <= mb_type_general;
                last_cycle  <= cycle_cnt;
                valid_r     <= 1'b1;
            end
        end

    assign cycle_out = cycle_out_r;
    assign type_out  = type_out_r;
    assign valid_out = valid_r;
endmodule
```

然后在 testbench 里实例化它并打印：

```verilog
// tb_nova.v 里加
wire [31:0] perf_cycle;
wire [3:0]  perf_type;
wire        perf_valid;

perf_counter u_perf (
    .clk(clk), .reset_n(reset_n),
    .end_of_MB_DEC(u_nova.end_of_MB_DEC),
    .mb_type_general(u_nova.mb_type_general),
    .mb_num_h(u_nova.mb_num_h), .mb_num_v(u_nova.mb_num_v),
    .pic_num(pic_num),
    .cycle_out(perf_cycle), .type_out(perf_type), .valid_out(perf_valid)
);

always @ (posedge clk)
    if (perf_valid)
        $fdisplay(perf_fd, "%0d %0d %0d %0d %0d",
                  pic_num, u_nova.mb_num_v, u_nova.mb_num_h, perf_type, perf_cycle);
```
